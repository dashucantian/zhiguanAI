## 六、本课顺手挖出的两条我方缺陷（**证据齐全，未动代码**）

### 现象
5／8 份归档里，**近六成相邻样本的时间戳只差 0.001 ms（1 微秒）**，而真实名义间隔应是 3.906 ms。我方 `timestamps` 数组**没有一个重复值**——对比之下，他方那份 205 个重复**原样留着**。

### 根因（读码定位，非推测）
`muse2-repo\muse2-master\muse_local_server.py:421-425`

```python
def _append_ts(self, t: float):
    """Append a sample timestamp, enforcing strict monotonic increase."""
    if self.timestamps and t <= self.timestamps[-1]:
        t = self.timestamps[-1] + 1e-6
    self.timestamps.append(t)
```

BLE 一包 4–5 个样本常共用同一**到达时刻**，`t <= last` 触发，包内第 2 个起被排成 `+1 µs、+2 µs…`。
这条是为了满足 `05_产品与开发\muse-direct\tools\ingest_session.py:254-265` 的规约校验（「字典 V1.2 §3.1 明文要求**严格单调**」，非单调即**中止入库**）。

### 后果（可量化）
`console_server.py:2137-2147` 用 `|diff(ts) − 1/sfreq|` 的 p95 当「抖动」显示在会话质检里：
**5 份中招的读到 20.9–21.5 ms**，3 份干净的是 0.00–0.10 ms。也就是说面板上那句「抖动 21 ms」**不是设备抖动，是我方自己造的台阶**。

### 附带发现（同一条时间戳链上的第二处）
`S04` 的时间戳**整条按 250 Hz 铺设**，而该会话设备是 Muse S、meta 写 256 Hz：
`N/256 = 3704.5 s` ≠ 实际跨度 `3796.5 s`，而 `N/250 = 3793.4 s`，误差仅 **3.1 s**。
⇒ **这份归档的时间轴系统性慢 2.4%，一个 63 分钟的会话被拉长到 67 分钟口径。**
机理与 `ingest_session.py:240-243` 自记的旧缺陷（写死采样率致合成时间轴压缩 2.4%，1 小时约 85 秒）一致；
09-18 的修复只管**新入库**，**盘上这份仍是旧轴**。任何用 S04 做长时程比对（入睡过渡、趋势斜率）的分析都会带上这个 2.4%。

### 与课程的对照（这一条最值钱）
同一类问题（包内样本共用一个时间戳），两条路：

| | 他方（课程） | 我方 |
|---|---|---|
| 做法 | 摘要里**如实报** 205 个重复 ＋ 打一句警告 | **改写**成微秒递增，让它「看起来合法」 |
| 声明 | `within_packet_interpolation: False` | 无任何声明 |
| 效果 | 问题留在证据里，可追 | 问题被抹进数据，且**污染下游指标** |

课程 §格9 的原话正好是判据：**"Duplicated clock values or large jumps require investigation, not silent interpolation."**

### 修法选项（**请法师裁定，本窗不出手**）
- **甲**：包内样本按标称间隔展开（第 k 个样本＝包时刻 + k/FS）。时间轴变均匀，但**这是插值**，须显式声明并标 `interpolated: True`。
- **乙**：把规约从「严格单调」降为「**单调不减**」，重复值原样保留，另设一栏报 `duplicate_timestamp_count`。与他方做法一致，**证据最诚实**。
