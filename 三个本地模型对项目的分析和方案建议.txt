## 四、工作线③的语音管道——这是当前最大的空白

TTS/ASR 不是大语言模型，是独立的本地小模型，Strix Halo 64GB 统一内存跑它们毫无压力：

- **会议录音转文字（ASR）**：**FunASR / SenseVoice**（[funasr.com](https://www.funasr.com/)）——中文强、带 VAD/标点/说话人分离、可 CPU 运行、提供 OpenAI 兼容接口，能直接接进你们现有 Agent 工作流。这是 2026 年本地中文转写的默认选择。
- **VR 实时语音引导（TTS）**：主选 **CosyVoice**（阿里开源，支持用法师声音克隆——"法师的声音在 VR 里引导"这件事对项目的叙事价值极大）；低延迟兜底用 **Kokoro/sherpa-onnx + Matcha**（ONNX、毫秒级）。
- **实时链路架构**（沿用你们 09-04 调研已定的"低频智能层"结论）：

```
EEG → 控制器(现有, <20ms) → Shader/音频参数        ← 帧级，不经过 LLM
```

LLM 只做"导演"不做"演员"——这条你们判语里已经有了，语音管道只是把它补完整。

## 一、先把"你们在做什么"说清楚：四层拆解

你列的 5 项工作其实可以归成 **4 层**，每一层的"数据敏感度 × 实时性要求 × 对模型能力的依赖"完全不同。这是后面所有架构决策的基础：

| 层级 | 对应你的工作 | 数据敏感度 | 实时性 | 核心诉求 |
|---|---|---|---|---|
| **A. 数据与资产层** | 脑电存储/筛查/标注/辅助建模、3D数字资产源数据 | ⚠️⚠️⚠️ 极高（个人生物特征，隐私红线） | 中 | 本地、可追溯、可复现 |
| **B. 实时交互层** | VR+脑电实时文字转语音引导交互 | ⚠️⚠️ 高 | ⚠️⚠️⚠️ 极高（<1s 延迟） | 低延迟、本地化 |
| **C. 内容与协作层** | 文档整理、会议录音转写、公众号文章、视频、流程管理 | 🟡 中（可能含项目信息但非生物数据） | 低 | 质量 + 效率 |
| **D. 管理与生态层** | 项目架构/分工/线上协同、社区运维、经验共享 | 🟢 低到中等 | 低 | 可复用、可沉淀 |

**这条线是关键结论：决定一个任务该本地还是上 API，看的不是"能不能"，而是"数据敏不敏感 + 要不要实时"。** 绝大多数工作（A/B 层）必须本地；只有 C/D 层里**不含私有信息的那部分**才值得考虑用外部 API。

## 二、核心架构原则：数据分级 + 一个"编排中枢"

我建议的顶层结构是 **"1 个本地编排中枢 + N 个专职模型/工具"**，而不是让三个大模型各干各的。原因：你们要的是**分工协作**，而协作需要一个"调度者"来分活、路由、汇总。

```
                    ┌─────────────────────────┐
   用户/社区 ─────▶ │  编排中枢(Router/Orchestrator)  │
                    │  任务分类 → 路由到对应模型/工具 │
                    └───────────┬───────────────┘
        ┌───────────────┬───────────────┬───────────────┐
   [Qwen 主力]      [快速模型]       [专用工具链]      [可选API]
   复杂推理/编排    实时对话/TTS提示   Whisper转写        非敏感创作
   RAG文档检索      低延迟交互         CosyVoice语音     特殊能力补充
   代码/架构设计                                              (见下)
```

**为什么这样分：**
- 单个大模型很难同时做到"又快又强又专"。用**一个路由层**把任务分给最合适的执行者，才是真正发挥三个模型价值的方式。
- 这也直接对应你第 1 项职责"**分工协作 + 项目架构维护**"——这个中枢本身就是你们项目管理能力的数字化体现。

## 四、哪些该用本地、哪些可考虑 API + 更好的开源模型推荐

### ✅ 必须/建议全部本地（对应你们的隐私红线）
- **语音转文字（会议录音）**：`faster-whisper`（large-v3，MIT 协议，本地跑，60分钟音频 RTX3090 约5分钟）+ `pyannote` 做说话人分离。**这是你们最该先落地的**——会议录音转写是高频刚需。
- **文字转语音（VR引导）**：`CosyVoice2` / `GPT-SoVITS`（支持中文、可声音克隆）或轻量的 `Piper`。实时交互建议用低延迟模型。
- **脑电数据处理**：开源生态已经很成熟——`BrainFlow`（数据采集/解析）、`braindecode`（HuggingFace 上的 EEG 深度学习工具箱，含预处理/可视化/分类架构）、`MNE-Python`、`MOABB`（BCI 基准）。这些直接对接你们的 A 层。
- **文档/RAG**：`RAGFlow` 或 `Dify`（都支持本地部署 + 接入本地 LLM），做项目文档的知识库检索。

### 🟡 可考虑 API 的部分（仅限**不含私有数据**的场景）
原则：**把要交给 API 的内容先"脱敏/匿名化"**——比如用本地模型先把会议记录里的项目名称、人名、脑电指标抽掉，再用外部 API 做纯创意写作润色。能本地做的绝不外传。

值得为特定能力开 API 窗口的情况：
- 需要**极强推理**的复杂任务（本地最强模型也搞不定时），且数据已脱敏；
- **代码补全/生成**如果本地模型不满意，可临时用外部编码模型；
- 视频/公众号的**初稿创意**，脱敏后让强模型发散，再交本地模型落地。

> 我的建议：**第一阶段先完全不碰 API**，把本地链路跑通、建立信任和数据沉淀习惯；等明确遇到"本地做不了"的瓶颈时，再针对性开 API 窗口。这样最安全，也符合你们"数据不上网"的底线。
