## 二、双轨设计（P34 裁「甲乙并用」）

### 轨 A：逐通道自适应阈值在线标记（入 `qc_pipeline.py`）

**新增函数**：`_blink_markers(eeg, sfreq, channels, thresholds=None)` → dict

**输入**：`eeg` (n_samples × n_channels)，`sfreq`，`channels`，可选阈值覆盖  
**输出**：`{"per_channel": {ch: {"epochs": [[start_s, end_s], ...], "count": N}}, "total_blink_epochs": M}`

**算法草案**（三步骤，均基于现有工具链风格）：

1. **带通滤波提取低频成分**（眨眼能量集中在 <4Hz）：用 `scipy.signal.butter` + `filtfilt` 做 0.5–4 Hz 带通，取前额通道（Muse 默认 TP9/TP10/AF7/AF8，但实际通道名从 meta.channels 来；若无明确前额通道，对全通道跑）。
2. **逐通道自适应阈值**：对每通道的滤波后信号，计算绝对值的滑动窗口中位数（窗口＝1s），阈值＝中位数 × k（k 默认 3.0，可调）。超过阈值的连续段记为一个眨眼事件。
3. **合并相邻事件**：间隔 <200ms 的眨眼合并为一个；输出每个事件的起止秒数。

**集成点**：在 `assess()` 内，`_channel_quality` 之后、IAF 之前插入调用：

```python
    # A3：眨眼伪迹标记（只标记，不进 reasons）
    try:
        metrics["blink_markers"] = _blink_markers(eeg, sfreq, channels)
    except Exception:
        metrics["blink_markers"] = {"per_channel": {}, "total_blink_epochs": 0}
```

**关键约束**：
- **不追加 reasons**：即使检测到大量眨眼，也不影响 `recommend`。
- **不写 npz**：标记只存在于内存 dict，由 `write_qc_json` 一并落盘到 qc.json。
- **阈值可调**：通过 `thresholds` 参数传入 `blink_k`／`blink_window_s`／`blink_merge_ms`，默认值写在函数签名里。

### 轨 B：独立成分分析离线复核（独立脚本，不入 qc_pipeline）

**新文件**：`tools/blink_ica_review.py`（或 `05_产品与开发/质检工具集/blink_ica_review.py`）

**功能**：对指定 npz 跑 FastICA，提取与眨眼模板相关性最高的成分，可视化该成分的时域波形与空间拓扑，供人工复核轨 A 的标记是否准确。

**输出**：HTML 报告（含交互式波形图），或 PNG 静态图。

**触发方式**：命令行 `python blink_ica_review.py <npz_path> [--out-dir <dir>]`

**不接入判定链**：纯探索工具，不影响 QC 结论。

## 三、侧线文件格式与落点

### 格式选择：**JSON**（与 qc.json 同构，易读易解析）

**文件名**：`<sid>_blink_markers.json`（例：`ZEN-20260830-P001-S02_blink_markers.json`）

**落点**：与会话定稿同目录（归档位 `02_raw/<sid>/`，隔离位 `03_quality_control/quarantine/<sid>/`，暂存位同理）

**内容结构**：

```json
{
  "session_id": "ZEN-20260830-P001-S02",
  "generated_at": "2026-10-14T08:30:00+08:00",
  "qc_version": "1.1",
  "threshold_version": "20261013",
  "blink_detection": {
    "algorithm": "bandpass_0.5_4Hz_adaptive_median",
    "parameters": {
      "k": 3.0,
      "window_s": 1.0,
      "merge_ms": 200
    },
    "per_channel": {
      "AF7": {
        "epochs": [[12.3, 12.8], [45.1, 45.6], ...],
        "count": 23
      },
      "AF8": {
        "epochs": [[12.4, 12.9], [45.2, 45.7], ...],
        "count": 21
      }
    },
    "total_blink_epochs": 44
  }
}
```

### 备选方案：**嵌入 qc.json**

直接在 `qc.json` 的 `metrics` 里加 `"blink_markers"` 字段（即轨 A 的输出 dict）。优点＝单文件；缺点＝qc.json 体积膨胀、且与"标记是侧线"的语义不符。

**本窗立场**：**两者并存**——轨 A 的结果既写进 qc.json（供快速查阅），也单独写 `<sid>_blink_markers.json`（供离线复核与历史追溯）。理由：qc.json 是判定产物，blink 标记虽不进判定链，但属于质检元数据，理应同在 qc.json 里有一份；侧线文件则是为轨 B 和人工复核准备的完整记录。

**窄口子定义（P27乙）**：仅在 `_process_row` 的幂等键构造处，把"降权版"标识（如 `downweighted=True` 或 `qc_verdict_sha16` 变化但原始 eeg_sha256 不变）纳入去重判断，使得同一份原始数据的降权重算不被当成重复投递。

**具体做法**（设计稿，不落码）：

当前幂等键＝`unit_id`（由 `session_id` ＋ `brain_base_version` 派生）。降权版的重算会改变 `qc_verdict_sha16`，但 `eeg_sha256` 不变。需在 `_commit_row` 或上游判断：若 `eeg_sha256` 相同但 `qc_verdict_sha16` 不同，且差异仅来自"降权"（即 `metrics.downweighted` 存在），则允许覆盖旧行而非报错 duplicate。
