### 闸5｜两页抢槽不张冠李戴——**成立 ✅（含 `elsewhere` 分支已复现）**

**先修正一处我方（W1 记录）对"抢槽"的表述理解**：读码后确认 `_nd_sse_ensure()` **每次请求都把订阅槽切到本请求的地址**（`_ND_SSE.update(target=target, …, state="connecting", frames=0)`）。因此：
- **同址两页** → 复用同槽（共享）；
- **异址两页** → 后请求者**抢占**槽（先请求者下一次取数时再切回自己）；
- `elsewhere` 分支＝「`_nd_sse_ensure` 之后、`_nd_sse_snapshot` 之前」目标被换掉时的**防护分支**，窗口以微秒计。

**实测分三步**：

| 步骤 | 方法 | 结果 |
|---|---|---|
| 1 | 6 轮真并发异址 | `data` 与 `addr` **6/6 全部匹配**（不张冠李戴） |
| 2 | 25 轮 + 双实例 80 次受检并发 | `elsewhere` **0 命中**（窗太窄，概率法撞不上） |
| 3 | **确定性复现**：临时副本把 80ms 延时注入「ensure 之后、snapshot 之前」（**逻辑一字未改**，仅撑窗），跑 6 轮 | **命中 3/6（R2／R4／R6）** |

第 3 步实测输出（R2）：
```
A(60526).state=live       target=127.0.0.1:60526   ← 持有方，正常
B(59999).state=elsewhere  target=127.0.0.1:60526   ← 非持有方如实自报
   err=「推送订阅已被其他页面切到别的地址（本页回落单次拉取）」
```
**判定要点**：`B.sse.target` = **A 的地址（60526）**，即槽指向真正的持有方——**不冒充持有方、不张冠李戴**；B 侧 `data` 由单次 GET 取得（回落路径），未混用 A 的推送帧。

> **结论：闸5 五分之五成立**——`elsewhere` 分支**已确定性复现**（此前"未观察到"系窗口太窄，非分支失效）。

## 五、附：两条链路的区分（应法师"这两个不一样，问题出在哪里"之问）

法师截图显示的是**控制台『真机蓝牙』扫不到 Muse 头环**；而本复核走的是**HTTP 取 NeuraDock 平台**。二者**无任何共用环节**：

| | 法师截图那条 | 本复核这条 |
|---|---|---|
| 数据源选择 | **真机蓝牙（电脑内置适配器）** | **NeuraDock 指标 API（HTTP）** |
| 传输 | **BLE 蓝牙**（`ble_receiver` → `find_muse` → `MuseS.connect_and_initialize`） | **HTTP**（`GET 127.0.0.1:60526/api/v1/metrics`） |
| 依赖 | **Muse 头环开机／有电／在广播** ＋ 电脑蓝牙适配器 | 对方桌面程序在跑、端口已知 |
| 代码路径 | `console_server._worker` → `BleDirectReceiver` | `console_server.ndmetrics_proxy`（本复核全程走此路） |
| 本复核是否触及 | **完全未触及** | 全部 |

### 只读 BLE 扫描实测（`_analysis_tmp/ble_scan_readonly.py`，12 秒）

```
发现 16 个 BLE 设备（XJ02-S×2 等）
Muse 类命中 0
NeuraDock 类命中 0
```
**三条推断**：
1. **电脑蓝牙适配器工作正常** —— 若适配器异常，`BleakScanner` 一个设备都扫不到；实测扫到 16 个。
2. **Muse 头环未在广播**（因此 `find_muse` 无从发现，界面停在"正在扫描 Muse 头环（最长 10 秒）…"）。
   常见成因：头环未开机／电量耗尽／已被其它设备或程序配对占用／距离过远。

> **复现本复核那条链路的准确操作**：数据源可留原样；只需在「旁证源（只读·不入库）」选 `NeuraDock 指标 API（HTTP）`、地址填平台当次 `IP:端口`（本次 `127.0.0.1:60526`，每次重启会变）。

**依据（我方代码＋厂商公开仓库，非推测）**：`neuradock_receiver.py` L8-19 明载协议出自厂商开源仓库
`eeg-workstation-agent/docs/data-protocol.md`；通道序、250 Hz、µV、`start` 命令、42/10 字段、
"TCP 可能把一行拆成多个包"均已定版。厂商 `context/hardware.md` 亦载同一通道表。
**APP 界面第 8 行波形是平的**由此得解：硬件 16 针定义里 **CH8 = "not used"**
（`eeg-workstation-hardware` README 的电极排针表）。

### 8.2 实测：关掉那个 APP 之后（法师第 3、4 问的硬证据）

### 8.3 会不会冲突（法师第 2 问）

三者要分清，**只有第三样冲突**：

1. **9600（主数据源）× 指标 API（旁证源）——彼此不冲突。**
   一个是出站 TCP 到 APP 的套接字，一个是出站 HTTP 到平台；不同进程、不同端口，互不抢。
2. **驾驶舱自己的「真机蓝牙」——这才是冲突源。**
   它去抢蓝牙适配器与头环，而头环那一跳在对方手里。法师第二张截图正卡在这一步：
   数据源＝**真机蓝牙（电脑内置适配器）**、状态＝**"正在扫描 Muse 头环（最长 10 秒）…"**
   ⇒ **我方正在抢**。（且我们的 BLE 路径是 **Muse 专用 GATT**，对 NeuraDock 头环即使扫到也连不上。）
3. **同源共死（隐性）。** 二者共用同一个头环、同一个 exe：APP 一关，两条一起断（见 8.2）。
   另：两者**数值不可能相等**——一个是原始 µV，一个是对方 4 秒窗算出的 0–100 分；
   旁证只能"对方向"，不能"对数字"。

### 8.4 它在本地跑吗？有没有出网？（法师第 3 问）

- **本地**：是。APP 在**本机开一个 TCP 服务器**，我们把数据接走；原始数据不必经过互联网。
- **但绑定的是局域网 IP**：APP 界面自报 `ServerSocket.local IP: 192.168.188.105`、端口 `9600`
  ——**不是 `127.0.0.1`**。即**同一局域网内的机器都可能连上并取走原始脑电**。
  这是一处**暴露面**，本轮只如实登记，**是否收口（改绑回环／防火墙限制）请法师裁**。
- **有无出网**：本轮抓取瞬间，全机**没有任何一条指向非内网地址的 ESTABLISHED 连接**
  （`netstat -ano` 过滤掉 `127.*`／`::1`／`192.168.*` 后为空）⇒ **未观察到上传行为**。
  此为**快照证据**，不等于"永不联网"；要坐实须持续抓包。
- **一处须留意的外发口**：厂商 agent 的 LLM 模式会**把允许清单内的指标摘要**送给语言模型，
  其架构文档明写"**原始脑电与稠密数值数组从不包含在内**"。即：**原始数据不出机，指标摘要可能出机**。

### 8.5 "不开那个 APP 直接接"——可行性核查（法师第 4 问）

**结论：现阶段绕不开；但有一条正当正路。** 依据：

| 证据 | 内容 |
|---|---|
| 厂商 agent 源码 | 数据源只有 `simulator｜replay｜**TCP**`，默认 `127.0.0.1:9600` **——连厂商自己的开源程序都不碰蓝牙** |
| 厂商 Python 教程 | 标题写"Bluetooth real-time streaming"，正文实为 **via TCP (Bluetooth mode)** |
| **录屏软件仓库** | 只放**发行说明与二进制**，明写"**installer／binary 不自动按开源授权**"⇒ **闭源** |
| **硬件仓库** | 公开的只有**电极排针**与 **MCU 调试口**；**不含蓝牙 GATT／服务特征 UUID** |

**三条路线（按代价排序，供法师裁）**：

- **甲·立刻可做（零协议风险）**：让那个 exe **随开机自启＋最小化到托盘**，"每次手动打开"这一步就没了。
  进程仍在，蓝牙仍归它——**这是最省事且不碰红线的做法**。
- **乙·正路（建议）**：向厂商索取**蓝牙 GATT 接口规范**，或**无界面/服务版**。
  厂商 GitHub 维护者 **JunwenLuo（罗工）**；我方档案本就有"**罗工回函**"草稿，此问完全对口。
  硬件仓库自述"为第三方集成提供**接口与端口规范**"⇒ **索取 GATT 属正当请求**。
- **丙·不推荐（须法师裁）**：自行逆向蓝牙协议（嗅探 GATT）。技术上有手段（bleak／BLED112＋只读扫描），
  但**等于自造驱动**，违"不猜厂商协议"，且固件升级即失效。

**另一条捷径——USB 模式**：硬件支持 USB 与蓝牙两路；我们的 `TcpReceiver` 支持 `transport=auto`
（USB 10 字段／蓝牙 42 字段自动识别）。**改用 USB 线连采集模块⇒蓝牙这一位彻底空出**，
但**仍要开那个 exe**（USB 文本流也是它转发到 9600 的）。即 USB 解决"占蓝牙"，不解决"要开 APP"。
