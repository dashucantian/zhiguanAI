## 一、事实（实测，非推定）

| # | 缺陷 | 静态自测 | 真浏览器 |
|---|---|---|---|
| 1 | **优先级 ＋ 和 − 都是 −5**：点 ＋ 数字反降，作业永远无法降权 | **全绿**（自测走 HTTP API 传绝对值，绕过前端算式） | 点 ＋：10→5；再点 −：5→…一路只降 |
| 2 | 非活跃窗口一律标「静默」：MCP 明报 `cold` 也被改口 | 全绿（无此项断言） | 应答里 `cold` 窗口显示为「静默」 |
| 3 | 进程榜榜首 `System Idle Process 3052.6%`（PID 0 记账项） | 全绿（只断言"不给命令行"） | 榜首是噪声，真实负载被挤到第二 |

**根因（#1）**：`if(action==='inc'||action==='dec'){ action='priority'; value=…(action==='inc'?5:-5) }`——**先把 `action` 改掉，再拿它做三元判断**，`==='inc'` 恒假，两个按钮同向。属最朴素的赋值／判读错序，但在静态检查里完全隐形：服务端收到的 `value` 永远是合法整数（1–99），API 层无从判错。

## 二、为何漏过

1. **自测只覆盖到 HTTP 边界**，前端"算出什么值再发"这一段无人验——按钮语义与算式之间没有断言。
2. 三处缺陷都属**语义正确性**（数字对不对、标签照不照实、榜首是不是真负载），不属**结构正确性**（有没有 BOM、有没有外链、有没有泄密），而 93 项自测几乎全是后者。
3. `psutil` 进程迭代默认把 PID 0 一并给出，属平台既知行为，未设防。

## 三、处置

- #1 改为**先定增量再改 action**：`const d=(action==='inc')?5:-5; action='priority'; value=clamp(cur.priority+d)`；真浏览器复测 10→15→10→5→10 双向生效。
- #2 改为照实取 `w['state']`；复测同一答复内 `cold`（MCP 快照）与 `静默`（mtime 推断）并存，来源不再被抹平。
- #3 `PID < 8` 不入榜；复测榜首为真实负载。
- **加永久回归检查**（`selftest.py`【3】）：断言前端块内 `==='inc'` 的**最后一次出现**在 `action='priority'` **之前**；并做**反证测试**——把原缺陷写法喂进同一判据，确认它 FAIL（判位 177／改位 109）。无反证＝检查可能是空转。
- 修完重跑：**93 项、退出码 0**。

## 四、连带自曝：回归检查本身的一处误报

首版检查直接对源码块做字面位置比较，**被代码注释里的字面量绊倒**（新加的注释写了"早先写成 `action='priority'` 在前"，检查把注释当成了代码）→ 自测 92 过 1 失。
处置：比较前 `re.sub(r"//[^\n]*","",blk)` 剥行内注释。
**教训**：对源码做字面断言的检查，必须先剥注释与字符串，否则注释会反过来污染判据；且**新增检查项自身也要跑一次反证**，不然它会以"看起来在把关"的方式长期误报或空转。
