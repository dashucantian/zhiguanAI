# 复现 004：从零把一个飞书自建应用接通一张多维表格的写链路（含验证点与已知失败模式）

> 完成日期：2026-10-14｜来源：W3 协调窗 `542dc2cd` P2 案全链路实跑（维那应用 `cli_a9f5a5f1ece29cef` × 排期表 Base）
> 含摄：坑 049（auto_number）／坑 051（两层权限＋同名应用）→ 判语 019（两层缺一不可＋零变化探针）→ JP-014（判断取舍）。本篇只写**照做步骤**，论证不重抄。
> 目标：一个陌生人照本篇操作，**半小时内**让一个自建应用对一张不属于它的多维表格拿到"读＋写"，且**全程零脏数据**。

## 前置

- 你是该应用的**开发者后台管理员或协作者**（能申请权限、发布版本）。
- 目标 Base 的**所有者**（或有管理权的人）愿意配合点两次页面。
- 应用至少开了**机器人能力**（「添加文档应用」搜索得到它的前提之一）。

## 步骤清单

| # | 动作 | 命令／入口 | 验证点 |
|---|---|---|---|
| 1 | 申请 API scope | 先跑一次写命令被拒，**点错误体里的 `console_url`**（比自己在后台找快）；至少 `base:record:read`＋`base:record:update`＋`base:record:create` | 后台权限列表三行呈"已开通" |
| 2 | 发布应用版本 | 开发者后台 → 版本管理与发布；**可用范围必须包含 Base 所有者**（否则第 5 步搜不到应用） | 版本状态＝已发布 |
| 3 | 等待生效 | 通常分钟级 | — |
| 4 | 读探针（scope 层验证） | `lark-cli base +record-list --base-token <BT> --table-id <TID> --limit 1 --as bot --format json` | `"ok": true`（仍拒且码 `99991xxx`＝scope 没生效，回第 1 步） |
| 5 | 添加文档应用 | Base 页面右上「···」→「···更多」→「**添加文档应用**」→ 搜应用名 | ⚠**同名应用核对 app id**（不要按图标认，实测同名两个） |
| 6 | 授权 | 该应用行右侧下拉选「**可管理**」（高级权限开启时不可低于此档） | 面板显示"可管理" |
| 7 | 写探针（文档层验证，**零变化**） | 取一行现值 → `lark-cli base +record-batch-update --base-token <BT> --table-id <TID> --json @probe.json --as bot`，probe 内容＝**把该格原值写回**：`{"update_records":{"rec_xxx":{"<列名>":"<现值原样>"}}}` | `"ok": true`（仍拒且码 `91403`＝文档层没过，回第 5 步） |
| 8 | 真写入 | 按业务写。⚠`任务编号` 等 `auto_number`／`updated_at` 列**不提交**（写了不报错、值被服务端盖掉，见坑 049） | 写后**逐条按 record_id 回读**核对 |

## 已知失败模式（照做也会撞的，都在这里）

1. `99991672 app_scope_not_applied`＝**scope 层**：没申请／没发布／还没生效。错误体的 `console_url` 直达申请页。
2. `91403`＝**文档层**：应用不在该 Base 协作者名单，或角色低于「可管理」。⚠先跑 `lark-cli drive +member-list --token <BT> --type bitable --as user` 核**appid**——"开过可管理"可能开给了**另一个同名应用**（本案实证）。
3. 「添加文档应用」里搜不到应用＝发布版本**可用范围不含你**（或应用没开任何云文档 API 权限）。
4. 写入 `ok:true` 但值不对＝写进了**服务端持有的列**（auto_number 等，坑 049）——写后必须回读。
5. 探针千万别用"真插一行再删"：删行销号不回收、号永远跳（坑 049 同根），零变化写回才是净验证。
