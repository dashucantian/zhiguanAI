### 步 1｜先读三处，不要先读正本

- **读**：`00_当前状态.md` 顶行 → `AI-开工入口.md` §〇／§一／§二／§二bis → L1 里指向的**现势那一节号**（现＝协调正本 §34）

### 步 2｜跑开工前检查，并确认闸门是活的

- `powershell -NoProfile -ExecutionPolicy Bypass -File 开工前检查.ps1`；收口时同法跑 `收口检查.ps1`
- **验证点**：任一门的输出必须能区分"通过"与"未执行"。**"没输出"≠"通过"**。
- ⚠**已知失败模式（坑 017 原型）**：`收口检查.ps1` 闸 2 曾因 filter 形状写错**连续两日恒报 0 且无人发现**。⇒ 本路径要求：**任何新闸上线前必须先做一次反向验证**（喂一个已知会失败的数据，看它响不响）。今日闸8／闸9 即照此做：闸8 喂不存在的节名须返回 `−1` 而非 `0`；闸9 喂 `vr_mandala.html` HEAD 侧第 42 行（已知空白）须报 `blank? True`。
- ⚠**第二个失败模式（`KZ-1007-W3e`）**：PowerShell 按 GBK 解 git 的 UTF-8 输出会**吞掉换行**，使 `(?m)^Model:` 这类判定假性失败。**判"缺"之前必须直读原始字节复算**（`cmd /c "git cat-file … > 临时文件"` 再按 `0x0A` 切行）；**取证要在 PS 那侧跑**——用 Python 模拟 .NET 会把结论订反（坑 016 同族）。

### 步 4｜落共享文之前重跑判据（不是开工时查一次就完）

- 判据〔2026-10-10 法师裁「一条规则死锁。同意你的建议」，落规约 §二bis 硬规则 7〕：**不数 `running` 个数，改判「目标文件是否落在任一在场 `running` 窗口的写入面内」**。写入面＝该窗本轮派工函／己档／在途 `git status` 所列文件与目录。

### 步 6｜提交：逐批候放行，件数实取

## English Summary

**Goal:** a stranger window (or a fresh session) completes the collaboration mechanics safely within two hours — writes to shared files, takes numbers, commits, closes — without repeating the errors already recorded in this library.

**Why it did not exist:** both prior reproduction paths covered devices and signal chains. The collaboration mechanism never had a "run it and it works" path; it lived on oral transmission and on reading long documents. **That absence is the common upstream of every pit recorded today: rules written in the middle of a 2,000-line ledger are not on the read path, and a rule that is not on the read path has no force.**

**Structure (per the master's 2026-10-10 ruling that the four genres are nested — pit → ruling → precedent → reproduction, with reproduction containing the other three, so nothing is re-described):** this path restates no argument; it converts each recorded failure into one executable step plus one verification point. Pit cards become the ⚠ notes, ruling cards become the criterion used in step 4, precedent cards become the *reason* the "recompute, don't transcribe" requirement exists.

**Four verification points:** the index generator runs and section E reports a nonzero count; the closing gate runs with the L1 length gate passing; the newcomer can state the signature format, the numbering lookup, and who releases commits **without opening the ledger**; and both staged-file counts (before and after `git add`) are measured, not counted by hand.

**Self-proof that this path itself has not rotted:** `生成登记索引.py` gained a **section F**, which enumerates every "awaiting ruling / awaiting a separate word" marker in the ledger and shards, sorted by days since the file was first committed. Real output on 2026-10-10: **169 hits, 75 older than three days, oldest 16 days.** This number is *not* presented as "169 pending decisions" — that would merely become new noise. What it proves is that many items were written down as "pending" and never raised again; what it cannot prove is how many are genuinely open versus closed-but-never-struck, **and that ambiguity is the point: without a strike-through action, even "how many are actually pending" is unanswerable.** One spot check: `KZ-0925-W1b` proposed three rules on 09-25, including "a naming ruling must ship with its landing point verified"; none are in the entry spec today, while a sibling rule was landed 10-09. **So the same shape was raised eleven days ago and stepped on again today — the evidence that recurrence is not about noticing, it is about nothing forcing the item to be seen again.**

**Honest limit:** §六 (the strike-through step) has no enforcement point — it is itself an unenforced "pending" item. Pinning it requires either making section F a commit gate (the master ruled on 2026-10-09 not to add gates to `收口检查.ps1`; that ruling was not overridden, so this window did not do it) or restoring the C3 patrol (cron currently paused). Both await one word.
