## 判决

**硬规则 7「共享文单写方」保留，但判据换变量**：不再以「本仓 `running` 会话数＝1」为唯一前置，改判**「目标文件是否落在任一在场 `running` 窗口的写入面内」**——不在其写入面即照写，且须在本窗己档同条明记「用例外口＋目标文件＋为何不在他窗写入面」；在其写入面内的一律**扣住不写**，候复测＝1。**写入面＝该窗本轮派工函／己档／在途 `git status` 所列文件与目录。**

四项**未放松**：① fork／侧栏任务仍一律只读取证；② 未裁事项仍不得预落；③ §三 并发四纪律照旧；④ §三.5 提交前逐行读 diff 照旧。

## 依据（可核验的事实）

- **死锁实证（本轮，2026-10-10）**：协调窗向四窗发完放行与排序通知后，`list_chat_sessions` 本仓 `running` ＝ **3** ⇒ 协调正本 §31、6 件已裁定文书、以及三个窗口的己档／登记分片**全部落不了笔**。链条是：`要记录"我刚派了什么" → 须先派工 → 派工使 running>1 → 判据禁止落笔`。
- **协调窗的本位就是派工**（法师 10-08 定长期口径：跨窗派工／边界／归属／回执全走 W3）⇒ 死锁不是偶发，是**结构性必然**：规则要它做的事，恰好触发规则自己的禁止条件。
- **根因＝判据选错了变量**：`running` 计数测的是「几扇窗在干活」，而规则要防的是「两个进程写同一个文件」。二者**只在单窗特例下重合**。四窗并行时，前者恒 >1 而后者未必成立。
- 落点：`AI-开工入口.md` 硬规则 7 下两条子项（例外口＋根因）；详见协调正本 §31.1；坑卡 **021**。

## 被否方案

- **甲｜维持裸计数判据**：规则自锁，且锁住的正是"记录裁定"这件事——最该留痕的动作最先被禁止。否。
- **乙｜废掉硬规则 7**：会退回 2026-10-09 坑 019 那个状态（分身顶着同一 sessionId 实时改写主窗己档，归属与状态不再可推定）。否。
- **丙｜给协调窗开永久豁免**：豁免无边即等于规则对该窗不存在，而他窗仍受限——同一条规则两种语义，比死锁更坏。否。
- **丁｜改用"文件锁"机制**：需改共用脚本与客户端能力，超出本轮授权面（法师 10-08 裁共用 `.ps1`「不准修」，10-10 只放开空行探针一项）。候另议。

## 可复用教训

**判据选的变量必须与规则要防的事同源。** 用"活动量"当"冲突量"的代理，在有协调角色的体系里必然自锁——因为协调的定义就是制造活动量。发现规则自锁时，正解不是加豁免、也不是废规则，而是**回到"这条规则到底在防什么"，重选那个变量**。

## English Summary

**Decision:** Hard Rule 7 ("single writer per shared document") stays, but its criterion changes variable: instead of requiring the repo's `running` session count to equal 1, it now asks **whether the target file falls inside any present `running` window's write-surface**. Outside it → write freely (and record in your own window log which exception you used and why); inside it → hold until the count drops to 1. Write-surface = the files/dirs listed in that window's dispatch letter, its own log, and its in-flight `git status`. Four things were *not* relaxed: fork/side tasks stay read-only, unruled items still can't be pre-landed, the four concurrency disciplines, and line-by-line diff review before commit.

**Evidence:** On 2026-10-10, after the coordination window sent release-and-ordering notices to four windows, `running` = 3 — so the coordination ledger §31, six already-ruled documents, and three windows' own logs were all blocked. The chain: *to record "what I just dispatched" → must dispatch first → dispatch raises running >1 → criterion forbids writing*. The coordination window's standing role **is** dispatching, so the deadlock is structural, not incidental. Root cause: the criterion measured the wrong variable — `running` counts "how many windows are working," the rule wants to prevent "two processes writing one file." These coincide only in the single-window special case.

**Rejected alternatives:** keep the bare count (self-locking); delete Rule 7 (returns to pit 019's unattributable state); grant the coordinator a permanent exemption (one rule, two semantics — worse than the deadlock); implement file locks (needs shared-script changes outside this round's authorization).

**Reusable lesson:** A criterion's variable must be same-origin as what the rule is trying to prevent. Using "activity level" as a proxy for "conflict level" inevitably self-locks in any system with a coordinator role, because coordinating *is* generating activity. When a rule locks itself, the fix is neither an exemption nor repeal — go back to "what is this rule actually preventing" and pick a different variable.
