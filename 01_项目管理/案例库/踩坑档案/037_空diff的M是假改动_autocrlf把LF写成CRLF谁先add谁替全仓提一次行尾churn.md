> ｜危害等级：**中高**——它自己不破坏内容，但它让"看起来需要提交"这件事变成假的，而四窗共用一个 index，**谁先 `add` 谁就把一次无意义的大 diff 钉进历史**。

## 现象

`案例库/曼荼罗场域/Case-M01、M02` 在库内一直是好的，只是被人从工作区挪走（git 报 `D`）。本窗执行「搬回原处」：

```
git restore --source=HEAD -- 案例库/…        # 复原
git status --porcelain                        # → M（不再是 D，看起来"有改动"）
git diff --numstat -- 案例库                  # → 空（没有任何内容差）
```

⚠**M 与"空 diff"同时成立**＝矛盾。二进制实测才看清：

```
库内 blob：CR 数 0，10,604 B（纯 LF）
restore 后工作区：CR 数 117，10,721 B（全被写成 CRLF）
本机 git 配置：core.autocrlf = true
```

⇒ `git checkout/restore` 在 Windows 侧按 autocrlf 把 LF 展开成 CRLF，`git status` 靠 stat（体积／mtime）判脏，而 `git diff` 走归一化比对，所以**内容确实没变、状态却是脏的**。

## 根因（两层，第二层更要命）

1. **`M` 是"stat 脏"不是"内容脏"**。四窗共用一个 index，别的窗看不出这个区别：只要它跑一次 `git add 案例库/…` 或 `git add .`，就会把**一次纯行尾改写**（本例 117 行／110 行）当成"改动"提掉，历史里从此多出一条谁也解释不清的 churn，而且**下一次 checkout 又会长回来**——变成反复出现的假差异。
2. ⚠**测量工具本身也在造假**：本窗先用 `git show HEAD:… | od -c` 数出"HEAD 里有 31 个 CR"，据此写成"库内是混合行尾"——**那是 bash 管道文本模式换行转换造出来的**。真值＝**库内 0 个 CR**（Python 直读字节 `count(b"\r")` 复算）。⇒ 与今早 `curl | python` 那条"看板 JSON 坏了"的假警报**完全同族**：**管道不是无辜的。**

## 对策（四条，可逐条核查）

1. **见到"脏状态＋空 diff"先判为假改动**，处置＝**用二进制直写复原**（`python` 里 `git show HEAD:<path>` 取 bytes 直接写文件），**不要再走 `checkout/restore`**；复原后逐字节复算 sha256 与 CR 数双证。
2. **提交前三件套**（共享工作树专用，本窗已并入 §三 并发纪律候裁）：`git diff --cached --numstat` 看行数 → 再跑 `git diff` 看**是不是空** → 空 diff 的 M 一律先复原、**绝不带脏提交**。
3. **测行尾／字节数一律直读二进制**（`open(path,'rb').read().count(b'\r')`），**禁用 `… | od`、`… | wc`、`curl | python` 这类文本管道**测二进制属性；要用管道就先落盘再读。
4. ⚠**反例（何时 M 是真改动）**：同一条 `git diff` **非空**、且 `--numstat` 有行数＝真改动，按纪律照常提交；别把本卡当"看到 M 就忽略"的许可证——**判据是 diff 空不空，不是 status 显不显**。
