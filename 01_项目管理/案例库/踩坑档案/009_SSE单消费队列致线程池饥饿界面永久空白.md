# 坑 009：SSE 单消费队列致线程池饥饿，「状态正常但波形永久空白」

## 现象（用户视角）

2026-09-13 法师启动**纯监测采集**（真机蓝牙 Muse），界面永久停在「正在连接数据源…」，
脑波图、频段、PSD 全部空白：

- 前端提示不变、波形不动，**看起来像没连上**
- 但 `/api/monitor/status` 正常返回 `{"status":"recording","running":true}`
- 后端 worker 线程正常推 tick，**数据正常累积并成功落盘**（12.8 分钟完整）

即"后端在采集、界面不更新"的分裂状态。法师第一反应怀疑是 09-08 采集台合并
（纯监测＋闭环反馈并入同一界面）所致。

## 根因

**git 考古否定了"合并所致"的猜测**：单消费 SSE 设计自最初发布（`89996d4`）即存在，
合并大改（`10f7f65`）只改前端入口与仪表卡，未动推流架构。真实根因是三个缺陷叠加：

**① 线程池饥饿（主因）**

SSE 生成器用阻塞方式取事件：

```python
ev = await loop.run_in_executor(None, lambda: MONITOR.events.get(timeout=1.0))
```

每个连接长期占用一个**默认线程池线程**（上限 `min(32, cpu+4)`）。而浏览器
`EventSource` 断线会自动重连，旧生成器若未及时退出就持续堆积 → 线程池被占满 →
新连接的生成器**拿不到线程、永远 yield 不出首条数据** → EventSource 一直处于
pending 状态：既不触发 `onerror`、也收不到任何消息。

而 `/api/monitor/status` 是普通 async 接口、**不依赖那个线程池**，所以照常返回
`recording`。这正解释了"后端一切正常、前端永久空白"的诡异组合。

**② 单消费队列**：`MONITOR.events` 是一个 `queue.Queue`，多个 SSE 连接**互相抢事件**，
任一连接的消费都会让其它连接收不到 tick。多开标签页必现。

**③ 队列无界**：无人消费时无限积压（每帧 `wave` 含 4×1280 点），13 分钟即显著占内存。

**④ 前端把错误吞掉了**：`monEs.onerror = () => {}`，且全文件**零重连逻辑**
（`connectMonitorStream` 只在页面加载与点开始时各调一次）→ 一旦断流即永久静默黑屏。

## 确诊方法（可复用）

关键手段：**以第二观察客户端接入推流，看事件到底有没有产出**。

```
python output\20260910_VR标准模板三重分析\probe_stream.py
```

实测结果（10 秒）：`tick=55`、packets 137→2986、四通道波形齐备，
**且队列里还积压着 18:52:33 开始采集那一刻的消息**（"正在扫描 Muse 头环"等 4 条）。

这条积压证据是决定性的：它说明**整整 13 分钟前端零消费** —— 问题不在采集层、
不在 worker，而在推流通道与前端接收层。

⚠️ 探针成本须知：改造前 `events` 是单消费队列，探针接入会**抢走前端的事件**
（本例中前端本就没在消费，代价为零）；且探针只影响显示，**数据在 buf 内累积，
保存不受影响**。改造后为广播语义，多客户端可并存、不再互抢。

## 解法

**后端：单消费队列 → 广播注册表（`EventBroadcaster`）**

- `asyncio.Queue` 按订阅者独立分配 → **非阻塞、不占线程池**，饥饿根因消除
- `publish` 用 `loop.call_soon_threadsafe` 跨线程投递（worker 线程 → 事件循环）
- 队列**有界**（maxlen=200），慢消费者丢最旧一帧（推流是实时显示非可靠传输，
  保实时性优先）
- 断开时 `finally` 必摘除订阅 → 杜绝生成器泄漏
- `start()` 调 `reset()` 清空上次会话积压，防旧事件污染本次连接
- `events` 保留为**只读兼容属性**指向 legacy 队列：`neuradock_console_selftest`
  直接消费 `MONITOR.events`，此举避免破坏其接口（红线5 不建平行路径）

**同构修复 `ExperimentSession`**：闭环实验路径是**同一缺陷**，不修必同样复发。
其 worker 有 4 处 `self.events.put(...)` 须同步改 `broadcaster.publish(...)` ——
若只把 `events` 变属性指向 legacy 队列而不改这些 put，事件会只进 legacy、
进不了订阅者，**反而弄坏实验流**。

**前端：推流看门狗（纵深防御第二道）**

- 记录 `monLastEventAt`，由既有 `pollStatus`（3 秒轮询）检测
  「后端 `running` 但超 `MON_STALL_MS`(6秒) 无任何事件」→ 主动重连
  （复用既有轮询，**不新建定时器**，避免多套轮询互相干扰）
- `onerror` 不再吞错误，如实记录 `monEsState`
- `onopen` 刷新活性时间戳 —— 否则看门狗会拿"断流前"的旧时刻，在首帧到达前
  就误判断流并反复重连（**自我干扰**）
- 状态栏如实标注「⚠推流 Ns 未更新」；重连 ≥5 次提示「数据仍在后台累积，
  可稍后停止并保存取回」

## 排障顺序（可复用）

界面空白但后端状态正常时，按这个顺序查：

1. **先分清是哪一层空白**：查 `/api/monitor/status`。返回 `recording` 说明
   采集层没问题，故障在推流层或前端层
2. **以第二客户端接入推流**（`probe_stream.py`）：
   - 收到 tick → worker 活着，问题在前端接收/渲染
   - 零 tick 但有 ping → worker 线程已死或卡死
   - 完全无输出 → SSE 生成器起不来（**线程池饥饿的典型症状**）
3. **看队列是否积压旧事件**：积压着"开始采集那一刻"的消息 = 前端从未消费过
4. **查服务进程线程数**是否随重连轮次单调增长 → 生成器泄漏／线程池饥饿
5. 最后才怀疑前端渲染逻辑

⚠️ 反面教训：**别只看 status 接口正常就判"后端没问题"**。status 是普通 async 接口，
与推流走的是不同资源路径，二者可以一个正常一个瘫痪。

## 教训

**① "编译通过 / 静态校验通过"与"运行时正确"是两回事。** 本次故障代码全部编译通过、
`validate_console.py` 也全绿，缺陷纯在运行时资源模型（线程池）。09-11 我做 e2e 时
用模拟源跑通即判"无回归"，**未覆盖「前端 SSE 断流」这一真实故障面**，
这是本故障未被提前发现的直接原因。验证要覆盖"资源耗尽／连接异常"这类
只在特定运行条件下才暴露的形态。

**② 用户的归因猜测要先验证再采信。** 法师怀疑"合并大改所致"，听起来很合理
（时间上也吻合：合并后才高频使用统一界面），但 git 考古证明该设计从最初就在。
若顺着猜测去查合并 diff，会白费功夫并可能改错地方。**先拿证据定位层级，再谈归因。**

**③ 前端吞错误＝把可诊断的故障变成不可诊断的故障。** `onerror = () => {}` 一行，
让"连接 pending"与"一切正常"在界面上完全无法区分，法师只能看到永久空白、
我也只能靠外部探针反推。凡是长连接，界面必须能如实反映连接活性。

**④ 同构缺陷要一起修。** 闭环实验路径是同一套写法，只修监测路径等于留一颗
定时炸弹；且改动会连带影响它（`events` 变属性后，直接 put 的代码会绕过广播）。
修一处推流缺陷时，必须 grep 全部 `.events` 使用点。

**⑤ 本档案与坑 003 的对照**：两者表面都是"数据断流、界面静默"，但 003 在
**硬件/蓝牙层**（数据源真的断了，worker 检测静默并重连），009 在**推流架构层**
（数据源好好的，事件送不到前端）。**排障时先确认数据是否真在产生**，
再决定往硬件层还是通道层查 —— 否则会拿蓝牙的解法去治推流的病。

## English Summary

**Symptom:** In pure-monitoring mode the UI stays forever on "connecting to data source…"
with all waveforms blank, while `/api/monitor/status` correctly reports
`recording/running:true` and the backend keeps accumulating and saving data
(12.8 min session saved intact). A split state: backend recording, UI dead.

**Root cause:** Three stacked defects in the SSE push layer (git archaeology ruled out
the suspected 09-08 console-merge — this design existed since the first release):

1. **Thread-pool starvation (primary).** The SSE generator fetched events via
   `loop.run_in_executor(None, lambda: q.get(timeout=1.0))`, so every connection pinned
   one default-pool thread (cap `min(32, cpu+4)`). `EventSource` auto-reconnects kept
   piling up un-exited generators until the pool was exhausted; new connections then
   never got a thread and never yielded a first byte, leaving EventSource permanently
   *pending* — no `onerror`, no data. Meanwhile `/api/monitor/status` is a plain async
   route that does not touch that pool, so it kept returning `recording`.
2. **Single-consumer queue:** several SSE connections stole events from each other.
3. **Unbounded queue:** with nobody consuming, frames (4×1280 points each) piled up.
4. **Frontend swallowed errors:** `monEs.onerror = () => {}` plus zero reconnect logic
   turned any stall into a permanent silent black screen.

**Diagnosis method (reusable):** attach a *second* observer client to the stream.
It received 55 ticks in 10 s while the queue still held messages emitted at session
start — proving the frontend had consumed nothing for 13 minutes, i.e. the fault was
in the push/receive layer, not acquisition.

**Fix:** replaced the single-consumer queue with `EventBroadcaster` (per-subscriber
non-blocking `asyncio.Queue`, cross-thread `call_soon_threadsafe` publish, bounded with
oldest-frame drop, `finally` unsubscribe, `reset()` on session start), applied
**isomorphically to `ExperimentSession`** (same defect; its 4 `events.put` calls had to
become `publish`, otherwise events would bypass the broadcast and break that path), and
kept `events` as a read-only compatibility property for existing self-tests. Frontend:
a stall watchdog inside the existing 3 s `pollStatus` (backend running but no event for
6 s → reconnect), honest `onerror` state, `onopen` liveness refresh (else the watchdog
self-triggers before the first frame), and a visible "⚠ stream stale Ns" indicator.

**Evidence:** 6 concurrent connections each got 22–23 ticks (spread 1); after 70 total
open/close cycles a new connection still got 23; server thread count 53 → 53 (**zero
growth**). Watchdog test (real browser via CDP, `monEs.close()` while backend kept
running): UI showed "stream stale" at t+4.5 s, reconnected at t+7.5 s, resumed ticks
within 0.2 s, no JS exceptions.

**Lessons:** (1) Compiles + static checks passing ≠ runtime-correct — this defect lived
purely in the runtime resource model, and my earlier e2e used a simulated source and
never covered the "frontend SSE stall" failure surface. (2) Verify a user's causal
guess before adopting it; the merge suspicion was plausible but disproved by git history.
(3) Swallowing frontend errors converts a diagnosable fault into an undiagnosable one.
(4) Fix isomorphic defects together. (5) Contrast with pitfall 003: both look like
"silent data stall", but 003 is hardware/BLE (source truly dead) while 009 is push
architecture (source fine, delivery broken) — confirm data is actually being produced
before choosing which layer to debug.
