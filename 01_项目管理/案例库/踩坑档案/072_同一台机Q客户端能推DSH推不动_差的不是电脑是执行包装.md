# 坑 072：同一台机、同一个 git，Q 客户端能推、DSH 推不动——差的不是电脑，是执行包装

> 〔取号留证〕2026-10-23 14:1x 本机 `Get-Date` 实取；`0*.md` 现势末号＝**071**，`072` 前缀零命中 ⇒ 顺延取 072。
> 发现窗：DSH 承接窗 `fc2ce735`｜触发：法师问「千问和 Q 客户端推送都没这问题，为什么 DSH 有？是电脑的问题吗？」

## 现象

同一台机、同一系统、同一把 ssh 钥匙、同一个仓库：
- **Qoder／千问客户端里** `git push` 正常；
- **DSH 窗内**：`sh.exe: *** fatal error - couldn't create signal pipe, Win32 error 5` ⇒ `fatal: Could not read from remote repository` ⇒ 退码 **128**；
- 但**同一份提交**由 DSH 之外的**计划任务**推送，一次成功（2026-10-23 14:07 那轮 `S5 推：推完 2 笔，余 0`）。

## 根因

不是电脑、不是网络、不是仓库权限，而是**谁把 git 拉起来**：

1. 客户端直跑 git —— git 是普通子进程，`sh.exe` 可以正常建管道；
2. DSH 每次工具调用都套一层**沙箱执行边界**（confined mode），该边界**禁止程序创建命名管道**；
3. git 走 ssh 传输时必须拉起 `sh.exe`，而 MSYS2 的 `sh` 启动即需 signal pipe ⇒ 被拒（Win32 error 5＝拒绝访问）⇒ ssh 起不来 ⇒ 传输失败。

旁证：`status`／`log`／`commit --no-verify` 在沙箱内都能跑（不起 sh）；一旦涉及 **hook 或 ssh 传输**就必失败——这条边界早已在 10-11 的 sh 钩子零执行上显过一次形。

## 处置

- **甲**：把文件政策放开到 `danger-full-access`（法师 10-23 择甲）；
- **乙**：把**推送**交给沙箱外的计划任务（`DSH_Run_2h` 的 S5），本地提交留存、每两小时自动补推——**已在跑并验证成功**；
- 换 HTTPS **不解决**：Git for Windows 仍 spawn `git-remote-https` 子进程，同样要管道。

## 教训（可复用）

1. **"某客户端能做、这个客户端不能做"时，先比执行包装，不要先怀疑机器。** 同一台机、同一条命令，成败常常只差"外层有没有沙箱"。
2. 沙箱锁的是**管道、句柄、网络出口**这类原语；凡是需要"起子进程并接标准流"的工具（sh、ssh、npm、node 管道），一律先假定会被拦，并预备**沙箱外通道**（计划任务／独立进程）。
3. 失败分级要写对：推送失败不是"提交坏了"，是**通道不通**；本地提交必须保留，恢复通道后补推即可——本轮执行器已按此改为软失败。
