# 坑018：Git运行时异常与index锁残留——先核持有者，不自动清锁

2026-10-04｜W1事件报告：AI-015，W1-GLM53FLASH-20261004-A；W3整理：AI-014，W3-DESKTOPOR-20261004-A。取号前实际枚举档案目录，末号017，本件取018。内部存档，非新规约；收录依据为W1正式请求载明法师“赞同”，不扩成自动清锁授权。

## 现象与证据等级

W1报告DSH桌面端内置Git/sh运行时多次出现 `fatal error - couldn't create signal pipe, Win32 error 5`；写操作中断后见 `.git/index.lock`，后续操作失败，报错有时被截断；称本轮两次确认无git进程后移除锁并恢复。这是当事窗口自述，本卡未取得两次完整日志、进程/锁时间线，未独立复现崩溃。

W3此前实际观察过0字节index.lock及清理权限不足；后来只读Git可继续、锁消失。2026-10-04本轮现查HEAD为cf11351，index/HEAD/next-index三锁均不存在，共享index仍有他窗文件重命名暂存。不同环境与时点，不能据W3现查证明W1崩溃根因，也不能称一切Git操作在所有环境均被残留锁阻断。Git只读命令有些仍可运行，默认status可能尝试刷新index；诊断可采用GIT_OPTIONAL_LOCKS=0减少可选写锁，失败仍须报告，非万能修复。

## 根因边界

信号管道创建失败说明该运行时当次出现拒绝访问类错误；“崩溃导致写中断并留下锁”是与报告相容的解释，不独立证明最初拒绝访问由何而来。进程权限、安全软件、句柄/资源、运行时实现等需宿主证据，不能以长会话次数直接断言上下文耗尽或模型腐化导致系统崩溃。

锁文件存在只证明有锁路径，不证明仍有持有者或已经无人持有。0字节、旧时间戳、工具环境未见git进程都不足以单独授权删除。DSH或Claude工具环境可见的进程并不必然覆盖全部Windows宿主与其他客户端；仅Get-Process git也可能漏git.exe以外的相关进程、子进程或刚启动的并发写入。

## 排障与恢复边界

先保留原stderr、退出码、命令与时刻，停止重复写操作；核实际git-dir/common-dir/worktree，避免检查了另一仓库。现查锁、共享index与在途窗口，区分运行时错误、活动锁、孤儿锁与权限不足。宿主侧确认所有相关写入已停止且原持有窗口结束后，由获本次明确权限者备份具体锁路径并按批准操作，随后只读复查HEAD、index与工作区归因。清锁不等于回滚半完成提交，需核提交对象和暂存状态；不reset、restore或撤掉他窗暂存来“变干净”。

W1所报移除锁恢复保留为两次事件处置记录，不把Remove-Item命令变成通用可自动执行动作。权限拒绝不能靠反复重试或提升权限绕过；先报告访问范围与所需批准。若本窗口工具删除被拦，应走工具规定的授权流程，但仍须先满足宿主无活动写入的证据条件。

## 预防提案，不自行生效

检查脚本增加锁存在提示可以作为候审提案：检测只读、提示持有者未知、不自动删、不将“无进程”当充分依据；配已知有锁/无锁及权限不足反例证明提示确实会响。本轮未改收口检查.ps1、规约、cron或自动化权限。避免把“发现故障”直接变成新运行规则。

## 可复用教训

运行时异常、锁残留、活动写入与授权是四个不同问题。先让故障与证据边界可见，再恢复；恢复命令有效过，不代表以后可以自动执行。
