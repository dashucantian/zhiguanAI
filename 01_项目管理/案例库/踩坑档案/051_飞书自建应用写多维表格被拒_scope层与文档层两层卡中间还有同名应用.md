# 坑 051：飞书自建应用写多维表格被拒——scope 层与文档层两层卡，中间还夹着一个同名应用

> 取号留证（2026-10-14，W3 协调窗 `542dc2cd`）：入档前 `ls 踩坑档案/` 实取末号 **050** ⇒ 按规约 §二.5「编号先查后取」取 **051**。证据链＝证据台账 EV-0005／EV-0006／EV-0007（log_id 三枚在册）。

## 现象（时间线，用户视角）

- 10-13 晚，法师：「开了可管理 权限。」→ 次日应用身份写多维表格**仍被拒**，返回码 `99991672 app_scope_not_applied`。
- 10-14 早法师令「P2 你再最后试一遍」：读探针回 99991672、零变化写探针也回 99991672——**错误体里自带一个 `console_url`（开发者后台 scope 申请页链接）**，此前多轮猜测都没打开过它。
- 法师照链接申请完 scope（「P2 好了」）：读**通**了，写却换了新码 **`91403` "you don't have permission"**——码变了，卡点换了层。
- 用 `drive +member-list` 现查这张 Base 的协作者名单：3 名＝法师本人（full_access）、应用 `cli_aa38ac3781b85bd9`（full_access）、一位只读用户——**维那（`cli_a9f5a5f1ece29cef`）根本不在名单里**。而法师「可管理早就开了」是真的：**开给了名单上那个应用**。
- 法师打开「添加文档应用」面板，截图显示**两个同名的「止观AI-维那」**（蓝图标＝大机大用／紫图标＝来自飞书多维表格），都授了可管理 → 重跑零变化写探针，`ok:true`，全链路收口。

## 根因（三个坑叠着，容易混为一谈）

1. **坑 A（权限是两层不是一层）**：`base:record:*` 有两道互不替代的闸——①**scope 层**（开发者后台申请 API 权限，缺了回 `99991672`）＋②**文档层**（这张表本身要把应用加为协作者；高级权限开着时须给**可管理**，缺了回 `91403`）。在后台勾完权限≠这张表放行。
2. **坑 B（同名≠同应用）**：「止观AI-维那」有两个（app id 各异）。法师「开了可管理」开的是**另一个**应用（`cli_aa38ac…`），本方据"开了"推定"开给了它"＝**拿人话的省略当系统事实**。appid 级核对（member-list 的 `member_id`）是唯一可靠判据。
3. **坑 C（错误码没被当索引用）**：91403 一案（见判语 017 关联与规约 §二.17）已证明官方码表一行顶三次试错；本案 99991672 的错误体更进一步——**直接把申请页链接递到你手上**，而前期仍走了三轮猜测才去查。

## 解法

1. 开发者后台给应用申请 `base:record:read/create/update`（最短路径＝点错误体里的 `console_url`，同页顺手勾齐 create）。
2. 文档侧：打开多维表格 → 右上「···」→「···更多」→「**添加文档应用**」→ 搜索应用（⚠同名应用**核对 app id**，别按图标认）→ 授**可管理**。
3. 验证：先 `+record-list --as bot --limit 1`（读通＝scope 层过），再做**零变化写探针**（见下），`ok:true` 才算通。

## 排障顺序（可复用）

**先读码分层**（`99991xxx`＝scope/应用层、`91403`＝文档层）→ **错误体自带链接先点**（别自己搜）→ `drive +member-list` 现查协作者名单、对 appid → 「添加文档应用」授可管理 → **零变化探针**收口（写回原值，`ok:true` 即证写通又不造脏数据）。**不要一上来就改代码、更不要换姿势重试**——两层权限怎么猜都猜不出来，每一层都有官方判据。

## 教训

**报错码就是官方给的索引；"开过权限"必须核到 appid 那一位——同名不算同应用，"开过了"不等于"开给了它"。**

- 同族：坑 049（写通之后的下一坑：`auto_number` 列写值被服务端盖掉，接口照样 `ok`）——本案收口不等于链路健康，逐列回读是写后的另一道闸。
