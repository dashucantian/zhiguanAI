# 坑 003：蓝牙数据流静默断连，闭环实验零决策即失败

## 现象（用户视角）

法师启动闭环实验，实验很快结束但没有产出数据。后台记录：

```
模式：真机（BLED112 自动）
tag：closedloop
n_decisions：0
error：数据流静默 18 秒（疑似蓝牙断开）
data_path：null
```

实验"跑起来了"，却一个决策周期都没完成，等于空转失败。

## 根因

Windows 蓝牙栈在长时间流式传输下出现**环境性静默断连**——连接看起来还在，但数据流停了。系统的看门狗检测到 18 秒无新数据后，判定数据源失效并中止实验。

这不是孤例：2026-09-01 下午就发生过一次系统蓝牙栈环境性故障导致连接失败，当时定性为"环境性故障"，恢复步骤记在进程看板阶段 5c。蓝牙在 Windows 上的稳定性是本项目反复出现的卡点。

## 解法

短期（恢复当次实验）：
1. 头环断电重连：关电源、重新开机、指示灯亮后再启动实验
2. 确认头环未被其他设备（手机 Muse App 等）占用蓝牙配对
3. 必要时重启本机蓝牙服务或重插 BLED112 适配器

长期（架构层面）：
- 闭环实验已有看门狗：静默超时即中止并记录错误，不会无限空转
- **V1.3（2026-09-06）静默断连自动重连**：看门狗判定静默后不再直接终止，
  而是委托 `_request_reconnect` 自动重建连接会话（最多 3 次、间隔 5 秒，
  数据恢复即重置预算）；预算用尽才走原"自动保存+告警"路径。重连期间
  不保存、不中止会话，已采数据不受影响。内置蓝牙与 BLED112 两条路径
  均接入（扫描失败/连接失败/流中断同样委托重连）。
- **V1.3 BLED112 写语义修复**：`_BgapiClientAdapter.write_gatt_char` 原把
  response 语义反转（默认等待写响应），而 Muse 控制特征不支持写响应，
  导致握手首条指令超时、"连上但零数据流"。现统一用无应答写命令。
- **V1.3 串口释放**：BLED112 会话退出时 `backend.stop()` 释放串口，
  避免重连或下次启动时适配器被占用。
- 真机长时程稳定性排查已列为阶段 B 任务（看板 ZG-014），目标是"连续 30 分钟无静默断连"
- 数据出口已支持模拟源回放：用已入库的真机数据（如 ZEN-20260906-P001-S12）做离线回放测试，使映射参数迭代不再依赖蓝牙实时连接

## 排障顺序（可复用）

实验"跑了但没数据 / n_decisions=0"，按这个顺序查：

1. 先看错误信息里的**静默时长**——有"数据流静默 N 秒"字样，基本就是蓝牙断连，不是算法问题
2. 查头环是否被其他设备占用配对
3. 查 BLED112 适配器 / 蓝牙驱动状态
4. 最后才怀疑信号处理或闭环逻辑（在数据流本身断了的情况下，下游逻辑没机会运行）

## 教训

**画面再美，数据断流即失效。** 视觉闭环的前置条件是数据链路的长时程稳定，而不是渲染效果。蓝牙在 Windows 上的稳定性是必须正视的工程风险，不能假设"连上了就一直连着"。这也是为什么 B3 离线回放测试有价值——它把"映射逻辑调试"和"蓝牙稳定性"两个问题解耦，不必每次都赌蓝牙不断。
