# 坑 066：取数工具自己没验过——`Get-Content` 按 GBK 解码把 74 行算成 45，钩子的 `timeout` 在 Windows 撞 TIMEOUT.EXE 让自检从未真跑

## 现象（四型）

1. **行数算错**：我用 `Get-Content` 数行，v2 模板报 **45 行**、卡 v1 报 **43 行**；用 `[System.IO.File]::ReadAllText()` 数 `\n` 得 **74 行**／**79 行**。接班窗据此指出我单⑥ 的读数错。
2. **输出捕获被拒**：`git status --short | Out-Null` 与 `git status --short > 文件` 均报 `Program 'git.cmd' failed to run: Access is denied`；裸跑（不经管道、不重定向）正常。两个独立窗各自撞到一次。
3. **`@()` 赋值假零**：`$x = @(git status --short)` 返回空数组**且不报错**——"零改动"与"没读到"长得一模一样（坑 058 同型）。
4. **钩子假绿**：`pre-commit` 里 `timeout 20 python ev_check.py` 在 Windows 被解析成系统 `TIME‌OUT.EXE`，报 `Invalid syntax`，钩子于是打一行"[ev] 自检脚本非零退码（1）⇒ 照旧放行"——**它设计成永不拦阻，所以"没跑成"与"跑通了"输出几乎一样**，该仓每次提交的 ev 自检实际是空转。

## 根因

**"能取到数"和"取到的是真数"是两件事，我只验了前者。** 具体三处：解码默认值（GBK vs UTF-8）会改变行数；沙箱对 native 进程 stdio 的处理会让捕获静默失败；Windows 上同名命令（`timeout`）与 GNU 工具行为不同。三者都不会报错，只会给一个**看起来正常的错数**。

## 解法（三条，已落条文／姿势）

- **计数**：一律 `[System.IO.File]::ReadAllText()` ＋正则数 `\n`，`Get-Content` 只用于看内容不用于计数（卡 v1.1 §三.2 已写死）。
- **取全文**：凡计数一律**直跑看屏**；需要落盘时用 `cmd /c <命令> > %TEMP%\out.txt` 绕开 PowerShell 的管道（`d776cb39` 接班窗自曝此姿势，回执 §八）。
- **验钩子**：钩子"永不拦阻"的设计下，**必须有"没跑成"的独立信号**（本仓 ev 钩子已有 `[ev] 自检零输出` 一档，但 `timeout` 那条让它变成非零退码而非零输出）。修 `timeout` 前，凡报"钩子过了"都要加一句"它可真跑过"。

## 排障顺序（可复用）

**先验量具，再验数据。** 拿一个已知答案的样本（本例：手数一页 74 行的文件）喂给同一个命令，对不上就换尺，别去质疑被测量。

## 教训

**凡是"一个命令给一个数"，先问这把尺自己验过没有；量具没验，数是真数也是假数。**
