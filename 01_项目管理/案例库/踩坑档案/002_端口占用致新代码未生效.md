# 坑 002：端口被旧进程占用，导致"新代码没生效"

## 现象（用户视角，原话）

- "Pico 上这个网址打不开啊，显示已离线"
- 重启批处理后，控制台窗口出现红字 `[Errno 10048] error while attempting to bind on address ('0.0.0.0', 8777)`

## 根因（表象是网络问题，真相是进程问题）

昨天启动的旧版控制台进程一直没关，**独占 8777 端口**，而且只监听 `127.0.0.1`（本机回环）。今天重启批处理时：

- 新服务想绑 8777 → 端口已被占 → 抛 ERROR 10048（地址已在使用）→ 新进程启动失败
- Pico 从局域网连过来 → 连到的是那个**旧进程**（旧代码没有 VR 功能、且只听回环地址）→ 表现为"已离线"

**关键认知**：`127.0.0.1`（只监听本机）和 `0.0.0.0`（监听所有网卡）是两回事。旧代码只听 `127.0.0.1`，局域网设备根本连不进来；新代码已改为 `0.0.0.0`，但新代码没跑起来，等于没用。

## 解法

1. 查谁占了端口：`Get-NetTCPConnection -LocalPort 8777 -State Listen` → 看 OwningProcess
2. 确认该进程**空闲、无进行中的采集会话**（查 `/api/monitor/status` 和 `/api/experiment/status`），避免误杀正在采数据的会话
3. 终止旧进程：`Stop-Process -Id <pid> -Force`
4. 确认端口释放后，重新用批处理启动新服务
5. 验证监听地址变成 `0.0.0.0:8777` 而非 `127.0.0.1:8777`

## 排障顺序（可复用）

局域网设备"连不上/已离线"，**先查端口与进程，再查网络**：

1. 服务是否在跑、监听的是 `0.0.0.0` 还是 `127.0.0.1`（只听回环 = 局域网必连不上）
2. 端口是否被旧进程占用（新代码可能根本没启动成功）
3. 防火墙是否放行（本项目已放行 Python 3.12 全端口含 Public，不是障碍）
4. 最后才查 Wi-Fi 网段是否互通

## 教训

"重启一下"不等于"新代码生效了"。如果旧进程没退干净，重启会**静默失败**（新进程绑不上端口直接退出），而你看到的还是旧服务——表象完全正常，行为全是旧的。每次改完服务端代码，要验证的不只是"服务在跑"，而是"跑的是新代码、监听在所有网卡上"。
