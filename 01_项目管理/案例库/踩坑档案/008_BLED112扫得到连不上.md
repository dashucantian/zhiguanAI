# 坑 008：BLED112 扫得到头环却连不上（L4 connect 超时）

## 现象（用户视角）

法师在止观AI 统一控制台选「真机蓝牙（BLED112 外置适配器）」，会话起来后界面红字：

```
数据流静默 15 秒（疑似蓝牙断开，重连 3 次未成功）
```

头环开机、蓝灯亮、在 2 米内；同一只头环用「电脑内置适配器」却能正常连接、波形正常。即——**内置蓝牙通、BLED112 不通**。

## 分层诊断（bled112_diag.py，2026-09-09 实测）

| 层 | 检查 | 结果 |
|----|------|------|
| L1 | 串口发现（vid=0x2458 Bluegiga） | ✅ COM3 在 |
| L2 | BGAPI 后端启动 | ✅ 串口未被占用 |
| L3 | 扫描头环 | ✅ 扫到 `MuseS-E8D8` / `00:55:DA:BB:E8:D8` |
| **L4** | **发起连接** | ❌ **connect 超时**：public/random 两种地址类型都抛空 `NotConnectedError` |
| L5–L8 | 特征枚举/订阅/握手/收包 | 未到达（卡在 L4） |

**三重排除**（都不是失败原因）：
- 直连模式（跳过扫描，adapter 状态最干净）→ 仍失败；
- 放宽连接参数（interval 40–80、supervision_timeout 600）+ 超时加到 30 秒 → 仍失败；
- 占用检查 → 无 python 进程、系统蓝牙栈无 Muse 连接记录，**头环没被占用**。

## 根因（定性）

**失败精确锁定在「BLED112 发起连接」这一环：扫得到、连不上。** pygatt 的 `connect()` 发出 `gap_connect_direct` 后，超时窗口内等不到头环回 `connection_status=connected` 事件（`bgapi.py:494` 抛空 `NotConnectedError`）。

关键历史核实（踩坑档案 003 + 项目进程看板阶段 5e/5g）：
- BLED112 通道 09-05 实现、09-06 做过 V1.3 写语义修复，但**始终标注"真机回归待法师实测"，从未被验证成功过**；
- 09-06 那次失败的层是"**连上了但零数据流**"（卡在握手后，看门狗报"静默18秒"）；
- **09-09 这次的失败层更靠前——连 L4 连接都过不去**。两者不是同一个故障。

嫌疑（按可能性）：① BLED112 适配器固件偏老，与 Muse S（较新 BLE 外设）的 `gap_connect_direct` 时序/参数不兼容；② pygatt 5.0.0 对这只头环的连接握手适配问题。**非本项目代码回归**（BLED112 连接代码本轮一行未改）。

## 解法

**短期（务实，已采纳）**：内置蓝牙既已验证正常（法师 09-09 实测问题3 排除），**日常采集不依赖 BLED112**。BLED112 暂列"已知连接层不可用、待查固件"，不阻塞主线。

**深挖（待法师拍板）**：
1. 纯 BGAPI 底层连接探针——绕开 pygatt，直接发 BGAPI 字节命令读适配器返回码，定位是固件层还是协议层；
2. 查/升 BLED112 固件版本——需 Silicon Labs（原 Bluegiga）BGAPI 工具，超出当前环境；
3. 换一只 BLE 适配器或用 bleak 的 WinRT 后端替代 pygatt 的 BGAPI 后端。

**可观测性改进（已落地，提交 4cacbcc）**：看门狗最终红字此前只显示通用文案、吞掉底层真因；现已让 `_last_reconnect_cause` 把最后一次真实原因（如"扫描未发现 Muse 头环""BLED112 连接失败"）带进错误文本——下次故障界面直接可见根因。

## 排障顺序（可复用）

"BLED112 连不上 / 数据流静默"，按这个顺序：
1. **先跑 `bled112_diag.py`**（L1–L8 分层）——一眼看出卡在哪层，不要盲改代码；
2. L3 能扫到但 L4 连不上 → 嫌疑适配器固件/连接参数，**不是**头环也不是本项目代码；
3. L3 都扫不到 → 头环没开机/被占用/刚被反复 connect 打进自闭态（**静置 30 秒再试，勿连续 connect**）；
4. 对照实验：用内置蓝牙（已知良好路径）扫+连同一头环，能连→问题特定于 BLED112，连不上→头环侧。

## 教训

**"买了备用通道"不等于"备用通道能用"。** BLED112 从 09-05 实现到 09-09 从未真机验证成功，期间一直靠"待法师实测"挂着——备用路径若不主动验证，真要用时才发现是坏的。**分层诊断工具（L1–L8）的价值**：把"连不上"这种笼统现象拆到具体某一层，避免在错误的层（代码/参数）上反复试错；而**反复 connect 会把 BLE 头环打进暂停广播的自闭态**，越试越糟——诊断要"单次、干净、有对照"。

## English Summary

**Symptom:** The console's "BLED112 external adapter" source connects the session but the UI shows "data stream silent 15s, reconnect failed 3×". The **same headset works fine over the PC's built-in Bluetooth** — built-in OK, BLED112 not.

**Layered diagnosis (`bled112_diag.py`):** L1 serial (COM3, vid=0x2458) ✅, L2 BGAPI backend start ✅, L3 scan ✅ (sees `MuseS-E8D8` / `00:55:DA:BB:E8:D8`), **L4 connect ❌ (timeout — empty `NotConnectedError` on both public/random address types)**, L5–L8 never reached. Ruled out: direct-connect mode (cleanest adapter state), relaxed connection params + 30s timeout, and occupancy (no python process, no system Muse connection record).

**Root cause:** Failure is precisely at "BLED112 initiates connection" — it scans the headset but cannot connect. pygatt's `gap_connect_direct` never gets a `connection_status=connected` event within the timeout. History check: the BLED112 path (built 09-05, write-semantics fix 09-06) was **always marked "pending real-device test" and never verified working**; the 09-06 failure was a *later* layer ("connected but zero data stream"), while 09-09 fails *earlier* (L4 connect itself). Suspect: aging BLED112 firmware incompatible with Muse S's connect timing, or pygatt 5.0.0 handshake adaptation. **Not a regression** — BLED112 connect code untouched this round.

**Fix (pragmatic, adopted):** Built-in Bluetooth is verified working, so daily acquisition does not depend on BLED112; BLED112 is parked as "known-bad at connect layer, firmware TBD". Deeper options pending decision: raw-BGAPI connect probe (bypass pygatt), firmware check/upgrade (needs Silicon Labs tooling), or swap adapter / use bleak WinRT backend instead of pygatt BGAPI. Observability fix shipped (commit 4cacbcc): the watchdog's final error now carries the last real reconnect cause instead of swallowing it.

**Lesson:** "Bought a backup channel" ≠ "backup channel works". BLED112 was never real-device-verified from 09-05 to 09-09. A layered diagnostic (L1–L8) pinpoints *which* layer fails and stops wrong-layer trial-and-error; and repeated `connect` attempts drive a BLE peripheral into a stop-advertising self-lock — diagnose **once, clean, with a control** (built-in Bluetooth as the known-good path).
