# 坑 081：隔离执行撞上共享工作树——起点不净，连工都开不了

## 现象（原话）

- 2026-11-03 17:2x，本窗派 Qoder 做「隔离执行实验」：在 `_analysis_tmp/wt/12ying-p1` 建独立 worktree，改 12.8 营推宣台账。
- 17:29 回件：**未开工**。任务书第 ① 步要求目标路径 `git status` 为空，实查不为空：

```
 M 06_宣发素材/发布队列/00_发布队列索引.md
?? 06_宣发素材/发布队列/01_发布审查清单.md
   56 insertions(+), 5 deletions(-)   ← W2 窗 cbd182cb 的在途改动
```

- 它给出的三条理由全部成立：worktree 从 HEAD 建**不带**这 56 行；主树有未提交改动，`merge --no-ff` 必被拒或冲突 ⇒ **「可合回」判据先天不成立**；替它带走＝替 W2 做提交决定。

## 根因（两层，第二层才是真的）

1. **表层**：目标目录被另一窗的在途改动占着。
2. **里层**：**我们所有窗共用一个工作树**（`D:\Project\zhiguanAI`）。共享树里「未提交的在途改动」是常态，而 `worktree add` 只接 `HEAD`——**它拿不到任何未提交的东西**。
   ⇒ 所以「隔离执行」不是加一条 `git worktree add` 就有的能力；**它的前提是可隔离的基线**，而共享树长期不提供这个前提。

## 解法（三条，按代价排）

- **甲·等**：等对方窗把在途改动提交或撤掉，基线归零再开工。最干净，但把实验节奏交给别人的排期——本轮因此押后。
- **乙·携带**：把在途改动原样带进 worktree 一并提交。**不取**：等于替另一个窗做提交决定，归属面立刻脏（坑 076 同族）。
- **丙·换载体**：挑一个**当前无他窗在途改动**的目标（本轮改到 `vr_gates\`，现查 0 项脏）。实验价值不减，且能立刻开工。**本轮取丙。**

## 排障顺序（可复用）

要开隔离执行，先跑三步：

1. `git status --porcelain -- <目标路径>` ——**必须为空**；不空就先查是谁的；
2. `git worktree list` ——确认为空、且没有同名分支残留；
3. `git rev-parse HEAD` ——记下起点 sha，收尾时用它算「主树是否被夹带改动」。

三步任一不满足，**不要开 worktree**：开了也合不回去。

## 教训

一句话：**共享工作树里没有「干净起点」这回事，除非你专门去要；而隔离执行的全部价值，都压在起点干净这一条上。**
