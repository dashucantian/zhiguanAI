## 一、现象：一条判据在两个时刻给出相反答案，而两次都合规

硬规则 7（`AI-开工入口.md` §二bis）原判据＝「开工前先 `list_chat_sessions` 看本仓是否有第二个 `running` 会话，**有则只出报告不落共享文**并报法师」。

**同一条判据的自我打脸**（W1 工程线 `b8729a7a` 来函 §〇 原样指出）：W3 派工函 §首 自陈「写前实测本仓 `running` 数＝**1**」——22:26 写时计数为 1、因此落了盘；W1 次日计数为 **3**、因此不落。**两次都严格按判据办，结论相反。**

## 二、根因：判据的量被"遵守判据所必需的动作"自己抬高

**协调窗的本位就是派工，而派工必然把 `running` 抬到 >1**（要派的窗得醒着）。于是：

```
要记录"我刚派了什么" → 须先派工 → 派工使 running >1 → 判据禁止落笔 → 记录不下来
```

规则咬住了自己的前提。**这不是执行不严，是判据选错了变量**：`running` 计数**度量的是"有多少窗在干活"，而规则真正想防的是"两个进程写同一个文件"**。两者只在"独窗作业"这一特例下重合，四窗并发是本项目的常态而非常态的例外。

⇒ 与坑 019 的关系：019 立的这条规则**目标是对的**（防"一名多手"），**判据选错了**。019 卡自己已如实标注「本条有已知漏检面，不要当万能闸用」——本坑是那句话的另一面：**它不只漏检，还会误禁**。

## 三、解法（法师 10-10 裁「同意你的建议」，已落 `AI-开工入口.md` §二bis 硬规则 7）

**判据从「裸计数」改「写入面」**：

- 目标文件**不在**任一在场 `running` 窗口的写入面内 ⇒ **照写**，且须在**本窗己档**同条明记「用例外口＋目标文件＋为何不在他窗写入面」。
- 目标文件**在**他窗写入面内 ⇒ **扣住不写**，候 `running` 复测＝1。
- 写入面＝该窗本轮派工函／己档／在途 `git status` 所列文件与目录。

**不减免四项**（例外口只放开"记录与已裁定文书"）：① **侧边栏／fork 任务仍一律只读**——019 那个病根（同 sid 两进程）与计数无关，不能被这个例外口放过；② 未裁事项仍不得代落；③ §三 并发四纪律照旧；④ §三.5 提交前逐行读 diff 照旧。

**连带一条流程改进**（采纳 W1 §七#3 建议）：**派工模板内置判据**——协调窗在派工函里直接写明"你的己档与你自己名下的分片按例外口照落"，不再让每窗各自撞一遍再各自上呈。

## 四、排障顺序（可复用）

一条规则连续被两窗以上报"我按它办但办不成" ⇒ **先怀疑判据选错了变量，不要先怀疑执行纪律**。查法：把判据的**度量对象**与规则的**防护目标**并排写出来，看它们是否只在特例下重合。若重合面＝独窗作业，而项目常态是多窗并发，则判据必错。

## 五、教训

**"一条规则死锁"（法师原话）比"一次违规"严重，因为它让守规矩变成不可能。** 判据要选**与被防事件同因果链的变量**（谁在写这个文件），不要选**廉价但只在特例下等价的代理变量**（有几个窗在跑）。这与 JP-010「拿易测的代理指标替代难测的真实判据」是同一个形状，只是那次发生在验收、这次发生在制度。
