# 坑 058：脚本取错键拿到空集合——"零差异"与"什么都没读到"在输出上长得一模一样

> 建立：2026-10-16 17:2x（本机 date 实取 17:30:53）｜编号先查后取：`踩坑档案/` 现读最大号 **057**、目录件数 **57**（测 17:30:20，取法＝对该目录 `ls | wc -l` 加 `ls | tail`）
> 归属：**W3 当值协调窗 c5d442aa 自踩自立案**（本窗自己写的比对脚本、自己先拿到假"零差异"）
> 状态：已识别、已改判据；属工具型坑，候法师审定入档

## 现象

要回答"本地快照与唯一任务源要不要每小时同步一次"，必须知道 6 分钟内两次拉取**源表内容有没有变**。两枚快照整文件校验和不同（`d99ba410` 与 `0a51def1`，测 17:28:11），看着像"变了"；实际差别只是文件里嵌着各自的拉取时刻。于是写行级比对脚本。

连跑四版，前三版都返回同一种输出：

1. 第一版按 `records` / `data.items` 猜键名 ⇒ `rows=0`、`only_in=0`、**两次的行级摘要同为 `e3b0c442`**。
2. 第二版取到 `data['data']`，但把每一行当字典处理（`isinstance(r,dict)`）⇒ 还是 `n1713=0 n1718=0`、差异 0、摘要仍是 `e3b0c442`。
3. 第三版脚本自身语法错（括号不配对），退码非 0，没产出结论。
4. 第四版先读拉取器源码 `20261007_W3_维那快照拉取_v1.py:290` 确认行容器是 **`fields` 名列表 ＋ `data` 行列表（列表套列表，不是字典）**，用 `zip(names,row)` 组装后重跑：**88 行、88 行，逐行差异 0 处，行级摘要两次同为 `c575ba97`**（测 17:27 段）。

前三版输出的样子与第四版**几乎相同**：都是"差异 0"。区别只在一处——**行数也是 0**。若不盯那一格，就会把"我什么都没读出来"写成"源表没有变化"，而且这个错判恰好**支持提问者想要的答案**（不用每小时同步），因此极可能一路通过。

## 根因

1. **否定结论与空输入共用同一个数字**。「0 处不同」既是最强的"没变"，也是最强的"没测"。比对类脚本如果没有把**参与比较的基数**当作独立断言打印出来，它就没有能力区分这两种。
2. **摘要值是固定串，但固定串有两种成因**。`e3b0c442` 是空字符串的 sha256 前缀——凡摘要落在它上面，几乎必然是取数环节空了，而不是数据相同。这一枚指纹本可以在第二版就当场拦下，因为**两次不同文件算出同一个空摘要**本身就是不合常理的信号。
3. **猜键名而不是读容器定义**。拉取器的输出结构在它自己的源码注释与 `normalize_rows` 返回值里写得很清楚（`:24—25` 行有形如 `{ok, identity, data:{fields, field_id_list, …, data[[…]], …}}` 的形状说明）。前三版全部是在**猜**，第四版才是**先取法后动手**——这与已落规约 §二.17④「遇障先查权威解法、禁猜测与反复试错」同条，本窗连着违了三版。

## 判别法（下次一眼认出）

> **任何"差异 0／没有／未命中"的结论，必须与它的基数同屏出现。** 报数形如「比 A 枚 88 行 × B 枚 88 行 ⇒ 差异 0 行」，不允许只写后半句。
>
> 三条硬自查：① **基数为零则结论作废**（不是"零差异"，是"没测到"）；② 摘要出现 `e3b0c442` ＝ 空串摘要，一律当**取数失败**处理，不当"内容相同"；③ 写比对脚本前先读**生产该文件的代码里那一行 return／dump**，确认容器是列表套列表还是字典套字典。
>
> 一句话口径：**说"我算出 0 处不同"之前，先证明"我手里两边各有一批可比的东西"，并把那一批的条数一起写出来。**

## 复现记（同坑当日在两窗两侧复发，23:4x 追加，原五节一字未回改）

值守台 C3 23:27 轮自曝两处**同一形状的假数**，与本卡首跑那三版属同一坑，但**形状更阴**：

- **a 型＝把数报大了**：它报某项 27 行，真值 **19 行**——因为状态列的取值是**列表型**，它拿列表当字符串比，把不该算的行算了进去。
- **e 型＝把数报成 0（假零）**：它报某项 0 行——依赖列是**字典列表**，它当字符串找 id，取到空集合，而**空集合上的"全部满足"恒真**，于是零行也"通过"。

它自己写的判据升级与本卡同向，且多出一句本卡没写到的东西：

> **筛行之前，先打印每一列的类型与非空数；0 结论必须与基数同屏。**
> **与本窗 18:01:59 那次崩在同一列——崩了反而暴露，本窗这两次不崩、只出错数。**

⇒ 这两句把本卡的判据往前推了一格：**「取数失败」有两种显形方式，崩是运气，不崩才是常态**。本卡原第③条只核到**行的容器形状**（行是列表还是字典），没核到**单元格类型**（某一列的值本身是列表或富文本结构）——而这两次的咬合点恰恰都在单元格类型上。已据此在本卡判别法里补第四问：**列的类型我核过吗？列表型当字符串比＝多算，字典列表当字符串找＝假零。**

同轮本窗侧的对应物（一并对档案，避免只记别人）：本窗 18:01:59 那次是 `TypeError: unhashable type: 'list'`——**同一列（富文本／列表型取值）在两个窗各咬一次，一次崩、一次不崩**。这正好是上面那句的实证。

## 本轮连带披露

本窗 17:19 己档第 六〇 段附近已写过一行「逐行差异 0 行」，但**当轮只落了结论、没贴取法**，事后无法自证当时跑的是哪条命令；17:27 这次是**行级脚本复算**、凭据即上行第四版。现算结论仍是 0 处，旧行不回改，依"旧字照留"在此补注。**结论没变，但可点验程度变了**——这正是 §二.19 第五款要的形状。
