## 三、结论：有条件采用

**采用**，但**只在这两个条件同时成立时**：

1. **目标路径 `git status` 为空**（无任何窗的在途改动）；
2. **任务以新增件为主**（新脚本、新文档），不是改共享件。

**不适用**（仍走主树）：

- **改共享件**的任务——worktree 最后仍要 `merge`，而 merge 撞主树在途改动就是冲突，隔离反而多一层；
- **被执行人依赖主树别处未提交状态**的任务（如调试时引用他窗正在改的件）。

**为什么不是"全面采用"**：本轮已经证过一次——原载体（12.8 营推宣台账）因为 W2 有 56 行在途，**连工都开不了**（坑 081）。`worktree add` 只接 `HEAD`，它隔离的是「写」，**不解决「基线干不干净」**。

## 四、过程中发现的一件系统性根因（要报法师）

执行位按来函要求自查，报出：

```
$ git config user.name   → zhiguanAI-agent
$ git config user.email  → agent@zhiguanai.local
```

⇒ **仓库级默认身份本身就是占位**。谁提交时漏带 `-c user.name`，就自动落占位——**坑 076 反复发作的根在这里**，不在某窗粗心。

两条处置，**候法师一句**：

| 案 | 做法 | 影响面 |
|---|---|---|
| 甲 | 把仓库默认 `user.name` 改成协调位或中性但可辨的值 | 影响所有窗；任何漏带 `-c` 的提交都变成「有身份但可能不对」——**比占位更容易误判**，我**不推荐** |
| **乙（推荐）** | 默认保留占位，但**每个窗出件前自查 + 提交后贴 `%an %cn` 回执**（已在 Qoder 侧落地） | 零风险；占位一旦出现就是「有人漏了自查」的明确信号 |
