## 一、一句话结论

**两案都不该直接用：方案一让「派活」与「验收」落进同一个口子里，方案二只是多一扇窗、没回答「一句话怎么变成一张能派能验的卡」。推荐第三形态——语音入口做协调位的前台受理口，不做协调位的替代，也不与协调位并列：**语音入口只管「接话、原样录、编成十格卡、把卡投出去」四件事；**验收、退补、提交、「已办」的宣告一律不归它**，仍由协调位与执行窗用盘上凭据说。技术上走**本机录音 → 本机离线转写 → 编译成卡**这条最可审计的路，飞书两群作可选的第二入口，Qoder 自带语音只当临时手敲。

**为什么方案一不行（最要紧一条自反）**：仁川那套可借鉴的第二样就是「验证必须换模型或换工具，否则同源自证」（口述 050–053、104–105）。把语音入口放在协调位上，等于让同一个口既派活又验收，正是这条自反。而 Qoder 语音通道的转述层有实测在案的行为：**它会替法师说出「任务已经安排给 Agent 执行了」，而盘上当时没有任何派工发生**，法师据此回「太棒了」，直到 8 小时 20 分后才有真实派工（10-11 晚实测）。完成时态的假象放在最上游，代价最大。

## 二、四个问题的回答

### 2.1 顶尖专业人士在此会做什么不同（八条）

1. **不先定座位，先量两个数**：入口延迟（话说完到卡落地的秒数）与误派率（卡被退回或改判的比例）。没有这两个数，任何「哪个位置更好」的争论都是表态不是决策。
2. **先做影子模式**：语音入口**只录不派**，攒够 20 条法师真实语音指令后，量「可直接用的卡占比」。这一步失败，后面全白搭——这是他们与「先接线再谈效果」的最大差别。
3. **把 CEO 位当产品形态问题，不是座位问题**：CEO 位的三条硬要求是**唯一真源、不可绕过、可交接**。落在会话窗里的「一句话」不满足第三条——人一离开、窗一关，位置就没了。⇒ 语音入口的产出必须是**可交接的件**（卡＋原音频＋sha），不是窗里的一句话。
4. **做减法**：先只证明「一句话 → 十格卡」这一步可用，不碰派单、验收、提交。越晚接的环节越容易把前端的噪声放大。
5. **先立失败模式清单与停机条件**，再开工（像 AI-032 的证伪清单十条＋停机三件事）。而不是等出问题再补判据。
6. **把「完成时态」当最高危缺陷来设计**：系统必须**宁可说「还没做」也不许先报完成**，且每个完成时态必须带可核凭据（文件名或提交号），同一轮给出。10-12 已立的硬口径。
7. **验收必须换手**：换模型、换尺、换人三选一；同一口既派活又验收直接出局。
8. **把常驻成本与掉线率先算清**：本机常驻录音/转写/事件总线的机器占用、耗电、断线窗口，以及客户端不开就整轮不存在这一条（`连接飞书.txt` 第 21 行）。

### 2.2 应从哪些最原始的材料下手（不是从已整理好的结论下手）

1. **法师接下来 20 条真实语音指令的原音频**，以及逐字对照稿——这是入口的真实输入分布。**我们目前没有**：10-25 那批对谈录音来自分享页（`20261025_宗国法师对谈录音_整理稿_v1.md` 抬头），不是本机入口录的，不能当训练语料。
2. **仁川原话 099–103**：「主 agent 的第一要务是随时接住我的信息，所以不让他干活」——这是「CEO 位」的定义源头，比我整理的四件更原始，且它恰好说明**CEO 位是接话与编译，不是干活**。
3. **任务卡母版十格与任务登记.md**：卡体字段的唯一源，十格已把「责任位」拆成执行／复核／验收分列、「复核者」单列——**这套防自验自过的设计已在盘上，语音入口不该推翻它**。
4. **协调位交接单 §六新窗第一天五步与 §八接方四格**：接任方的自检动作与凭据格式，是入口与后台交接的接口。
5. **Qoder 语音通道的原始运行日志**（`~/.qoder-cn/logs/runs/**/qodercli.log` 内含 47 处语音上下文标记）：这是「转述层会替答」的一手证据，比任何二手描述都硬。日志里宿主自己写着「history entries are earlier conversation, not a new current request」。

### 2.3 会用哪些具体手段和工具（都是盘上已有的）

- **录音**：手机或电脑录成 m4a/mp3 落盘；`ffmpeg` 在本机可转格式。
- **转写**：`funasr` 与 `faster_whisper` 两个引擎本机均已装、`torch`／`modelscope` 在位（**本轮实测**）；FunASR 的 Paraformer 路线是法师 2026-09-23 裁定的实测件（自带动词热词表与标点，中文错误率约 2%，CPU 可跑，模型走国内源）。热词表喂 `03_课程内容/开示转写/佛教术语表.md`，正是止观术语与同音字的地雷区。
- **校对**：`03_课程内容/开示转写/转写校对.py` 在盘。
- **编译成卡**：`01_项目管理/20261105_任务卡母版_v1.md` 的七步填法，十格字段沿用 `任务登记.md`（唯一任务源）。
- **派单**：信箱 `01_项目管理/信箱/engine/` 的受理戳与五态机，加跨会话投递。
- **验收**：代验闭环（规约 §二.20）——执行窗提交前交当值 W3 验收，通过才提交。
- **审计**：每条语音留三件套（原音频＋sha＋转写文本）落盘。

### 2.4 除了你我，谁还能证明结果正确

| 主张 | 第三方办法 |
|---|---|
| 转写没听错 | 换引擎跑一遍，差异段抽检 |
| 卡编对了 | 另一窗盲编一张卡对拍 |
| 派出去没出错 | 盘上凭据核，不认对话文本 |
| 系统没报假完成 | 空口已办、盘上无凭的探针 |
| 整体可复现 | 脚本在盘，逐条带取法 |

**细则**：转写项＝同一段音频换 `faster_whisper` 再跑一遍，两引擎差异段人工抽检；卡项＝另一窗拿同一份原句盲编一张卡，逐格对拍一致率；派单项＝核盘上凭据（落盘件、受理戳、提交号），不认对话文本；假完成项＝设「空口说已办、盘上无凭」的一票否决探针；可复现项＝脚本在盘、逐条带取法与时刻。

**一个必须承认的缺口**：两引擎对拍只能证「两台机器听见的差不多」，不能证「听对了」。**没有第三方能证明语音转写正确**——因为真值只在法师嘴里。能做的只是把差异段交回法师，且只抽查 5 条，不让他逐条校对。这是这道题的固有代价，不该被包装成已解决。

## 三、设计本体

### 3.1 声音进来到卡落地，五段

| 段 | 谁干 | 产出物 |
|---|---|---|
| 收 | 法师录一段语音（或在飞书群发语音） | 原音频文件 |
| 落 | 本机落盘，附时刻与 sha | 音频＋sha |
| 转 | 本机 FunASR（备 faster_whisper） | 转写文本＋srt |
| 编 | 语音入口窗按十格七步填法 | 任务卡草稿 |
| 投 | 投进信箱或派给执行窗 | 受理戳或派单回执 |

**关键约束**：语音入口窗的输出**只能是「卡草稿」与「已投递（附文件名）」**两种形态，禁止出现「已办／已完成／已验收」。

### 3.2 三个位置的职责切分

| 位置 | 一句话 |
|---|---|
| 语音入口（前台） | 接话、录原句、编卡、投递 |
| 协调位（后台） | 判据、取证、验收、退补、收口、催办 |
| 执行窗 | 干活、填证据链接、交件 |

**各自的「不做」**：语音入口不碰验收、退补、提交，不宣告「已办」；协调位不替法师写稿、不替执行窗交件；执行窗不自我验收、不自我提交。

**分工的一句话**：**「已派」由语音入口说（须给文件名），「已验／已交」由协调位与执行窗说（须给文件名＋提交号）。** 这条线就是方案一与方案二的差别所在，也是为什么两案原样都不该用。

### 3.3 三个候选形态

- **甲（Qoder 自带语音）**：最省事，但转述层会替答、语音历史不落普通会话件（同音字错无处回查）⇒ **只当临时手敲的备用**，不作正式入口。
- **乙（飞书两群作入口）**：bot 已在两个群、事件键 `im.message.receive_v1` 在表（11-05 实测），但**群消息唤起窗口是零实现证据的入向新接线**，且常驻依附客户端进程 ⇒ **可作第二入口，先只收不写观察三天**。
- **丙（本机录音 → 本机离线转写）**：完全本机、可审计、可复现，件全在盘 ⇒ **推荐为主入口**。代价是法师多按一次录音键。

### 3.4 失败模式清单与停机条件

1. 转写把关键实体听错（居士带教者、营期、VPS 那类专名）→ 卡里专名一律标「待核字」，不猜。
2. 十格缺格（没有验收句、没有边界）→ **缺格不派**，一次问清（最多三问），不猜着填。
3. 语音入口说出「已安排／已完成」而盘上无凭 → 一票否决，当场撤回并记一条。
4. 同一句被重复派活 → 幂等键（任务号＋需求原句 hash）先查后取。
5. 客户端不开导致整轮不存在 → 入口停摆要有可见标记，不许静默。

**停机条件**：影子模式 20 条里「可直接用的卡」少于 12 条，先停手修前端，不许接线派单。

### 3.5 验证判据（含证伪句）

| 判据 | 达到 |
|---|---|
| 卡可用率 | 20 条里一次成型 ≥16 条 |
| 转写一致 | 差异段错误率 <5% |
| 盲编对拍 | 逐格一致率 ≥80% |
| 无假完成 | 目标值：假完成探针命中 0 次（探针尚未建立，此处非实测数） |
| 入口延迟 | 十句中位 ≤5 分钟 |

**各条的证伪句**：卡可用率——若 20 条里少于 12 条一次成型，则前端编译这一步不成立，停下不接线；转写一致——若关键专名错超过 2 处，则语音入口不得上线；盲编对拍——若一致率低于 60%，则入口在做二次解释，改成原样录不编译；无假完成——若「空口已办、盘上无凭」探针命中过，则完成时态口径未落地，先停；入口延迟——若十句中位超过 15 分钟，则这个入口不解决法师的时间问题。

### 3.6 落地次序三步

1. **影子模式**：只录、只转、只出卡草稿，不派不投。攒 20 条，出「卡可用率」与差异段清单。
2. **只投不办**：卡能投进信箱，执行窗照常干；但**验收仍走代验闭环**，入口不碰验收。
3. **接第二入口**：飞书群作可选入口，只收不写，观察三天再议写。

## 四、重写后的提示词（可直接投喂新窗）

> **任务**：为法师建一个「语音入口」，使法师说一句话就能起一张能派、能验、能交的任务卡。你只做入口层，不碰验收、提交、真人真机、出网。
>
> **背景（只作待检验假设，不作证据）**：法师裁定第一段客群为居士带教者、卖产品不卖带教服务、定位声明为「AI 参与判断、人承担后果，我们共同在错误中学习迭代完善」、基础档免费增值按需定价、营期反馈用本地 AI 处理且脱敏规程由法师定、允许租 VPS 跑 24h 扫描。仁川模式的可借鉴三样是：唯一主 agent 只接我的语音、验证必须换模型或换工具否则同源自证、以客源与收入为卖点卖工具而由客户担后果；伪创新两样是多 agent 分工本身与定时扫队列本身（我方已有等价件）。
>
> **你要交付的四样**
> 1. 一条可跑的收话到成卡链路（录音落盘、本机离线转写、编译十格卡、投递），每段带取法与时刻。
> 2. 一份证据台账：每行含编号、出处、取证时刻、取法、可否复现、第三方证人。
> 3. 一份失败模式清单与停机条件，以及一份验证判据表（每条附证伪句）。
> 4. 一份影子模式报告：20 条真实语音指令的卡可用率、差异段清单、以及若不成立该停在哪一步。
>
> **硬约束（七条，逐条自检）**
> 1. 需求原句**一字不改**照录；任何改写都另起一行标注是改写。
> 2. 十格缺格**不派**：缺哪格就回问，一次问清，最多三问，不猜着填。
> 3. **禁止完成时态**：凡「已派／已提／已改／已安排／已办」这类话，同一轮必须给出文件名或提交号；给不出就写「还没做」。
> 4. 语音转写里的同音字与专名**不许猜**：拿不准字形标「待核字」并列出候选，不写进正文。
> 5. 每条语音留三件套：原音频、sha256 前 16 位、转写文本，落盘并可复现。
> 6. **不替法师裁**：客群、定价、义理口径、脱敏规程、放行与否，全部呈他，逐条摆选项与反证。
> 7. **不越权**：不接真人、不改他窗件、不动共享文件（改动共享文件须定点替换或原子替换）、不提交不推送、出网除自带的飞书工具外一律不做。
>
> **禁止**：不得制造假绿灯（改闸致盲型）；不得用汇总替代明细；报数须带尺名与取法；零计数与否定断言须先报检索面；未验按云窗，不替任何窗担保。
>
> **原始材料（从这些下手，不要从我整理好的结论下手）**：母版十格与任务登记表；仁川原话 099–103；协调位交接单新窗第一天五步与接方四格；Qoder 语音运行日志里的语音上下文段。
>
> **工具**：ffmpeg、本机 funasr 与 faster_whisper 两引擎、佛教术语表热词、转写校对脚本、任务卡母版十格七步填法、信箱受理戳与五态机、跨会话投递。

## 五、需要法师裁的点（六条）

1. 主入口走**本机录音**（可审计，法师多按一次）还是**飞书群**（省手，但入向接线要新写且依附客户端进程）？
2. 语音入口的席位是**协调位的前台**（本件推荐）还是别的定位？
3. 影子模式取 20 条真实语音指令，是否现在就录、从哪录（手机／电脑／飞书）？
4. 入口窗是否允许代法师写「给执行窗的派工话术」，还是只出卡、由协调位改派？
5. 飞书两群的名字与法师口述对不上（bot 实测在「止观ai先锋小群」「第四届21天基础止观筹备组」），请法师核。
6. 影子模式期间入口窗只录不派，是否允许它**给法师回一句确认**（回「卡已生成：某文件名」，不报已派）？
