我专门看了一圈目前社区、Agent开发者、Anthropic/OpenAI官方最佳实践，结论其实非常统一：

2025-2026 年主流共识已经从 Prompt Engineering 转向 Context Engineering（上下文工程）。

核心思想是：不要维护越来越长的聊天记录，而是主动管理上下文。

而你的情况：

有完整项目结构
本地文档体系完善
长周期开发

实际上非常接近目前社区公认的最高效工作流。

第一梯队方案（我最推荐）
文件系统 = 长期记忆

不要让聊天窗口承担记忆。

让：

项目文件
+
项目文档
+
阶段总结


承担记忆。

Anthropic 官方把这种思路称为：

Memory + Just-in-Time Context Retrieval

即：

信息存外部
需要时再取进上下文

而不是一直塞在对话窗口中。

社区最佳案例

目前 Claude Code、OpenCode、Aider、Cursor 高级用户里最流行的是：

project/

README.md

docs/
├── requirements.md
├── architecture.md
├── decisions.md
├── api.md

context/
├── current_status.md
├── todo.md
├── lessons.md


每次新会话：

只加载：

当前任务相关文档


而不是：

整个历史对话


这被认为是最稳定的方式。

为什么不建议一直使用一个窗口

Anthropic 官方专门提到一个概念：

Context Rot（上下文腐化）

意思是：

随着上下文越来越长，

模型会出现：

注意力分散
重要约束丢失
旧错误被反复引用
推理质量下降

即使还没达到窗口上限，

效果也可能已经开始变差。

这其实和很多人的体感一致：

前20轮特别聪明

100轮以后开始跑偏

最佳压缩策略

官方和社区都推荐：

阶段压缩（Compaction）

工作完一个阶段：

不要保存整个聊天。

而是生成：

# 状态摘要

## 已完成

- 用户模块
- RBAC权限

## 技术决策

- FastAPI
- PostgreSQL
- Redis

## 当前问题

- 支付回调设计

## 下一步

- 接入支付宝
- 接入微信支付


控制：

500~1500 Token


即可。

超长项目最佳架构

如果是：

3个月+
半年+
一年+


的项目。

只保留：

关键结论


不保留全部聊天。

成本最优解（社区公认）

我综合 Anthropic 官方、Claude Cookbook、Agent 社区总结后，认为对于你的情况最优策略是：

不推荐
一个窗口聊到底

推荐
阶段工作
↓
生成总结
↓
写入项目文档
↓
关闭窗口
↓
新窗口
↓
重新加载文档


循环。

我自己会给你的终极模板

每次准备开启新阶段时：

直接给 AI：

# 项目背景

@project_overview.md

# 当前架构

@architecture.md

# 技术决策

@decisions.md

# 当前状态

@current_status.md

# 当前任务

实现订单支付模块


通常：

1000~3000 tokens


就足够了。

而不是：

历史对话 100000+ tokens


最终结论（优先级排序）：

🥇 项目文档 + 阶段总结 + 新会话重启（最佳实践）
 🥈 阶段压缩后继续会话（次优）
 🥉 全程维护超长上下文聊天（最不推荐）

对于你这种已经有本地项目架构体系的人，我认为最优方案甚至不是“管理聊天上下文”，而是：

把聊天窗口当作一次性推理器，把项目文档库当作真正的记忆系统。

这也是目前 Claude Code、Cursor、Aider 等重度开发者社区正在收敛到的主流工作方式。
