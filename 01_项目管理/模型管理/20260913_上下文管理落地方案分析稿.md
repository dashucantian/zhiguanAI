## 〇、一句话结论

### 2.3 这条发现解释了三个既存现象

1. **规约形同虚设**：任何 AI 窗口都不可能真读完 §一 清单，只能挑着读或干脆不读——而"不读"正是 KZ-013（不知有 KZ 规则）、KZ-014（不知 Session 要区分窗口）的成因。

3. **云端窗口与本地窗口的能力差**：云端模型窗口大（可容纳更多必读），本地模型窗口小（必须极简）。**同一套规约不可能同时适配两者**——这是材料没考虑的分叉。

这是否可行？我的判断是：**可行，但必须改为"索引＋按需检索"，而非"清单全读"**。具体见 §四 方案。请 GPT 就"能否在保留规则约束力的前提下压到 3000 tokens 内"给出意见。

## 四、调整方案（六项，按优先级）

### P1 · 建"分层加载"体系，替换"清单全读"（对应材料 Level 1–4）

**核心改动：把开工规约 §一 的"读这些文件"改成"读这一个文件，其余按需取"。**

| 层 | 文件 | 预算 | 内容 | 加载时机 |
|----|------|------|------|---------|
| **L0 索引** | MEMORY.md（已有，29 行≈3095 tok） | ≤4,000 tok | 一行一条，只给"有什么、在哪" | **自动加载**（系统已有此机制） |
| **L1 状态** | `00_当前状态.md`（**新建**） | **≤1,200 tok** | 当前阶段／进行中的事／卡点／下一步／最近 3 条裁定 | **每次开工必读，唯一必读** |
| **L2 规约** | `AI-开工入口.md`（已有，需瘦身） | ≤1,500 tok | 只留强制动作与判定权边界，删除可查的细节 | 开工读（或读 L1 里的摘要） |
| **L3 按需** | 判语 13 张、台账、词汇表、日志 19 篇、28 个记忆文件 | 不限 | 全文 | **只在任务需要时检索读取** |

**关键纪律**：L1 状态文件**必须 ≤1,200 tokens**，超了就把细节下沉到 L3。这条是材料 Level 1（≤1000 tok）的项目化落地，放宽到 1200 是因为本项目须含密级与窗口信息。

**L3 按需检索的可行性已实测**：项目已具备 Grep／Glob／Read 工具链，判语与台账均可精确定位（本会话多次这样用）。**所以"不全读"不等于"不知道"，而是"知道去哪查"**。

### P2 · 建 `00_当前状态.md`（补材料 Level 3 缺口）

**实测项目无此文件**（§一 对照第 4、5 项）。建议结构（严格 ≤1,200 tok）：

```
# 当前状态（开工唯一必读）
更新：YYYY-MM-DD HH:MM by <Session>

## 当前阶段
（1–2 行）

## 进行中（含负责人窗口）
- W1: …
- W4: …

## 卡点／待法师裁定
- F1 两套四窗口撞名处置
- …

## 最近 3 条裁定
- 09-13 四窗口编制
- …

## 开工须知的三条硬约束
1. 原始脑电／学员档案／声纹绝不出网（D3/D22）
2. 涉文本订正登记 KZ＋就地注记
3. 提交走五步确认，禁 git add . / commit -a
```

**维护规则**：每次会话结束由该窗口更新（对应材料 Level 4 的 Session Summary，但**合并为一个文件而非每会话一个文件**——避免 19 篇日志式的体量膨胀）。历史细节进工作日志，本文件只留当前态。

### P3 · 开工规约 §一 改为"按需检索表"（解决 §二 超窗问题）

把现在的"开工前读什么（6 项全文）"改为：

```
## 一、开工前
1. 必读：00_当前状态.md（≤1200 tok）＋本规约（≤1500 tok）
2. 按需查（不要全读，用 Grep/Read 定位）：
   - 术语口径 → 词汇命名映射表
   - 某项决策为何这样定 → 案例库\决策判语\（按编号或关键词检索单张）
   - 历史订正 → 书稿勘误与订正台账（检索 KZ-0NN）
   - 身份/窗口/提交规范 → AI代理身份登记
   - 模型选型 → 模型与工具路由表
3. 判语含修订注记，作废条款不得沿用（如 003 的 VLX-Seek 已移出）
```

**效果**：开工固定开销从 ~64,800–86,400 tok 降到 **≤2,700 tok**，压缩约 **96%**，且本地 16K 窗口的 Ornith 也能装下。

### P4 · 阶段压缩纪律（对应材料 Compaction）

材料建议 500–1500 token 摘要。**项目现状失度**：19 篇工作日志合计 110,742 字符，单篇最长 8,927 字符（≈6,695 tok），**超材料建议 4–13 倍**。

建议：
- 工作日志保留现有详细度（它是 L1 素材层，价值在完整），**但每篇顶部加 ≤300 tok 的"一句话摘要＋关键结论"**，供 L1 状态文件引用；
- L1 状态文件只引摘要，不引全文；
- 会话结束时的阶段总结写进 L1，**不另建 session_summary 文件**（避免文件数膨胀）。

### P5 · 窗口与上下文预算的对应关系（材料未覆盖）

四窗口的上下文需求差异很大，应配不同预算与模型：

| 窗口 | 典型任务 | 建议模型 | Context 需求 | 说明 |
|------|---------|---------|-------------|------|
| W1 工程线 | 代码修改、真机调试 | 本地 Qwen3.8（32K）或云端 | 中（代码文件大） | 须留足代码上下文，L3 按需检索更关键 |
| W2 文档线 | 书稿、判语、日志 | 本地 Qwen3.6 A3B（32K，速度最快） | 中 | 书稿单篇 5,000–10,000 字符，可容纳 |
| W3 制度与机动 | 跨域协调、归因、方案 | 云端（窗口大）或 Ornith（复核） | **高**（须跨多文档） | 本会话即此类，已实证长上下文导致 6 次误判 |
| W4 模型线 | 模型调试、训练、评测 | 本地 Qwen3.6／Ornith | 低—中 | 评测集单文件小 |

**一条重要建议（待 GPT 验证 F2）**：**W3 这类跨域协调任务，应主动控制会话长度**——材料说的"工作完一个阶段→生成总结→写入文档→关闭窗口→新窗口重新加载"循环，最该用在 W3。本会话已是反例：从摘要续接后继续数十轮，导致反复误判。

### P6 · L3 密级对加载范围的硬约束（材料完全未覆盖）

材料假设所有项目文档都可自由加载。**本项目不行**：

- 《隐私分级说明》：原始脑电／学员档案／声纹／督导内容**绝不出网**（D3／D22 铁律）
- `02_修道班运营\机密-学员数据\`（781 MB／569 文件）属 L3
- **若用云端模型（如本会话），L3 内容不得进入上下文**——本会话已两次因 grep 越线带出该目录内容片段，记入教训

**故加载体系须加一条前置过滤**：任何"按需检索"都不得触及 L3 机密目录。建议写进开工规约 §四（判定权边界）与 L1 状态文件的"三条硬约束"。

### 10.3 本轮 AI-001 自我纠错：一次测量口径虚警（重要教训）

核校过程中我**先犯了一个错并险些据此误改方案稿**，如实记录：

- **错误判断**：本轮初次复核用 PowerShell `Get-Content -Raw` 测必读文件，得「决策日志 34036、台账 12310…」等，与方案稿记载（27266／9881…）**全部不符**，遂判断「方案稿数字系统性偏小约 20%、合计少记 17448 字符」，并误报「3 项必读文件不存在」。
- **「3 项不存在」纯属错**：那两个路径（`02_架构与理论\…判语档案.md`、根目录 `MEMORY.md`）出自**我记忆里的旧版规约**；现行规约 §一 实际指向 `案例库\决策判语\`（13 个分散文件，命名 `001_…`）与《分工与决策日志》，**全部存在**。又是一次「凭记忆核查」（KZ-009/010 同型）。
- **数字不符是测量口径错**：PowerShell 5.1 的 `Get-Content -Raw` 对 **UTF-8 无 BOM** 文件按 ANSI/GBK 解码，中文被错误拆分致字符数**虚高约 25%**。改用 `[System.IO.File]::ReadAllText()`（默认 UTF-8）重测，七项与方案稿记载**逐项吻合**：

| 台账 | 9,881 | 9,881 | 0 |

| 路由表 | 2,798 | 2,871 | +73 |
| 开工入口 | 3,221 | 3,221 | 0 |

- **结论**：**方案稿 §二 的数字是准确的，本轮虚警才是错的。** 差 75 字符（主要来自路由表 +73，原因未深究，疑为 09-13 后微调或同步差）**不影响任何结论**（超窗 2–5 倍稳健）。我差点把正确数字改成错误数字——这正是开工规约 §五.4 的反向印证：方案稿数字精确不是「可疑」，是因当初用了正确口径。
