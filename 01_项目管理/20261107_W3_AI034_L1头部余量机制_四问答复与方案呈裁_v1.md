## 一、第一问：设定的值是否合理

### 1.1 现读三值（全部带尺名与时刻）

| 项 | 现读值 | 尺名（判据出处） | 时刻 |
|---|---|---|---|
| 判据上限 | **1,578 字符** | `收口检查.ps1:588` `$judge = 1578` | 2026-11-07 23:2x 现跑 |
| 计量口径 | 全部字符（含换行） | `收口检查.ps1:587` `$lenS = ([System.IO.File]::ReadAllText($f5s,[System.Text.Encoding]::UTF8)).Length` | 同上 |
| **工作树现读 L1** | **1,172 字符 ⇒ 余量 406** | 同上两行 | 同上 |
| **入库版（HEAD）L1** | **1,521 字符 ⇒ 余量 57** | `git show HEAD:00_当前状态.md` 后取字符数 | 同上 |
| 工作树未入库改动 | **2 增 3 删** | `git diff --numstat -- 00_当前状态.md` | 同上 |
| 开工入口体量 | **51,879 字符**（表内无其判据行，闸 18 只报不判） | `收口检查.ps1:592—594` | 同上 |
| 头部更新条现读长度 | `:4` = **295 字**（11-07 21:2x）／`:5` = 232 字（11-06 04:4x） | `收口检查.ps1:53` 闸 3（头部 ≤12 行内、`^> (更新\|前次更新)`、Length > 300 告警） | 同上 |

**⚠ 一处必须说清的差**：法师说的「余量仅 57 字符」＝**入库版**的数（1,521 对 1,578）；**协调位当轮已修**的那一笔**在工作树、尚未入库**（2 增 3 删），落进去余量就是 406。⇒ **57 与 406 不是分歧，是两个时点的读数**；工作树那一笔是否入库，按提交纪律候放行。

### 1.2 这个值合不合理：本窗的判断是「**数值可留，机制不合理**」

**数值本身**：1,578 这个绝对值是 2026-10-29 瘦身方案定下的，量级与「一页必读」相称——现状 1,172 字符（约 2 屏），人读得完。**它没坏，不必改**。

**三条不合理（都在「机制」不在「数」）**：

1. **字符是唯一尺，与读负担脱钩**。真正要防的是「必读页读不完」，不是「字符数超某个整数」。同样的 1,578 字符，写成十条短行（要翻十下）与写成三段（读一遍就完）**读负担差很远**，但判据看不出差别。
2. **绝对值与更新行的实际尺寸不匹配**。一条更新行实测 295 字 ⇒ 406 的余量**只够再放一条**（1,172 + 295 = 1,467 仍过，1,172 + 590 = 1,762 即超）。也就是说：**余量不是缓冲区，是「还能写一条」的许可**。这正是法师说的「再增一条即超」——机制没错，但**它逼着每轮做「下沉」这个动作，而没人写明下沉规则**，于是就出现「滞后」。
3. **判据只判总量、不判条目数与条目长度**，于是每轮的新增都挤在同一把尺上靠自觉守 300 字（闸 3 只在头部 12 行内查、且只报「某行超 300」）。**没有「新增必下沉」的收支规则** ⇒ 越写越挤。

**结论**：**1,578 留作兜底红线（防止状态页无限膨胀），但主要手段应当是结构性上限。**

## 二、第二问：其他专业团队在类似方案里怎么做（调研）

> **取法说明**：以下六条是本轮出网调研所得的**做法要点**；来源出处名称照录。**本窗未把原页链接存盘**，不凭印象生成链接（§二.11 禁猜 URL）——若您要逐条复核原页，请指定，或本窗下一轮重新检索并把链接与访问时刻一并存盘。**要点本身可独立成立，不依赖链接。**

| 来源（出处名称） | 在「状态页／必读页放多少、怎么防它胀」上的做法 | 对我们的可搬之处 |
|---|---|---|
| **DeepSeek Harness（`doc-budgets.manifest.json`）** | 给每份文档定**字数预算**，逐文档记上限；另设 `verify-doc-budgets` 门禁自动查超限；**超限的处理顺序写死**：先搬走 → 再压缩 → 最后才提高上限，且**提高上限必须在提交说明里解释** | ①预算按文件分配，不靠人估 ②超限有固定处理顺序 ③**改预算要留解释痕迹** |
| **GitHub Projects 最佳实践** | 任务与状态**单一真值源**；状态面与档案面**冷热分离**——现势面只留「现在是什么」，历史进冷档 | ①L1 只留现势 ②历史一律下沉冷档（我们已经在做，方向对） |
| **Azure ADR（架构决策记录）** | 单一真值源；决策记录要**pithy／assertive／on-topic／factual**；**没人会读大文档**，小而模块化的才可能被更新 | ①更新条目要短 ②长内容另开件，L1 只放指针 |
| **Nygard／Cognitect（ADR 写作规范）** | 同上：文档要短、模块化、有人维护；大而全的文档会烂尾 | ①「更新行」不应承担正文职责 ②正文另落件、L1 放指针 |
| **docs-cleaner（文档防腐）** | 命名了两种病：**documentation rot**（文档腐烂）与 **version drift**（版本漂移）；同一主题跨文件超约 500 行即判 sprawl（蔓延） | ①L1 与冷档的差要显式维护 ②主题散落要收口 |
| **plan-tree（实施状态文档）** | **implementation-status 文档要短到能续跑会话**；长档案另置 | ①L1 的用途就是「续跑会话」⇒ 短是功能要求，不是省字 |
| **MVD（最小可行文档）** | 设计文档 **2 页以内**才有被读完的可能 | ①给 L1 定一个「页数当量」而非纯字符数更贴读负担 |

### 三条共同做法（这是要点里最值得抄的）

1. **分层，不压成字数**：现势面／档案面分开，长内容外置，L1 只留指针与现势。
2. **预算＋固定超限处理顺序**：预算不是「尽量不超」，是「超了就按 搬走→压缩→提额 的次序办」；提额是最后手段且要解释。
3. **上限的改动留痕**：改判据不是不能改，改了要说清为什么（这与我们在规约 §二.18「接受他者检验」里已经定的「题面自报数须可核」同一路）。

**对我们最关键的一条观察**：**专业做法里没有「一个绝对字符数硬卡状态页」这一条**。它们管的是**层级与条目数**，字符数只是预算的一种表达。我们现在把字符数当成唯一判据，正是「再增一条即超」的根因。
