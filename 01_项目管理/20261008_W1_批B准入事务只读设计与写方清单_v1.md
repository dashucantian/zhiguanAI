## 三、W3 未覆盖的三条新发现（都会改变方案形态）

1. **撤回闸不仅没写方，还有一枚 BOM 地雷。**`_participant_withdrawn:367` 用 `encoding="utf-8"` 读，而本仓写惯例**带 BOM**（`registry_tx.py:206`，`01_registry/participant_registry.csv` 与 `session_registry.csv` 实测均带 BOM）。⇒ 将来任何"守规矩"的写方一落地，`json.load` 就抛，并被 `:370-371` 的裸 `except → False` 吞掉 ⇒ **撤回检查静默失效（fail-open）**。另外真实逐参与者状态其实在 `01_registry/participant_registry.csv` 的 `status` 列（现值全 `active`），**没有任何代码读写它** ⇒ 仓里并存两套未对账的撤回事实。设计必须先决定以哪套为正源，不能另造第三套。

2. **「入队后隔离」今天只有手工编辑一条路**（§一.2）。这直接决定：**锁无法约束一个不存在的写通道**。要把 W3 §13.8「双次复核不足以保证」真正收口，要么**新建一个受控隔离写入口**（新代码面＋须裁），要么承认手工面在锁外、改用**内容指纹复核**把窗口从「无界」压到「重读之后到提升之前」。

3. **监测入口传的显式 QC 是被剥了字段的结果。**链：`qc_pipeline.assess* → console_server.qc_assess:161-172 → enqueue:412 → admit:382 → _qc_verdict:322-325`。薄适配层**只留 `recommend`／`reasons`／`metrics`**，故显式分支里 `quarantined` 恒 False、`threshold_version` 恒 None，且**零路径探测**（不读定稿）。⇒ 与 W3 §13.4 一致并补一句：**`source="fresh"` 只是代码标签，不代表未命中缓存，更不代表人工隔离已核**。法师已赞同「显式 ingest 不得覆盖隔离否决」——落实它必须改这个适配契约或改显式分支优先级，**两者都属共用脚本**，不是补路径能覆盖的。

## 四、候选一致性方案（三个，可叠合）

### 方案丙｜写方协议地板（最小，先决条件）

**主张**：先让四份准入输入**自身**写得可信，再谈跨文件事务。不改准入语义。

- 内容：① `write_qc_json` 与 `refresh_qc` 的 tmp 名改**唯一**（`<path>.<pid>.<rand>.tmp`）＋补 flush/fsync，统一到仓内已有的 `_write_json_atomic` 纪律；② `refresh_qc.refresh` 的 RMW 拆两段——**`assess()` 在锁外算**，然后**加锁→重读当前定稿→把最新 `quarantined` 从**重读值**前抄（不是从秒前的快照抄）→替换→放锁**；③ 定稿写入纳入与登记表同族的 `registry_tx.locked`（锁件＝`qc.json.lock`，复用现成机制，见 §二.D）。
- 锁序：**只新增 `qc.json.lock` 一层**，不与 congci 的 claim/brain/index 交叉 ⇒ 无新死锁面。
- 崩溃恢复：唯一 tmp 名 ⇒ 败者不会毁掉胜者字节；残留 `.tmp` 无害可回收；锁沿用 DEAD-only＋10 s TimeoutError 语义，挂死进程不夺锁、由人工按坑 018 清。
- 对 refresh 旧值覆盖：**直接闭合**（重读合并）。
- 对交叉发布与「数据已发布而登记表未写」：**闭合**。
- **不解决**：中间态（目录已发布、定稿尚未产生）、入队后状态变化、显式 qc 剥字段。
- 范围：`qc_pipeline.py::write_qc_json`（仅写入协议，**不碰 `assess`／阈值**）、`tools/refresh_qc.py::refresh:70`（＋其 import 段）。

### 方案乙｜三态准入＋消费侧双次复核（推荐增量）

**主张**：在丙之上，把「读不到定稿」从**回落放行**改成**unknown 不喂**，并在两个决策点重读。

- ① `_qc_verdict` 返回值增第三态：`{verdict: ingest|quarantine|unknown, reason, evidence}`。**unknown 的判定**必须是**位置感知**的（承 §13.8「不拿 ZEN- 前缀当充分依据」）：新增 `_locate_source_area(npz_path)`，**以 `_CFG["zen_root"]` 为根、按合法布局枚举**（`02_raw/<sid>/eeg_raw.npz`、`03_quality_control/quarantine/<sid>/eeg_raw.npz`）并用 `os.path.commonprefix`＋`realpath` 判**确在同一根之下**，据此得「归档位／隔离位／正常暂存位／未知位置」四选一。**仅当识别为正常暂存位**才允许现算；**识别为归档/隔离位却缺定稿或定稿损坏/字段无效 ⇒ unknown**；**位置识别不了 ⇒ unknown**（不冒充暂存）。
- ② `admit`：`unknown ⇒ admitted=False, reason="准入状态未知（阶段 X）"`。`quarantined` 取「**路径证据 ∨ 定稿证据 ∨ 显式证据**」三源**或**，任一为真即否决；显式 `recommend=ingest` 不得压下任一否决源。
- ③ 消费侧双次复核（§13.8 第二行）：`_process_row` 在 `:641` 现有 status 重读之后**追加一次准入重读**；并**在 `os.replace(cand,bp)`（`:710`）之前**、仍在脑锁内，**再重读一次**——重读用 `_resolve_npz` 解析后的**实际路径**与 `_read_index` 重读后的行身份，不只信旧 row。`recover_pending:789` 的 `os.replace`（`:802`）之前套同一道闸，并**补 `_claim_acquire`**（现缺）。
- ④ 定稿指纹入行：`enqueue` 把当时定稿的 `sha16`＋`threshold_version`＋`qc_source` 写进 row（`:472-473` 现在只存 source/recommend）；复核时**指纹变了 ⇒ 视为状态已变 ⇒ unknown 拒**，而不是拿新值继续。
- 锁获取顺序（必须钉进规约）：**`认领件 → qc.json.lock（仅读一下）→ brain 锁 → index 锁`**，全程只允许这一序；`admission` 侧任何函数**不得在持 index 锁时再取 index 锁**（`registry_tx.locked` **不可重入**，重入即自锁 10 秒后 `TimeoutError`——这条是给实现的硬约束：新复核调用**必须放在锁外或复用已重读的值**，绝不能让 `admit` 自己去拿 index/brain 锁）。
- 死锁风险：低。新顺序里 `qc.json.lock` 是被**读方短暂持有**、写方（丙）持有；两者不与 brain/index 形成环（写方拿 `qc.json.lock` 时不拿 brain/index）。**唯一要防的是同锁重入**，见上。
- 崩溃恢复：unknown 一律**不提升、不记 committed**（§13.8 第五行），行留 pending 待重试或人工；拒绝原因、复核阶段、来源与版本证据落 row／`record.json`。是否复用 `failed` 与重试计数**须随实现定**（本窗不自定）。
- 对 refresh 旧值覆盖：靠丙闭合；乙只负责把「refresh 期间」读成 unknown 而非放行。
- **仍不闭合**：**重读之后到 `os.replace` 之前**这一小段——因为隔离写方是手工的，不持任何锁。⇒ 乙是「窗口从无界压到微秒」，**不是严格保证**。本窗如实如此报，不称收口。
- 范围：`congci_pipeline.py::{_locate_source_area(新), _qc_verdict, admit, enqueue, _process_row, recover_pending, _resolve_npz}`；`console_server.py::qc_assess:161-172`（适配层保留 `quarantined`／`threshold_version`）＋两处 enqueue 调用点 `:698-705`／`:1151-1158`。

### 方案甲｜共同临界区（严格保证，但须先造写通道）

**主张**：只有当「状态变更生效」与「脑提升」在同一临界区，才能真正收口。

- 内容：在乙之上，**新建一个受控的隔离/撤回写入口**（CLI 子命令或 `console_server` 端点），该入口**必须持 `qc.json.lock` 与一把新增 `admission.lock`**；`_process_row` 的最终复核与 `os.replace(cand,bp)` **同在 `admission.lock` 内**完成；`participant_status.json` 的写方也走同一入口（顺带定正源：JSON 还是 `participant_registry.csv` 的 `status` 列）。
- 锁序：`认领件 → admission.lock → qc.json.lock → brain 锁 → index 锁`（写侧只取前两级，永不反向）。
- 死锁风险：中。跨模块两级新锁必须**唯一全序**；建议实现期加"加锁顺序断言"（持锁集合记入进程内并在调试构建校验单调不减）。
- 崩溃恢复：`admission.lock` 沿用 DEAD-only；提升是单文件 `os.replace`，索引提交恒最后（现有序已自证），所以"脑已提升、索引未提交"仍由 `recover_pending` 的指纹重读补登——**注意补登也要过闸**。
- 对 refresh 旧值覆盖：refresh 必须进同一临界区重读合并（乙/丙已含）。
- **代价与前置**：这是**新增产品面**（新的隔离/撤回操作入口），不是改 bug；需法师先裁「是否要有程序化隔离通道、正源是 JSON 还是 CSV」。**在这一裁下来之前，甲无法施工**，也不能靠锁去假装覆盖手工面。
