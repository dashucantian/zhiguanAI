## 一、为什么需要这张表

2026-09-12 两个实验证明，归因不能靠"把 git 的 user.name 改一改"解决：

- **实验 1**：只把 user.name 改成 AI 身份后，提交一份**法师手改**的内容 → git 记录 `author=AI`，法师的改动被署成了 AI。
- **实验 2**：用同一个 user.name 让两个 AI 窗口分别提交 → 两次 `author` 完全相同，**无法区分是哪个模型、哪个窗口**。

结论：必须有**稳定的身份对照表**，让每次提交的 author（内容归属）、committer（执行 AI）、trailer（模型／窗口／依据）都有处可查、彼此能区分。本表即此对照。

## 三bis、窗口分类与认领（2026-09-13 法师裁定：四窗口）

### 为什么是四窗口——实测依据，非凭印象

2026-09-13 对 git 全部 48 次提交、372 次文件变更按路径聚类，实测结果：

| 域 | 文件变更占比 | 活跃日数 |
|----|-------------|---------|
| D4 脑电／VR 代码 | **53%** | 7 天（持续） |
| D7 文档／架构／管理 | 15% | 2 天 |
| D2 案例库／判语 | 13% | 6 天（持续） |
| D1 书稿／纪实／发布 | 10% | 1 天 |
| D5 工作日志 | 5% | 3 天 |
| D3 评测集 | 2% | 1 天 |

**两项关键指标**：① **90% 的提交是单域的**（平均每次提交只触及 1.21 个域）；② 域间共现最高仅 3 次，其余均为 1 次——**域与域之间耦合极松**。

这两条数据说明：绝大多数工作天然单域，分窗口不会造成"重复交代背景"的浪费；真正持续并行的只有代码线与案例库线。

**故窗口按"背景是否共享"划分，而非按任务名目细分**：背景不同的分开（避免上下文污染），背景共享的合并（避免重复交代）。

### 四窗口定义

| 窗口 | 名称 | 负责范围 | 对应实测域 | 划分依据 |
|------|------|---------|-----------|---------|
| **W1** | 工程线 | 脑电采集／VR 反馈／控制台代码／真机调试 | D4（53%，7 个活跃日） | 体量最大且持续并行，独立成窗 |
| **W2** | 文档线 | 书稿《行者无疆》三编制／案例库判语与踩坑／工作日志／发布队列 | D1＋D2＋D5 | 同属文本叙事，**背景高度共享**（八条法则、隐私分级、术语表、KZ 台账），合并可省重复交代 |
| **W3** | 制度与机动 | 架构管理／归因体系／跨域协调／临时任务／巡检 oversight | D7（与所有域都共现） | 跨域协调须独立于具体业务线，否则既当运动员又当裁判 |
| **W4** | 模型线 | **模型调试／模型分工／模型训练**／评测集黄金任务集／模型选型与路由 | D3＋模型相关 | **法师 2026-09-13 指定**：模型调试与训练是长期任务，须有专窗 |

**两处判断说明（法师可纠正）**：

1. **巡检代审不占窗口**——实测两个定时任务仍在运行（「周进度巡检」每周一 08:30、「待审提醒」每天 20:00，`lastRunStatus=ok`），由 cron 自动触发、在独立会话执行，**不占用窗口配额**（当前 2/5）。故归 W3 oversight，不单设窗口。
2. **D3 评测集划归 W4 而非 W1**——评测集黄金任务集的对象是模型能力评估，与"模型调试／训练"背景共享，故随 W4。此为 AI 判断，若法师认为应归 W1（代码线），请示下即改。

### 认领规则

1. **开工第一件事：认领窗口号**，并在 §三 AI 代理登记表登记本窗口的 AI 身份与所用模型。
2. **一个窗口同一时段只认领一个窗口号**；同一模型开两个窗口，则用两个不同窗口号（这正是 2026-09-13 身份冲突的解法，详 KZ-014）。
3. **跨窗口任务**（如书稿改完要同步案例库）：由 W3 协调，或两窗口各自只改自己认领的文件，**不代对方提交**（并发纪律③认领制）。
4. **窗口号不复用、不转让**：W1～W4 为长期固定编制，人员（AI）可换，窗口职责不变。

## 四、会话编号规则（Session）

**〔2026-09-14 法师裁定 F1 甲：改含模型槽〕** 格式：**`W<任务窗口>/M<模型槽>-<模型简写>-<日期YYYYMMDD>-<当日序号>`**

- 例：`W3/M1-QWEN-20260914-A`（W3 制度窗口、M1 模型槽即 Qwen3.6-A3B、千问、9 月 14 日、当日第一个会话）
- **W＝任务域窗口（W1–W4，§三bis）；M＝模型槽（M1–M4，见下表）**。两维正交、都须记录——法师 09-12 要"什么模型改的"、09-13 要"哪个任务域"，缺一不可。
- 同一窗口同一天的多次提交，**共用一个 Session**；不同窗口即使同模型同日，窗口号不同故 Session 天然唯一。

| 模型槽 | 模型 | Context |
|------|------|---------|
| **M1** | Qwen3.6 35B A3B（Q4_K_M） | 32,768 |
| **M2** | Qwen3.8 27B（Q4_K_M） | 32,768 |
| **M4** | Ornith 1.5 35B A3B | 16,384 |

> 〔M3 说明〕《模型调参-分工.txt》原"窗口3 资料整理"用的也是 Qwen3.8，与 M2 同模型，故并入 M2、不单列 M3。模型槽定义源＝该调参文件，本表为其归因用途的镜像。

**〔格式演进史，均不改写历史提交〕**
- V1（≤09-12）：`<模型简写>-<日期>-<序号>`，如 `QWEN-20260912-A`——靠序号区分窗口，但序号无强制机制，09-13 两个千问窗口同署 `AI-001`＋`QWEN-20260913-A` 致 git 无法区分（**KZ-014**）。
- V2（09-13）：`W<窗口号>-<模型简写>-<日期>-<序号>`，窗口号前置为必填，解决 KZ-014。

- 过渡：V1／V2 的历史提交**保留不改写**（同 KZ-011 处置）。

- 用途：trailer 里写 Session，将来追查"哪个窗口、哪个模型改的"可精确定位。

## 五、git 身份配置约定

| 配置层 | 值 | 说明 |
|--------|----|------|
| 仓库本地 `user.name` | `zhiguanAI-agent` | **中性占位**，表示"AI 执行区"，不默认署任何具体 AI、更不署法师 |
| 仓库本地 `user.email` | `agent@zhiguanai.local` | 本地占位邮箱，非真实邮箱 |
| 每次提交 committer | `-c user.name='AI-00N·名称(模型)'` | 执行的 AI **显式指定自己**为 committer |
| 每次提交 author | `--author='内容归属人 <…>'` | 据"提交时确认"结果填法师或对应 AI |

**三条约束**：

1. **只改 `--local`，不动 `--global`**——避免影响法师机器上的其他仓库。
2. 仓库占位身份的存在的意义：若某次提交忘了显式指定 committer，会落到中性占位 `zhiguanAI-agent` 而非误署法师——**失败时退化为"身份待查"，而不是"错误归因到法师"**。
3. 本配置已由 AI-001 于 2026-09-12 设置（法师裁定五件一体推进即含此步），设置前后均验证。

```

Approved-by: 宗国法师 / 待审
Model: qwen3.8-max

Window: W3（制度与机动）
Errata: KZ-0NN（若涉订正）
```

> Session 格式见 §四（V3，2026-09-14 F1 裁定含模型槽）；`Window` 为冗余字段，便于不解析 Session 也能一眼看出窗口。
>
> **⚠️ 已知缺口（2026-09-14 发现，待法师裁定）**：M1–M4 全部是 **LM Studio 本地模型槽**，而云端模型（如本 AI 的 `qwen3.8-max`、以及 Copilot/GPT-5.6）**不在槽表内**。现行处置：云端窗口 Session 暂用 V2 格式 `W<窗口>-<模型简写>-<日期>-<序号>`（如本窗口今日的 `W3-QWEN-20260914-A`），**模型信息以 trailer 的 `Model` 字段为准**。是否给云端另设槽号（如 `MC`）请示法师——AI 不自行扩编。

**git 原生字段映射**：

- `--author` 填**内容归属人**（法师口述／手改 → 宗国法师；AI 撰写 → 对应 AI 身份）
- `committer` 为**执行提交的 AI**（来自 `-c user.name`）
- 其余四类信息（Author-Role／Proposal-by／Approved-by／Model／Session／Errata）走 **commit message trailer**（实测随 clone／push 自然传播，优于 git notes）

**类型词**（沿用项目既有 commit 习惯）：`docs`（文档／书稿）／`feat`（功能）／`fix`（修复）／`chore`（杂项）／`refactor`（重构）。

## 七、提交时确认流程（E3 乙，法师 2026-09-12 同意）

每次提交前，AI 走以下五步：

1. `git status` ＋ `git diff` **列出全部待提交变更**（文件级，涉关键内容则到行级）；
2. **逐项标注归因**：谁改的（法师口述／法师手改／AI 撰写／AI 整理）、哪个窗口、为什么改；
3. **列给法师确认**——这是"多问一轮"的代价，换来归因正确＋一次变更审查；
4. 法师确认后，按 §六模板提交，author／committer／trailer 据确认结果落；
5. **提交后核验**三字段是否按设计落地（`git log -1 --pretty=fuller` ＋ `%B` 读 trailer）。

> 副作用是好的：第 1–3 步等于每次提交都过一遍"这些变更是什么、是谁的"，能及早发现误改或他人并发改动（已两次撞见，详 §八）。

## 八、并发四纪律（E6）

项目已两次撞见"另一窗口在本 AI 工作期间改文件"（详方案 §4.2bis、§六quater），故立四条：

1. **改前先提交**：任何 AI 动手改文件前，先 `git status` 确认工作区干净；若有未提交变更，先处理（提交或报告），**不叠加**。
2. **改后即提交**：一轮改动完成立即提交，缩短工作区暴露时间。
3. **认领制**：同一时段一个文件只由一个窗口负责（可借飞书看板的"承担者"字段标注）。
4. **冲突停下报告**：发现工作区有**非自己产生**的变更，**停下报告，不覆盖**（与项目既有"删除／覆盖遇同名项先保留两边并询问"同一纪律）。

> 第 1、4 条是关键：它们把"静默覆盖"变成"显式停下"。多 AI 同写一个文件而无归因，是项目失控的最大风险（GPT 审议称为"冲突地狱"，本项目已实证）。
