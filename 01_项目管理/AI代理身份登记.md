> 建立日期：2026-09-12（宗国法师裁定"五件一体推进"后建立）
> 定位：归因体系的**身份基线**——《版本控制归因与 OneDrive 隔离方案》§四ter B 组件①，对应裁定 **E4（git 身份配置）＋ E7（身份登记表）＋ E3（提交时确认）＋ E6（并发纪律）** 四件的共同载体。

## 一、为什么需要这张表

2026-09-12 两个实验证明，归因不能靠"把 git 的 user.name 改一改"解决：

- **实验 1**：只把 user.name 改成 AI 身份后，提交一份**法师手改**的内容 → git 记录 `author=AI`，法师的改动被署成了 AI。
- **实验 2**：用同一个 user.name 让两个 AI 窗口分别提交 → 两次 `author` 完全相同，**无法区分是哪个模型、哪个窗口**。

结论：必须有**稳定的身份对照表**，让每次提交的 author（内容归属）、committer（执行 AI）、trailer（模型／窗口／依据）都有处可查、彼此能区分。本表即此对照。

## 四、会话编号规则（Session）

格式：**`<模型简写>-<日期YYYYMMDD>-<窗口序号>`**

- 例：`QWEN-20260912-A`
- 同一窗口同一天的多次提交，**共用一个 Session**
- 不同窗口即使是同一模型、同一天，也用**不同序号**（A／B／C…）
- 用途：trailer 里写 Session，将来追查"哪个窗口改的"可精确定位

## 五、git 身份配置约定

| 配置层 | 值 | 说明 |
|--------|----|------|
| 仓库本地 `user.name` | `zhiguanAI-agent` | **中性占位**，表示"AI 执行区"，不默认署任何具体 AI、更不署法师 |
| 仓库本地 `user.email` | `agent@zhiguanai.local` | 本地占位邮箱，非真实邮箱 |
| 每次提交 committer | `-c user.name='AI-00N·名称(模型)'` | 执行的 AI **显式指定自己**为 committer |
| 每次提交 author | `--author='内容归属人 <…>'` | 据"提交时确认"结果填法师或对应 AI |

**三条约束**：

1. **只改 `--local`，不动 `--global`**——避免影响法师机器上的其他仓库。
2. 仓库占位身份的存在的意义：若某次提交忘了显式指定 committer，会落到中性占位 `zhiguanAI-agent` 而非误署法师——**失败时退化为"身份待查"，而不是"错误归因到法师"**。
3. 本配置已由 AI-001 于 2026-09-12 设置（法师裁定五件一体推进即含此步），设置前后均验证。

## 六、commit 模板（与方案 §四ter D 一致）

```
<类型>(<范围>): <一句话摘要>

<为什么改：1-3 行>

Author-Role: 法师口述 / 法师手改 / AI撰写 / AI整理
Proposal-by: AI-00N
Approved-by: 宗国法师 / 待审
Model: qwen3.8-max
Session: QWEN-20260912-A
Errata: KZ-0NN（若涉订正）
```

**git 原生字段映射**：

- `--author` 填**内容归属人**（法师口述／手改 → 宗国法师；AI 撰写 → 对应 AI 身份）
- `committer` 为**执行提交的 AI**（来自 `-c user.name`）
- 其余四类信息（Author-Role／Proposal-by／Approved-by／Model／Session／Errata）走 **commit message trailer**（实测随 clone／push 自然传播，优于 git notes）

**类型词**（沿用项目既有 commit 习惯）：`docs`（文档／书稿）／`feat`（功能）／`fix`（修复）／`chore`（杂项）／`refactor`（重构）。

## 七、提交时确认流程（E3 乙，法师 2026-09-12 同意）

每次提交前，AI 走以下五步：

1. `git status` ＋ `git diff` **列出全部待提交变更**（文件级，涉关键内容则到行级）；
2. **逐项标注归因**：谁改的（法师口述／法师手改／AI 撰写／AI 整理）、哪个窗口、为什么改；
3. **列给法师确认**——这是"多问一轮"的代价，换来归因正确＋一次变更审查；
4. 法师确认后，按 §六模板提交，author／committer／trailer 据确认结果落；
5. **提交后核验**三字段是否按设计落地（`git log -1 --pretty=fuller` ＋ `%B` 读 trailer）。

> 副作用是好的：第 1–3 步等于每次提交都过一遍"这些变更是什么、是谁的"，能及早发现误改或他人并发改动（已两次撞见，详 §八）。

## 八、并发四纪律（E6）

项目已两次撞见"另一窗口在本 AI 工作期间改文件"（详方案 §4.2bis、§六quater），故立四条：

1. **改前先提交**：任何 AI 动手改文件前，先 `git status` 确认工作区干净；若有未提交变更，先处理（提交或报告），**不叠加**。
2. **改后即提交**：一轮改动完成立即提交，缩短工作区暴露时间。
3. **认领制**：同一时段一个文件只由一个窗口负责（可借飞书看板的"承担者"字段标注）。
4. **冲突停下报告**：发现工作区有**非自己产生**的变更，**停下报告，不覆盖**（与项目既有"删除／覆盖遇同名项先保留两边并询问"同一纪律）。

> 第 1、4 条是关键：它们把"静默覆盖"变成"显式停下"。多 AI 同写一个文件而无归因，是项目失控的最大风险（GPT 审议称为"冲突地狱"，本项目已实证）。

## 九、登记维护

- 新 AI 窗口加入 → 登记一行、分配新 ID（顺序递增不复用）；
- 本文件自身的变更，同样走 §七"提交时确认"；
- 与《书稿勘误与订正台账》分工：**台账记"文本改了什么、为什么"（订正语义）；本表记"谁在改、用什么身份改"（身份语义）；git 记"哪一行从什么变成什么"（字符级差异）**。三者互补，不互替。
