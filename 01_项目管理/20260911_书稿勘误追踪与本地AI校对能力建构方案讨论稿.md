## 一、问题诊断：三个被混在一起的子问题

法师的提问里含三个性质不同的子问题，混在一起会导致选错工具。拆开看：

**子问题 A：「我直接改了，AI 不知道」**
这是**变更可见性**问题。解决它需要的是版本控制或文件差异检测，**与 AI 无关**。任何一个字被改动，都要能被精确察觉（改了哪个文件、哪一行、从什么改成什么）。

**子问题 B：「AI 改完之后，要记录下来，后续做补充或修正」**
这是**变更台账**问题。解决它需要一个统一的订正登记处，把"谁在何时把什么改成了什么、依据是什么"落成可追溯的记录。项目已有雏形（术语校正对照表），但**散在 9 个文档里，没有单一台账**。

**子问题 C：「一键调用本地 AI 进行修正」＋「后续大量标注工作随时调整」**
这是**语义辅助**问题。这一层才真正需要 AI——批量检查同音字、术语一致性、引语与原件是否相符、风格是否统一。法师提到"大量标注工作"，说明这不是一次性需求，是长期产能问题。

**三者的依赖关系是单向的：C 建立在 B 上，B 建立在 A 上。**

如果跳过 A 直接做 C，会发生什么？法师改了文件，本地 AI 不知道哪里被改了，只能全文重扫；扫出问题后自动修改，**又因为没有 A，这次自动修改本身也不可见**——法师会失去对自己书稿的掌控。这是必须避免的路径。

所以本方案的施工顺序是 **A → B → C → D（一键入口）**，不可颠倒。

## 三、关键判断：您缺的不是本地 AI，是版本控制

法师的提问方向是"能否调用本地 AI"。但按 §一 的拆解，**子问题 A（我改了 AI 不知道）用 git 就完全解决，且成本接近零**；本地 AI 解决的是子问题 C，那是另一个问题。

这个判断有点反直觉，所以我把它讲透。

### 3.1 为什么 git 就够解决 A

法师在别编 06 里把"制成"改成"自成"并保存。此刻：

- **没有 git**：文件系统只知道"文件被写过"，最后修改时间变了。内容改了什么，无处可查。我必须重读全文、且必须记得原文才能比对——**而我不记得，因为我的上下文会清空**。这就是法师说的"AI 显然就不知道"。
- **有 git 且书稿已纳入**：执行 `git diff` 立即得到：

```
- > "要做成这种制成的因缘作用、事实的力量……"
+ > "要做成这种自成的因缘作用、事实的力量……"
```

精确到字符级，且**永久留存**。我不需要"记得"原文，git 记得。

这一层的能力，项目**已经具备**（git 已装、仓库已建、.gitignore 已设计），只差一次 `add` ＋ `commit`。

### 3.2 为什么本地 AI 不能替代 A

设想跳过 A，直接做"一键调用本地 AI 修正"：

1. 本地 AI 无从知道哪里被改过 → 只能全文重扫
2. 全文重扫 37.3 MB 文档（221 个 md/txt），即便只扫书稿也是数十万字 → 慢，且每次都要重跑
3. AI 扫出"可疑处"后自动修改 → **这次修改本身又不可见**（因为没有 A）
4. 法师失去对书稿的掌控：不知道 AI 改了什么、改了多少、依据是什么

第 3 点是致命的。它直接违反项目两条既有裁定：

- **判语 009**：反馈闭环定位"镜子非训练器"——镜子只照见，不代做
- **判语 013**：模型真值由数据与反馈交叉验证决定，AI 不自立法义

书稿的真值是法师定的。AI 自动改字，等于 AI 替法师定真值。**今天这个案例恰好证明**：如果我当时没问、直接把"制成"当成法师原话写进别编，那就是 AI 替法师定了真值，而且定错了。

### 3.3 那本地 AI 该干什么

它该干**镜子**的活：把可疑处照出来，交给法师判。具体三件：

1. **批量同音字／术语校对**：扫全稿，标出"这个词在这份文档里出现过 3 次、写法不一致"或"这个词与术语表不符"
2. **引语溯源核对**：书稿里所有〔法师原话〕标注的引语，逐条与逐字稿原件比对，标出用词差异（今天这个错字，这类检查能自动抓到）
3. **标注工作的语义辅助**：法师说"后续大量的标注工作都需要随时进行调整"——脑电数据标注涉及大量术语与状态描述，本地模型可做初筛，人做终审

这三件都是**提出候选、不自动落笔**。符合判语 009。

## 四、四层方案

按依赖顺序，每层独立可用、独立有价值，**可分层裁定、分层施工**。

### L1 · 变更可见（地基，零成本）

**做什么**：把书稿与项目文档纳入既有 git 仓库，提交基线；之后每次改动自动可查。

**具体动作**：
1. 复核并补充 `.gitignore`——**明确排除机密学员数据目录**（`02_修道班运营/`）、原始 EEG 数据、逐字稿原件是否纳入须法师裁定（它是 L1 素材层，纳入版本控制有利于溯源，但它是 147KB 的会议记录，含全部成员真名与内部讨论）
2. `git add` 书稿与项目文档目录（不含被排除项）
3. `git commit` 建立基线，提交信息注明"书稿纳入版本控制基线"
4. 约定提交节奏：**每次 AI 交付一轮产出即提交一次**；法师自行修改后，由 AI 在下次会话开始时提交（或法师双击一键脚本提交）

**成本**：约 30 分钟，零费用，无需安装任何东西。
**收益**：子问题 A 彻底解决。法师改任何字都可精确追溯，AI 不再依赖"记得原文"。
**风险**：GitHub 远程仓是**公开仓**（`github.com/dashucantian/zhiguanAI`）。**书稿一旦 commit 并 push 即公开**。故必须裁定：①书稿是否 push（建议**只本地 commit、不 push**，或建私有仓）②`.gitignore` 安全红线是否足够（已有 `*.pem`/`*.key` 等证书排除，但**没有学员数据目录排除**）。

> **这一条是本方案最高的风险项，须法师优先裁定。** 现状是远程仓已存在且公开，目前只有 168 个文件（以代码为主）被跟踪；若把书稿 add 进去又照常 push，L3 僧团事务与成员真名将进入公开互联网，且**即便日后删除也可能被缓存或索引**。

### L2 · 变更台账（低成本）

**做什么**：建单一勘误台账，把散在 9 处的订正记录归一。

**具体设计**（文件：`01_项目管理\书稿勘误与订正台账.md`，**不用下划线开头**，避开 `.gitignore` 的 `_*.md` 规则）：

|字段|说明|
|-|-|
|编号|订正序号，如 KZ-001|
|发现日期|绝对日期 YYYY-MM-DD|
|发现者|法师／AI／本地模型校对|
|错误类型|转写同音讹误／抄录错误／引用失实／术语不一致／事实不符／其他|
|错误原文|逐字记录|
|订正为|逐字记录|
|依据|法师口述／原件比对／实测／文档出处|
|影响落点|列出全部需同步的文件与行号|
|处置状态|已全量更正／部分更正／待裁定|

**首批入台账的内容**（已实测清点）：
- KZ-001「制成→自成」（本次，4 处已更正）
- 会议纪要附录对照表既有 5 条（老店→脑电、NeuraDock 六种误写、Pika→Pico 等）
- 本轮施工报出的两处事实不符（复现路径"两小时"宣称、第三章存档指向 006 号日志查无实据）
- 已留档的三次 AI 凭记忆出错（第五章记载）
- 判语 003／004 的修订注记

**成本**：约 1–2 小时（含把散落记录归集）。
**收益**：子问题 B 解决。一处订正、全项目可查；同类错误再犯时能立即比对历史。
**与既有架构的关系**：台账是**新增一个文件**，不是新增一套系统。它与飞书看板分工不同——看板管任务状态（ZG- 编号），台账管文本订正（KZ- 编号）。**不建议把台账放飞书**，因为它含 L3 内容原文，按隐私边界应留本机。

### L3 · 本地模型语义校对（中成本，须先验证）

**做什么**：启动 LM Studio 服务，写一个校对脚本，让本地模型扫书稿、标出可疑处，**只报告不修改**。

**三类检查任务**（按可行性排序）：

|任务|做法|可行性|
|-|-|-|
|①术语一致性|建术语表（NeuraDock／入照运融出／五相／三环／L1-L3 等），扫全稿比对写法|**高**——纯机械匹配，甚至不需要模型|
|②引语溯源|提取所有〔法师原话〕引语，与逐字稿原件逐条比对，标出用词差异|**高**——文本比对为主，模型只判"是否实质差异"|
|③同音字／语义可疑|模型通读，标出"此处用词与上下文义理矛盾"（如"制成"与"因缘作用"的自然生成义矛盾）|**未验证**——须实测本地 35B 模型的中文语感准确率|

**③ 必须先做小规模验证，不能承诺效果。** 验证方法：取已知答案的样本（会议纪要附录对照表 5 条＋本次"制成"＋人工植入的若干同音字错误），让本地模型盲扫，统计查全率与查准率。**若查准率过低（大量误报），法师会被噪声淹没，这一层就该降级或放弃。**

**模型选择建议**：按 09-05 实测，MoE 的 Qwen3.6-35B-A3B 速度最快（49.5 tok/s，开 MTP 69.4），适合批量扫描；Ornith-1.5-35B 在 09-10 评估中"最诚实"（不越线、不臆断），适合做"可疑处判定"这类需要克制而非发挥的任务。**建议双模型交叉**：MoE 跑量、Ornith 复核，两者都标出的才报给法师。这也符合判语 013 的交叉验证精神。

**成本**：脚本开发约 2–4 小时；验证约 1 小时；每次全稿扫描的运行时间待实测（37.3 MB 文档不可能全扫，须限定书稿范围，约 20 万字，估算数十分钟量级）。零费用、零出网。
**收益**：子问题 C 解决。批量校对与标注工作的产能瓶颈打开。
**风险**：①本地模型准确率未验证 ②误报过多会消耗法师审读时间 ③**模型可能"自作主张"改字**——必须在脚本层硬性禁止写入，只输出报告文件。

### L4 · 一键入口（轻量开发）

**做什么**：把 L1–L3 串成法师双击即用的入口。

**形态建议**（须法师裁定，见 §九）：

|方案|形态|优点|缺点|
|-|-|-|-|
|甲|独立 `.bat`（如 `书稿勘误检查.bat`）|双击即用，最简单；与项目既有"Muse脑电监测.bat"入口形态一致，法师熟悉|新增一个入口|
|乙|并入既有 Web 控制台，加一个"书稿校对"页|符合"统一架构不造冗余、不建平行入口"|控制台是脑电实验系统，书稿校对属另一域，并入可能造成职责混淆；且需改控制台代码（记忆载：控制台大改必过独立验收三维度≥4.5）|
|丙|不做入口，法师直接在对话里说一句"检查一下变更"|零开发|不是"一键"，且依赖会话在场|

**我的建议是甲**，理由：书稿域与脑电实验域职责不同，强行并入会污染控制台的单一职责；而 `.bat` 入口是法师已经习惯的形态，不算"平行入口"（那两个入口服务两个不同的域）。**但这与"不建平行入口"的既有约定有张力，须法师裁断。**

**一键脚本的动作序列**（甲方案）：
1. `git status` ＋ `git diff` → 检测法师改了哪些文件、哪些字
2. 把差异写入台账草稿（待法师确认后正式入账）
3. 若法师勾选"跑校对"→ 启动 lms server（若未启）→ 调本地模型扫改动涉及的文档 → 输出可疑处报告
4. 生成一份简报：本次变更 N 处、台账新增 M 条、模型标出可疑 K 处
5. **全程不自动修改任何书稿文件**

⚠️ `.gitignore` 当前忽略 `*.bat` 与 `*.ps1`，故入口脚本本身不会被版本控制。这可以接受（它是工具不是内容），但须注意脚本丢失无法从 git 恢复，建议另存一份副本。

## 五、本地 AI 校对的能力边界（诚实分层）

这一节回答"这类问题是不是可以用这种方式来解决"。**答案是：一部分能，一部分不能，必须分清。**

按"谁能判定对错"分三层：

### 第一层：机械可检（本地 AI 甚至不需要，脚本即可，准确率接近 100%）

- 术语写法不一致（同一术语多种写法）
- 引语与逐字稿原件的字面差异
- 已登记在册的历史错误再犯（比对台账）
- 跨文档引用失效（指向的文件或章节不存在）
- 数字与日期格式不一致

**今天这个案例属于第一层**——一旦"自成"进了台账与术语表，"制成"再出现就会被机械捕获。

### 第二层：语义需判（本地 AI 能做，但准确率未验证）

- 用词与上下文义理矛盾（"制成"的人为制造义 vs"因缘作用"的自然生成义）
- 逻辑跳跃、前后不一致
- 文风偏离（如某段突然变成方案文档腔，违反"人读化"要求）
- 疑似缺字、多字、语序错乱

**这一层是本地模型的真正用武之地，但必须先按 §四 L3 做验证再定取舍。**

### 第三层：唯法师知（任何 AI 都做不到）

- 法师口述原意（如"虚拟禅堂"那段，原话未落档，AI 无法凭转述判定）
- 义理分寸（如胎藏界喻的层级区分，法师明示"AI 不引申"）
- 是否愿意公开某段内容（L1/L2/L3 定级）
- 对当事人的处置（如第四章温伟东分歧段的知情确认）

**这一层必须由法师把关，AI 只能提出待决清单。** 本方案的所有产出都应止步于第二层，第三层一律上交。

## 九、风险与明确不做的事

**风险**

1. **公开仓泄露（最高）**：见 D1。远程仓已存在且公开，若 add 后照常 push，L3 内容进入互联网。**在 D1 裁定前，本方案不执行任何 git add／commit／push。**
2. **本地模型误报淹没**：若第二层检查查准率低，法师要审的"可疑处"比真错还多，反而增加负担。故 P3 验证不可跳过，且设定放弃阈值（建议查准率低于 70% 即降级为只做第一层机械检查）。
3. **AI 自动改字**：一旦发生即违反判语 009／013，且法师失去掌控。**脚本层硬性禁止写入书稿**，只允许输出报告文件与台账草稿。
4. **OneDrive 与 git 双写冲突**：项目在 OneDrive 同步目录下，若 OneDrive 进程运行时 git 正在写入，可能产生同步冲突或 `.git` 目录被部分同步。**建议 `.git` 目录加入 OneDrive 排除，或施工时确认 OneDrive 未运行**（实测当前未运行）。这一条须实测验证，本方案未验证。
5. **台账与文档内订正注记双轨**：台账是新增机制，各文档内已有订正注记（如本次别编 06 的注记）。两者须明确分工：**文档内注记服务读者（就地可见），台账服务检索（全局可查）**，不可互相替代，也不宜要求文档内注记全部迁移。

**明确不做**

- 不做全量操作监控、不录屏、不记键盘（09-06 已否决，四条依据仍成立）
- 不自建多智能体编排框架
- 不让 AI 自动修改书稿任何一字
- 不在 D1 裁定前执行任何 git 写操作
- 不把台账或书稿送上云端 AI 服务（GPT 验收包另有一套授权流程，且已化名）
- 不触碰 `02_修道班运营\机密-学员数据\`（本轮已发生两次检索越线，教训在册）
