## 三、三个发现

### 发现一 🔴 **每 60 秒一次的采集停顿——是我们的增量快照，不是设备**

**现象**：34 处断口的时间分布**不是随机的**——

```
18.0分/0.6s  19.0分/0.6s  20.0分/0.6s  …  44.7分/2.0s  45.1分/1.5s  …  48.1分/1.5s
每 1.0 分钟一处；时长从 0.6s 单调涨到 1.5s
```

**证据链（三重吻合，非推测）**：
1. **周期**：`QC_SNAPSHOT_INTERVAL_S` 默认 **60**（`console_server.py:209`）⇒ 与"每 60 秒一处"一致；
2. **位置**：`snapshot()` 在**实时推流主循环里同步调用**（`console_server.py:801-806`），注释自写"内部自带间隔判断与**持锁**"；
3. **代价随会话增长**：`muse_local_server.py:714-731` 在 **`with self.lock:` 内**把 `self.eeg_all[ch]`（**Python list**，`行369` 建为 `[]`）逐元素转成 numpy —— 48.5 分钟时约 **1000 万次元素转换**（eeg 一遍＋`eeg_pre_filter` 再一遍＋时间戳），**代价 ∝ 会话长度** ⇒ 与 0.6→1.5s 的单调增长一致；
4. **同一把锁（最后一环，已核）**：`self.lock`（`muse_local_server.py:358`）**既是采集入口 `add_eeg`（行445）的锁，也是 `snapshot`（行714）的锁** ⇒ 快照持锁期间**采集确实进不来**。

⇒ **结论（确证，四重吻合）**：这是**我们自己的 P0-4 增量快照在采集路径上持锁做全量拷贝**造成的周期性阻塞；
**会话越长越严重**。**那个"为了保护数据"的功能，正在损伤数据。**
断口合计 35.7 s，而实测真丢 0.66% ⇒ 一部分被 TCP 缓冲补齐、一部分真丢。

**建议（不改判据，只改实现；候裁）** —— 任选其一或组合：
- **甲**：锁内只做**引用级快照**（`list.copy()`＝C 级指针拷贝，毫秒级），转换与写盘移出锁外；
- **乙**：`eeg_all` 改**预分配 numpy 数组**，快照用 `arr[:n].copy()`（C 级 memcpy）；
- **丙**：快照移**独立线程/进程**，采集路径完全不经手；
- **丁**：间隔 60s → 300s（并把 `QC_SNAPSHOT_INTERVAL_S` 暴露到界面）。

⚠ 另有一处**待查**：真丢的样本是"厂商 APP 因我们读得慢而丢"还是"我们解析时丢"——需看
receiver 的 `bad_line_count` / `malformed_lines`（**这两个计数目前不进存档**，无法回看）。

这正是"自评 vs 客观"交叉核对的价值所在（该不一致**应当保留**，不要事后改写登记）。

**建议**：真机流程里把 **Oz 单通道的接触**列为下一次采集的开场检查项（`T2 判据`已有 std 量级口径，
但本次全通道 std 都高于 3–30 µV 的"安静态"区间 ⇒ 见发现三的张力）。

### 发现三 ⚠ **`OUTLIER_UV = 2000 µV` 是"整行丢弃"，且存档最大值正好贴着它——待查**

**旁证**：滤波前原始列的全局最大 = **1997.4 µV**，而 `neuradock_receiver.OUTLIER_UV = 100 × 20 = 2000`。
**贴得可疑**。若该阈值确在丢弃，则：
- 超限**整行**（含 5 组×7 通道）被丢弃 ⇒ **一个通道的瞬变会让七个通道同时缺 5 个样本**；
- 对多通道同步分析（wPLI 连接、地形图）是**系统性缺口**，且**大幅值段被系统性削掉**（选择偏差）。

**本轮不下结论**（无法回看 `bad_line_count`）。**待查**：加一处计数入 meta，下次即可对账。

### 附：`clean_ratio = 1.0` 与"幅值偏高"的张力（**只指出，不改判据**）

全通道原始列 std 中位 **70.2 µV**（典型静息 10–20 µV），`|x|>100µV` 占 **3.34%**，
而 `clean_ratio = 1.0`（577 段零噪声段）。
⇒ **`clean_ratio` 高 ≠ 信号安静**：它按频段噪声判段，对"整体幅值偏高、瞬变多"不敏感。
