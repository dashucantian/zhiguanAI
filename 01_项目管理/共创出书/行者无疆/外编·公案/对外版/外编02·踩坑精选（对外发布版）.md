## 一、WebXR 安全上下文——HTTP 下浏览器隐藏 VR 能力

### 现象（用户视角，原话）

- 第一轮："Pico 上这个网址打不开啊，显示已离线"
- 第二轮："已经打开了网页，看到了跟电脑上一样的场景，但是无法进入 VR。跟电脑上显示的一样，提示'当前浏览器不支持，请用 Pico 浏览器打开本页'。为什么会这样？"

### 根因（多个坑容易混为一谈，这里其实只有一个）

WebXR 规范规定：`navigator.xr`（进入 VR 的能力）**只在"安全上下文"里暴露**——即 HTTPS 或本机 localhost。

- 电脑上用 `localhost:8777` 打开 → 算安全上下文 → VR 按钮可用
- 头显走 `http://192.168.1.100:8777` → 纯 HTTP 局域网地址**不算**安全上下文 → 浏览器直接把 WebXR 能力藏掉，`navigator.xr` 为 undefined

所以页面报"不支持"，**不是头显浏览器不行，换任何浏览器走 HTTP 都一样**。电脑本地测不出来，一到头显就暴露——这正是"涉及 XR 的功能必须真机验证"的铁律来源。

〔AI 理解〕报错信息的措辞在这里是**误导性的**："当前浏览器不支持"指向的是浏览器能力，而真实原因是传输协议。用户第二轮的原话里有一句关键信息——"跟电脑上显示的一样"，这句说明页面本身渲染正常、只有 VR 入口失效，据此就能把范围收窄到 `navigator.xr` 是否存在，而不必怀疑页面代码。

### 解法

给控制台加 HTTPS 服务（自签证书，局域网自用足够），头显改走 https：

1. 新增证书生成模块：用 `cryptography` **幂等**生成自签证书至资产目录（cert.pem＋key.pem），有效期 825 天，**已存在则跳过**
2. 服务端改双端口：**8777 HTTP（电脑控制台照旧）＋ 8778 HTTPS（头显进 VR 必经）**，同一 app、`asyncio.gather` 并行 serve
3. 页面 ws／wss 随协议自适应：
   ```javascript
   const wsURL = `${location.protocol === 'https:' ? 'wss' : 'ws'}://${location.host}/ws/vr`
   ```
4. 头显首次访问 https 会弹"证书不受信任"，选"高级 → 继续访问"

### 排障顺序（可复用）

看到"无法进入 VR／`navigator.xr` 不存在"，先按这个顺序排，**不要一上来就改代码**：

1. 先确认页面**是否连到了正确的新服务**（见第二坑，端口占用会让新代码根本没生效）
2. 再确认**协议是不是 HTTPS**（这是本坑的根因，最常见）
3. 再确认设备与电脑**是否同一局域网段**
4. 最后才怀疑浏览器／引擎本身

### 教训

**本机 localhost 正常 ≠ 局域网正常 ≠ 头显浏览器正常。三者是三个不同的运行环境，其中头显浏览器还多一层 WebXR 安全上下文限制。安全上下文这类约束在文档里一行带过，但在真机上是决定性的——HTTPS 不是"锦上添花"，是 WebXR 的入场券。**

> 关联判语：《VR 首落地走 WebXR》（见外编 01）。已在本机 Pico 4 Ultra 真机验证通过。

## 二、端口被旧进程占用，导致"新代码没生效"

### 现象（用户视角，原话）

- "Pico 上这个网址打不开啊，显示已离线"
- 重启批处理后，控制台窗口出现红字 `[Errno 10048] error while attempting to bind on address ('0.0.0.0', 8777)`

### 根因（表象是网络问题，真相是进程问题）

昨天启动的旧版控制台进程一直没关，**独占 8777 端口**，而且只监听 `127.0.0.1`（本机回环）。今天重启批处理时：

- 新服务想绑 8777 → 端口已被占 → 抛 ERROR 10048（地址已在使用）→ **新进程启动失败**
- 头显从局域网连过来 → 连到的是那个**旧进程**（旧代码没有 VR 功能、且只听回环地址）→ 表现为"已离线"

**关键认知**：`127.0.0.1`（只监听本机）和 `0.0.0.0`（监听所有网卡）是两回事。旧代码只听 `127.0.0.1`，局域网设备根本连不进来；新代码已改为 `0.0.0.0`，但**新代码没跑起来，等于没用**。

### 解法

1. 查谁占了端口：
   ```powershell
   Get-NetTCPConnection -LocalPort 8777 -State Listen
   ```
   看 `OwningProcess`
2. **确认该进程空闲、无进行中的采集会话**（查监测与实验状态接口），避免误杀正在采数据的会话
3. 终止旧进程：`Stop-Process -Id <pid> -Force`
4. 确认端口释放后，重新用批处理启动新服务
5. **验证监听地址变成 `0.0.0.0:8777` 而非 `127.0.0.1:8777`**

### 排障顺序（可复用）

局域网设备"连不上／已离线"，**先查端口与进程，再查网络**：

1. 服务是否在跑、监听的是 `0.0.0.0` 还是 `127.0.0.1`（**只听回环＝局域网必连不上**）
2. 端口是否被旧进程占用（新代码可能根本没启动成功）
3. 防火墙是否放行（本项目已放行 Python 3.12 全端口含 Public，不是障碍）
4. 最后才查 Wi-Fi 网段是否互通

### 教训

**"重启一下"不等于"新代码生效了"。如果旧进程没退干净，重启会静默失败（新进程绑不上端口直接退出），而你看到的还是旧服务——表象完全正常，行为全是旧的。每次改完服务端代码，要验证的不只是"服务在跑"，而是"跑的是新代码、监听在所有网卡上"。**

〔AI 理解〕这一坑与第一坑在时间上是连着的：第一轮"已离线"其实是本坑（旧进程占端口），修掉之后才暴露出第一坑（HTTP 不是安全上下文）。**两个坑的现象描述几乎一样，根因完全不同**——这正是第一坑排障顺序把"先确认连到了正确的新服务"放在第 1 位的原因。

解法第 2 步（先确认无进行中的采集会话再杀进程）不是谨慎，是必需：**杀错进程的代价是一整段数据。**

## 三、蓝牙数据流静默断连，闭环实验零决策即失败

### 现象（用户视角）

法师启动闭环实验，实验很快结束但没有产出数据。后台记录：

```
模式：真机（BLED112 自动）
tag：closedloop
n_decisions：0
error：数据流静默 18 秒（疑似蓝牙断开）
data_path：null
```

实验"跑起来了"，却一个决策周期都没完成，等于空转失败。

### 根因

Windows 蓝牙栈在长时间流式传输下出现**环境性静默断连**——**连接看起来还在，但数据流停了**。系统的看门狗检测到 18 秒无新数据后，判定数据源失效并中止实验。

这不是孤例：项目早期就发生过一次系统蓝牙栈环境性故障导致连接失败，当时定性为"环境性故障"。**蓝牙在 Windows 上的稳定性是本项目反复出现的卡点。**

### 解法

**短期（恢复当次实验）**：

1. 头环断电重连：关电源、重新开机、指示灯亮后再启动实验
2. 确认头环**未被其他设备（手机 App 等）占用蓝牙配对**
3. 必要时重启本机蓝牙服务或重插外置蓝牙适配器

**长期（架构层面）**：

- 闭环实验已有看门狗：静默超时即中止并记录错误，**不会无限空转**
- **静默断连自动重连**：看门狗判定静默后不再直接终止，而是委托自动重建连接会话（最多 3 次、间隔 5 秒，数据恢复即重置预算）；预算用尽才走原"自动保存＋告警"路径。**重连期间不保存、不中止会话，已采数据不受影响。**内置蓝牙与外置适配器两条路径均接入（扫描失败／连接失败／流中断同样委托重连）
- **外置适配器写语义修复**：其 GATT 写方法原把 response 语义反转（默认等待写响应），而该头环控制特征不支持写响应，导致握手首条指令超时、"连上但零数据流"。**现统一用无应答写命令**
- **串口释放**：会话退出时释放串口，避免重连或下次启动时适配器被占用
- 真机长时程稳定性排查已列为独立任务，目标是"连续 30 分钟无静默断连"
- **数据出口已支持模拟源回放**：用已入库的真机数据做离线回放测试，使映射参数迭代不再依赖蓝牙实时连接

### 排障顺序（可复用）

实验"跑了但没数据／`n_decisions=0`"，按这个顺序查：

1. 先看错误信息里的**静默时长**——有"数据流静默 N 秒"字样，基本就是蓝牙断连，**不是算法问题**
2. 查头环是否被其他设备占用配对
3. 查外置适配器／蓝牙驱动状态
4. **最后才怀疑信号处理或闭环逻辑**（在数据流本身断了的情况下，下游逻辑没机会运行）

### 教训

**画面再美，数据断流即失效。视觉闭环的前置条件是数据链路的长时程稳定，而不是渲染效果。蓝牙在 Windows 上的稳定性是必须正视的工程风险，不能假设"连上了就一直连着"。**

〔AI 理解〕最后一条解法（离线回放）价值超出本坑范围：**它把"映射逻辑调试"和"蓝牙稳定性"两个问题解耦**，不必每次都赌蓝牙不断。

任何依赖不稳定外部数据源的开发，都值得先建一条回放通道。否则每次调试都在同时验证两件事，出了错也分不清是哪件。

## 四、凭假设推断算力，把统一内存机误判成"要买显卡"

### 现象

某日的调研报告里，本地大模型部署门槛被写成"需要 24GB 显存的 RTX 3090／4090"，并据此把 **GPU 采购列为隐性成本**，暗示可能要花钱买显卡。

次日实测本机配置后，**这个假设整个不成立**。

### 根因（AI 侧的方法错误，不是技术难题）

报告沿用了"本地大模型＝需要大显存 N 卡"的通用印象，**没有实测本机**就下了结论。实际本机是：

| 项目 | 实况 |
|------|------|
| 处理器 | AMD Ryzen AI MAX+ 395（Strix Halo，16 核 32 线程） |
| 机型 | ASUS ROG Flow Z13 |
| 内存 | 约 64GB LPDDR5X **统一内存**（CPU 与 GPU 共享同一内存池） |
| 显卡 | Radeon 8060S 核显，**无 NVIDIA 独显** |

统一内存架构下**根本不存在"显存不够要卸载到内存"的问题**，GPU 可直接访问全部权重——**不需要买任何显卡**。

更深的教训是：这台机器的真正瓶颈不是显存容量，而是**内存带宽**（约 215–256 GB/s）。带宽受限机器上，决定推理速度的是每生成一个字真正参与计算的**激活参数量**，而非总参数量。所以 MoE 架构（激活 3B）在这台机器上反而比 Dense 的 27B 级模型快 2–6 倍——**这个反直觉结论，只有实测本机、理解其架构特性才能得出。**

### 解法

1. 任何"本机能不能跑 X"的判断，**先实测本机配置**再说：
   ```powershell
   Get-CimInstance Win32_Processor
   Get-CimInstance Win32_ComputerSystem
   Get-CimInstance Win32_VideoController
   ```
2. **区分架构类型**：独显机看显存容量，统一内存机（Apple Silicon、AMD Strix Halo）看内存总量与带宽
3. 推理速度找**同平台实测数据**（如 Strix Halo 的 llama.cpp benchmark），**不要套用 N 卡数据**

### 排障顺序（可复用）

涉及"本机能否跑某模型"时：

1. 先实测本机 CPU／GPU／内存／**架构类型（独显还是统一内存）**
2. 找**同架构平台**的实测速度数据，而非泛泛的"官方推荐配置"
3. 再判断模型量化后体积能否放进可用内存
4. 最后才给结论

### 教训

**不要凭通用印象推断特定机器的能力。**"本地大模型要大显存 N 卡"是独显时代的经验，套到统一内存机上就全错。**一次没实测的假设，差点让法师白花钱买显卡、还差点选错模型架构。**凡是涉及"本机能不能跑"，实测永远优先于推断——**这是 AI 助理最该守的纪律，因为它最容易拿训练数据里的通用印象冒充对本机的判断。**

〔AI 理解〕这一坑与其余五坑性质不同：**其余五坑是技术难题，这一坑是 AI 的方法错误。**它被收进外编，是因为它对"人机协作"这件事的普遍价值高于任何一条具体技术经验：

AI 的知识来自训练数据里的通用分布，而"你这台机器"是一个具体个案。**通用印象在个案上失效时，AI 往往察觉不到**——因为它的输出看起来同样自信、同样有依据。

所以这一坑的教训被固化成了项目的一条纪律（正编第五章第七节）：**凡引用其他文档的"当前状态／剩余项／计数"，必须数实际条目或检索核实，不采信文档自报。**同一条纪律，在算力判断上是"先实测本机"，在文档引用上是"先数条目"。

> 关联判语：《MoE 优于 Dense（带宽受限）》（见外编 01）——那张卡的正确结论，来自本坑这次错误推断被实测推翻。

## 五、PowerShell 5.1 引号吞噬，导致 CLI 参数传递失败

### 现象（用户视角，原话）

调用云端多维表格 API 时，命令行报错：

```powershell
some-cli base +record-batch-create --base-token ... --table-id ... --records '[{"fields":{"任务名":"示例任务：初始化项目仓库"}}]'
```

报错信息：`JSON parse error at position 1: expected '{' but got '['`

**看起来是 JSON 格式错误，但实际上 JSON 本身没问题**——问题出在 PowerShell 5.1 对引号的处理。

### 根因

PowerShell 5.1 在将参数传递给外部命令（如 Node.js 编写的 CLI）时，会**吞噬外层引号**，导致：

- 你写的：`'[{"fields":...}]'`（单引号包裹的 JSON 数组）
- PowerShell 传给 CLI 的：`[{fields:...}]`（单引号被去掉，**JSON 键名的双引号也被去掉**）
- CLI 收到的：**非法 JSON**

这是 Windows PowerShell 5.1 的已知行为，**与 CLI 工具本身无关**。

### 解法

**用文件传递 JSON 参数**，避免命令行引号问题：

1. 将 JSON 写入临时文件：
   ```powershell
   $json = '[{"fields":{"任务名":"示例任务"}}]'
   $json | Out-File -FilePath "$env:TEMP\payload.json" -Encoding utf8
   ```
2. 用 `@` 符号引用文件：
   ```powershell
   some-cli base +record-batch-create --base-token ... --table-id ... --records "@$env:TEMP\payload.json"
   ```
3. 用完后删除临时文件：
   ```powershell
   Remove-Item "$env:TEMP\payload.json"
   ```

### 排障顺序（可复用）

调用外部 CLI 工具传 JSON 参数时：

1. 先检查 JSON 本身是否合法（用 `ConvertFrom-Json` 测试）
2. **如果 JSON 合法但仍报错，怀疑 PowerShell 引号问题**
3. 改用文件传递（`@文件路径`）
4. 验证文件内容是否正确（用 `Get-Content` 查看）

### 教训

**Windows 环境下，命令行参数传递复杂 JSON 时，优先用文件而非内联字符串。**这是 PowerShell 5.1 的固有限制，不是 bug，但确实容易踩坑。文件传递虽然多一步，但**更可靠、更易调试**（可以直接查看文件内容）。

这个坑不只影响某一个 CLI，**任何需要传 JSON 的外部命令都可能遇到**。记住这个模式：`Out-File` → `@文件路径` → `Remove-Item`。

〔AI 理解〕排障顺序第 1、2 步的组合是本坑最实用的部分：**先用 `ConvertFrom-Json` 自证 JSON 合法**。这一步把问题一分为二——JSON 本身错了，和 JSON 在传递途中被改坏了，两者的修法完全不同，但报错信息长得一样。

第六坑里生成 SSH 密钥时也踩到同一个坑（`ssh-keygen -N ""` 的空密码参数被引号吞噬），当时同样改用脚本文件执行。**同一个坑在同一天踩两次，说明它不是偶发失误，是环境特性。**

## 六、GitHub HTTPS(443) 被阻断，git push 超时——改走 SSH over 443

### 现象（用户视角，原话）

- "https://github.com/xxxx/xxxx.git 显示 404 啊！"
- "仓库好了，本地 git 可以用了吗？"

AI 侧观察到的错误：

```
fatal: unable to access 'https://github.com/.../....git/':
Recv failure: Connection was reset
fatal: unable to access '...': Failed to connect to github.com:443 after 21052 ms
```

push 命令挂起直至超时（120 秒），重试三次均失败。

### 根因（两个独立问题叠加，容易混为一谈）

**问题一：404 —— 远程仓库根本没创建。**

上一轮只执行了 `git remote add origin <url>`（登记远程地址），但**既没在 GitHub 上建仓库、也没 push**。`remote add` 只是写本地配置，**不会在远端创建任何东西**。所以访问那个 URL 就是 404。

**问题二：push 超时 —— 本机到 github.com:443 被阻断。**

这是国内网络访问 GitHub 的常见情况。诊断证据：

| 测试项 | 结果 |
|--------|------|
| DNS 解析 github.com | 正常 |
| github.com:443 (HTTPS) | **连不上**（TcpTestSucceeded=False） |
| 国内站点:443（**对照组**） | 正常 |
| github.com:22 (SSH) | 通 |
| ssh.github.com:443 (SSH over 443) | 通 |
| git 认证（credential.helper） | 已就绪（manager） |
| 本地仓库 | 已初始化，1 个提交在 master |

**DNS 能解析、国内站点 443 通、唯独 GitHub 443 不通 → 不是本机网络坏了，是到 GitHub 的 HTTPS 通道被阻断。认证和 git 配置都没问题，纯网络层。**

### 解法

改走 SSH 协议，并让 SSH 走 443 端口（`ssh.github.com:443` 实测通，**即使将来 22 也被阻断仍能走**）：

1. **生成 SSH 密钥**（ed25519，空密码便于自动化）：
   ```bash
   ssh-keygen -t ed25519 -C "your_email" -f ~/.ssh/id_ed25519 -N ""
   ```
   **注意**：在 PowerShell 里直接跑 `ssh-keygen -N ""` 会因引号被吞而失败，改用 bash 脚本文件执行（**见第五坑**）。
2. **配置 SSH 走 443**，写入 `~/.ssh/config`：
   ```
   Host github.com
     HostName ssh.github.com
     Port 443
     User git
   ```
3. **把公钥加到 GitHub**：仓库平台的 SSH key 设置页（**这一步必须用户本人做，AI 无法代登录**）
4. **远程地址从 HTTPS 改为 SSH**：
   ```bash
   git remote set-url origin git@github.com:<user>/<repo>.git
   ```
5. **push**（首次用 accept-new 自动信任主机指纹）：
   ```bash
   GIT_SSH_COMMAND="ssh -o StrictHostKeyChecking=accept-new" git push -u origin master
   ```

### 排障顺序（可复用）

git push 超时／连接被重置，**先分清是"远程没建"还是"网络不通"**：

1. 先 `git ls-remote origin`：若报 404／repository not found → **远程仓库没建**，去平台建空仓库（**不要**勾 README／.gitignore／license，否则与本地冲突）
2. 若报 Connection reset／Could not connect:443 → 测端口连通性：
   ```powershell
   Test-NetConnection github.com -Port 443
   Test-NetConnection github.com -Port 22
   Test-NetConnection ssh.github.com -Port 443
   ```
   **用一个国内站点（如 baidu:443）作对照，确认是不是本机整体断网**
3. 443 不通但 SSH 通 → 改 SSH 协议（本坑解法）
4. 全都不通 → 本机网络／防火墙问题，或需要代理

**不要一上来就重装 git 或改认证**——认证（`credential.helper=manager`）和 git 本身大概率没问题。

### 教训

1. **`git remote add` ≠ 创建远程仓库**。它只写本地配置。远程仓库必须先在平台上建好，push 才有目标。**这是新手最容易误解的一步。**
2. **国内访问 GitHub，HTTPS(443) 经常不稳定，SSH 更可靠**。而且要让 SSH 也走 443（`ssh.github.com:443`），因为 22 端口在某些网络下也会被阻断。**一次配好，长期受益。**
3. **诊断网络问题要有对照组**。测 GitHub 443 不通时，同时测一个国内站点 443——通了就说明不是本机断网，而是到特定目标的通道问题。**没有对照，容易误判成"我网断了"或"git 坏了"。**
4. **push 超时要设 `GIT_TERMINAL_PROMPT=0`**，否则 git 会挂在等待输入凭据上，表现为"卡死"而非"报错"，更难排查。

〔AI 理解〕教训第 3 条"要有对照组"是六篇踩坑里最能脱离本场景使用的一条。它的实质是：**单一测试结果不携带信息，差异才携带信息。**"443 不通"本身说明不了任何事——可能是本机断网、可能是 DNS、可能是对方封禁、可能是本地防火墙。加上一个对照组，四种可能被一次测试区分开。

本坑的现象里还有一处值得注意：用户报的是"显示 404"，AI 侧看到的是"connection reset"。**两个人看到的是两个不同的问题**（远程没建／443 被阻），但被当成了同一件事在排查。这也是为什么根因段要写"两个独立问题叠加，容易混为一谈"。

## 附 · 两篇专业向备查（未收入本书）

**未收录理由**：两篇高度依赖具体硬件型号、库版本与驱动栈，自足性不足（须具备 BLE 协议栈与特定适配器背景才能读懂），不符合外编收录标准第 1 条。

**但其方法论具有普遍价值，摘录于此**：

**附一（第三方库在 Windows WinRT 上发现不了设备，改走"既有采集层 → LSL"代理挂载）**

- 现象分两层：第一层设备发现失败（`Failed to find Muse Device`），而同一时刻另一个 BLE 库能正常扫到该设备；第二层（把发现超时从 6 秒放宽到 30 秒后）**连上了但零数据**——`get_board_data_count()` 恒为 0。
- 可迁移的教训：**"扫得到"与"连得上"与"有数据"是三个独立状态，任一失败都会表现为"设备不工作"。**排查时须逐层定位到底卡在哪一状态，而不是笼统重试。
- 可迁移的解法思路：当第三方库的设备发现层与本机蓝牙栈不兼容时，**不必放弃该库的分析能力**——用已验证可通的采集层拿数据，再通过标准协议（LSL）把数据喂给它，即"代理挂载"。

**附二（外置适配器扫得到头环却连不上，L4 connect 超时）**

- 价值在**分层诊断法**：把连接过程拆成 L1 串口发现 → L2 后端启动 → L3 扫描 → L4 发起连接 → L5–L8 特征枚举／订阅／握手／收包，逐层测试并记录结果，最终定位到卡在 L4。
- 配套做了**三重排除**（都不是失败原因）：直连模式（跳过扫描，适配器状态最干净）仍失败；放宽连接参数＋超时加到 30 秒仍失败；占用检查确认设备未被任何其他进程连接。
- 关键现象：**同一只头环用电脑内置适配器能正常连接、波形正常；换外置适配器则不通。**这个对照直接排除了头环本身的问题。
- 可迁移的教训：**分层诊断＋对照组，能把"连不上"这种笼统故障定位到具体一层。**三重排除的价值在于它把"可能是 X"逐条变成"确认不是 X"，剩下的即使没有正面证据，范围也已收窄到可处置。

〔AI 理解〕这两篇未收入正文，但它们的**方法**（分层诊断、对照组、三重排除）与第六坑的教训第 3 条是同一条：**用结构化的排除代替笼统的重试。**
