# 外编 04 · 复现路径（二）：把第二种脑电设备接入既有采集架构

> 状态：L3 内部草稿（2026-09-11 首稿）；待宗国法师审定后升 L1
> 收录方式：**据案例库《复现路径 002》全文收入**，技术内容（架构原则、grep 清单、接口契约、代码、五个工程点、两级自测、失败模式表、验收清单、里程碑）**一字未削**；所脱敏者为内部代码路径、厂商名与仓库名、提交哈希、内部报告文件名。
> **重要前提**：本篇同外编 03，**不是从零入门指南**，而是**架构改造指南**——目标读者须已有一套"单一设备＋单一入口"的采集系统。
> **本篇的适用面比标题宽**：它讲的其实是"**如何把单设备假设从一套系统里逐层剥离**"。任何做多设备／多数据源适配的项目都能用，不限于脑电。

---

> **目标读者**：已有一套"单一设备＋单一入口"的数据采集系统（如本项目的 Muse＋Web 控制台），现在拿到第二种设备（任何带 TCP 数据服务的采集工作站），想把它接进**同一个后端、同一个实验流程、同一个前端**，而不是另起炉灶写一套平行系统。
> **前置条件**：
> - 现有系统有一条清晰的数据通路：设备 → 接收器 → 环形缓冲 → 分析／保存／前端广播
> - 新设备能对外提供数据流（TCP／串口／LSL 任一均可，本卡以 TCP 为例）
> - 具备 Python 与一点点前端（HTML／JS）能力
>
> **预计耗时**：2–3 天（协议明确时）；若厂商协议要靠逆向，另加 1–2 天
> **难度**：中等。**真正的难点不在"收数据"，而在把单设备假设从系统里逐层剥离，以及用可复现的自测替代真机。**

## 第 0 步：先守住架构原则（半天，最重要）

**本项目遵守的约束**：新设备一律并入既有单一硬件层与唯一入口，**不开平行采集脚本、不加第二个控制台**。这条原则来自项目自身的"统一架构不造冗余"纪律。

它决定了后面所有技术选择：**接收器必须与既有接收器同接口、缓冲必须参数化而不是复制一份七通道版、前端必须按数据渲染而不是按设备写死。**

**动手前先做一件事：找全"单设备假设"的藏身点。**在代码库里 grep 通道名和采样率常量，本项目扫出四类：

```bash
grep -n "TP9\|CHANNELS\|SFREQ" **/*.py **/*.html
```

| 藏身点 | 表现 | 处理 |
|--------|------|------|
| 缓冲层常量 | `CHANNELS = ["TP9",...]`、`SFREQ = 256` | 改为构造参数（**缺省值＝原值**） |
| 会话／实验层 | 波形循环 `for ch in CHANNELS`、样本数 `len(eeg[CHANNELS[0]])` | 改读 `buffer.channels / buffer.n_ch` |
| 前端 | 图例、画布行数、通道读数写死 4 通道 | 改为**按帧数据的键动态渲染** |
| 保存层 | npz／报告的通道列表 | 由缓冲携带，**禁止二次推断** |

**判据**：改造完成后，跑一次旧设备的完整模拟，**产出与改造前逐字节一致**——这证明"缺省行为不变"，是后续一切的地基。

〔AI 理解〕这一步是全篇最容易被跳过、也最不该跳过的一步。**多数多设备改造失败不是因为新设备接不上，是因为旧设备被改坏了**——而后者往往在几周后才被发现。

"逐字节一致"这个判据的强度值得注意：不是"功能正常"，不是"看起来一样"，是**逐字节**。因为只有逐字节比对才能发现那些不影响运行、但已经悄悄改变数据语义的地方（比如通道顺序、采样率标注、元数据字段）。

grep 用通道名和采样率常量作探针也很讲究：**这两个是"单设备假设"最集中的载体**。通道名写死了设备型号，采样率写死了设备时钟。找出它们，基本就找全了假设的藏身点。

## 第 1 步：协议侦察（半天）

**优先级：官方开发者仓库 > 官方说明书 > 自己逆向。**

本项目的顺序反过来了（先读的说明书），**结果说明书漏了两个关键握手细节，是后来克隆官方 mock 服务器源码才发现的**。

**教训：厂商给 AI 助手写的集成仓库（SKILL／插件／mock 代码）往往比人类说明书更接近事实，因为代码不会漏写步骤。**

**侦察要拿到的六项信息（缺一项就别开始写代码）**：

1. **连接与握手**：端口、是否要先发指令。本案实测：TCP 连上 9600 后**必须发送 `"start"`**，否则一个字节都不推；**说明书全文无此句**。
2. **行格式与字段数**：本案为按行 CSV；USB 模式 10 列（1 样本）、蓝牙模式 42 列（5 组 × 8 字段），**必须按字段数自动识别**，禁止硬编码切列。
3. **通道顺序**：要拿到**代码级文档依据**。本案定版 `CP5, CP6, PO3, PO4, O1, Oz, O2`，250 Hz，单位 µV（与厂商答复、官方配置档案交叉一致）。
4. **时间戳语义**：单位（ms）、起点（设备开机／会话开始）、**重连后是否归零**——直接决定第 4 步的时基方案。
5. **分包行为**：一行 CSV 可能被 TCP 拆成多次发送（**官方 mock 故意如此演示**）→ 接收端**必须攒到换行符再解析**。
6. **无设备时能否出流**：本案答案是**不能**——"打开数据服务"按钮绑定设备连接状态，且无模拟模式。这意味着真机到货前，**验证只能靠自己造的 mock**。

**逆向兜底（本案实际用到）**：软件无文档时，解包其程序（Electron／Java 均可解），对界面组件类做字符串扫描，找到按钮使能条件绑定的状态字段。一天内可完成，**合法合规范围内仅用于互操作**。

〔AI 理解〕"缺一项就别开始写代码"是这一步的实质纪律。六项里第 1、4、5 项最常被忽略，而它们恰好都是**在写代码之后才会暴露、且暴露时难以定位**的：

- 漏了握手（第 1 项）→ 连上了但零数据，看起来像设备坏了
- 漏了时间戳语义（第 4 项）→ 数据能收但采样率虚标，看起来像信号处理有问题
- 漏了分包（第 5 项）→ 偶发半行解析错误，看起来像数据偶发损坏

**三个症状都指向错误的方向。**这就是为什么侦察要在写代码之前完成。

第 6 项（无设备时能否出流）决定的是**开发节奏**：能出流，就可以等真机；不能出流，就必须自己造 mock——而这恰好逼出了第 6 步那套自测，它最后成了全篇最有价值的部分。

## 第 2 步：定义接口契约（1 小时）

新设备接收器实现与既有接收器**相同的鸭子接口**，上层完全不感知设备差异：

```python
class TcpReceiver:
    running: bool              # 工作线程开关
    last_error: str            # 最近一次错误文本
    packet_count: int          # 已解析样本组数
    on_status: callable        # 状态回调（连接/断线/error/end 事件）
    def start(self): ...       # 非阻塞，内部起线程
    def stop(self): ...        # 置停 + 尽力优雅关闭（触发断连保存）
    def is_connected(self) -> bool: ...
```

**纪律**：**失败路径必须发 error＋end 事件**（与既有硬件层同一约定），否则前端会停在"假在线"。

〔AI 理解〕"假在线"三个字是本步的全部理由。一个只在成功路径上发事件的接收器，失败时前端不会报错——它会**保持上一次的状态**，于是用户看到的是"连着但没数据"，而系统认为是正常的。

这类故障最难查，因为**没有任何一处报错**。所以接口契约里把失败路径的事件列为纪律，而不是留给实现者自由发挥。

鸭子接口（同接口、不继承）的选择也值得留意：它让新设备**不需要既有接收器的任何代码**，两个接收器可以独立演化，只要接口一致。这比抽一个共同基类更松，也更适合"将来还有第三、第四种设备"的情况。

## 第 3 步：缓冲层参数化（半天）

**最小改动模式——全局常量原样保留，缓冲实例携带自己的布局**：

```python
class DataBuffer:
    def __init__(self, channels=None, sfreq=None, device="muse"):
        self.channels = channels or CHANNELS      # 缺省=旧行为
        self.sfreq = sfreq or SFREQ
        self.device = device
        self.n_ch = len(self.channels)
        self.eeg_all = {ch: deque(maxlen=SECONDS * self.sfreq)
                        for ch in self.channels}

    def add_eeg(self, sample_times, eeg, aux):
        chs = range(len(self.channels))           # 不再 range(4)
        ...
```

下游所有函数（波形窗口、频段功率、存盘、报告）里的通道数和采样率**一律改用实例属性**。**改动全部是"读实例"替换"读全局"，无逻辑变化**——这让代码审查极其便宜。

存盘元数据加一个 `device` 字段，**数据从此自带血统**（本项目入库登记与回放筛选直接受益）。

〔AI 理解〕"改动全部是读实例替换读全局，无逻辑变化"是这一步的设计目标，而不只是描述。它带来的好处是**审查成本**：一个只做机械替换的 diff，审查者可以逐行确认没有夹带逻辑改动；而一个混着逻辑改动的 diff，审查者必须重新理解整段代码。

`channels or CHANNELS` 这个写法的用意是**缺省即旧行为**——不传参数时，新代码的行为与改造前完全一致。这正是第 0 步"逐字节一致"判据在代码层面的实现方式。

`device` 字段看似只是一个标签，实际影响深远：**数据自带血统之后，两种设备的数据可以混在同一库里而不混淆**，横向比较（比如同一人在两种设备上的频段差异）才成为可能。没有这个字段，将来想比较就得靠文件名或目录结构猜，而猜是不可复现的。

## 第 4 步：写接收器（1 天，五个工程点）

**① 握手**：连接成功后立刻 `send(b"start")`，再进入收流循环。

**② 行缓冲**：socket `recv` 的返回边界与行边界无关，用 `buf += chunk; split(b"\n")` 处理，**残段留到下次**。

**③ 列数自适应**：按字段数分派（10 列＝单样本／42 列＝5 组），未知列数**记错跳过——宁缺勿错**，错列会静默污染数据。

**④ 时基（本卡最硬的一条经验）**：

- **不要**用"收到即当下"。TCP 积压会成批到达，若都打本地时间戳，**采样率瞬间虚标数倍**，下游滤波与频段分析全部失真——**这个 bug 正是自测时 mock 成批推送暴露的**。
- **要**用设备时间戳，加两道防御：**单调不回退**（回退即丢弃或重定基线）、**跳变超阈值**（如 >2s，常因重连归零）则重新锚定。
- 缓冲的 `add_eeg` 接受外部时间轴，**本地墙钟仅用于显示与新鲜度判断**。

**⑤ 看门狗与断连**：超过 N 秒无数据判离线并触发保存；断线自动重连（**指数退避，上限 10s**）；重连成功后**重发 `"start"`**。信号调理（去直流＋1–40Hz 带通）与既有设备路径同构，**保证两条硬件线的频段数据可横向比较**。

〔AI 理解〕④ 时基这一条值得单独讲，因为它的失效方式最隐蔽。

**症状不是崩溃，是数据看起来正常但全是错的。**采样率虚标数倍之后，滤波器的截止频率实际作用在错误的频段上，频段功率算出来仍然是"合理的数字"——只是那些数字与真实的脑电无关。这种错误**不会报错，只会在几周后的分析里表现为"结论很奇怪"**。

而它被发现的方式很有启发：**是 mock 成批推送暴露的**。真机的 TCP 推送通常比较均匀，成批到达不常见；mock 服务器按协议演示时故意拆包、成批推送，反而把这个 bug 逼了出来。**自测环境比真机更严苛，这是自测的价值之一——不是替代真机，是暴露真机不易暴露的路径。**

③ 的"宁缺勿错"同理：未知列数时记错跳过，损失的是几个样本；硬切列的话，得到的是**看起来完整、实际错位的数据**。前者可恢复，后者不可发现。

⑤ 的"重连成功后重发 `start`"容易被漏：重连之后设备侧的推流状态可能已复位，不重发握手就会回到"连上了但零数据"。

## 第 5 步：接通会话与前端（半天）

- 会话／实验构造处按 `adapter` 参数选择接收器与缓冲：新设备 → `DataBuffer(channels=NEW_CHANNELS, sfreq=250, device="newdevice")` ＋ `TcpReceiver`；**其余分支不动**。
- 前端设备下拉框加一项，payload 加 TCP 地址字段（默认 `127.0.0.1:9600`）。
- **波形渲染改为 `Object.keys(wave)` 驱动**，图例、行数、通道读数全部随帧数据自适应——**这一步做完，任何第三种设备的前端工作就只剩"加一个下拉选项"。**

〔AI 理解〕最后一句是这一步的验收标准，也是最值得记的一句。**判断一次"通用化改造"做得够不够，就看加第三个实例时还要改几处。**如果加第三种设备仍然要动渲染逻辑，说明通用化只做了一半。

`Object.keys(wave)` 驱动渲染听起来是小事，但它把前端从"知道有几个通道"变成"数据里有几个通道就画几条"——**前端从此不再持有任何关于设备的假设**。第 0 步要找的四类藏身点里，前端那一类就是这样消掉的。

## 第 6 步：不等硬件的端到端自测（半天，本卡的价值所在）

厂商软件没有模拟模式？**自己造一个数据源**——直接采用官方 mock 服务器（厂商在其集成仓库里提供的脚本），它**按真协议推流（含故意拆包）**。

两级测试（本项目均为**可重复运行的脚本，退出码 0／1，可直接进 CI**）：

**单元级**：mock 推流 → 接收器 → 缓冲。验证点：

- 握手发生、行数计数正确；
- 七通道全部到位，存盘数组形状 `(N, 7)`；
- **物理正确性**：mock 在某通道掺 10 Hz 正弦 → 频段分析中 alpha 应在该通道出主峰（**本案实测 10.03 Hz**）；
- **时基正确性**：实测采样率应 ≈250 而**不是成批到达的虚高值**；
- 42 列蓝牙行与 10 列 USB 行混合都能解析。

**集成级**：从真实会话入口（监测 start）走完整链路 → tick 事件波形含 7 通道 → 停止存盘 → 读回数组核对形状、`device` 字段、通道名。**并回归旧设备模拟路径，确认改造无涟漪。**

**自测产生的模拟数据文件当场删除，不入库——这条要写进脚本，人总会忘。**

〔AI 理解〕这一步被原卡自己称为"本卡的价值所在"，我认为这个自评是准确的，理由有三层。

**第一层：它把"没有真机"从阻塞变成了不阻塞。**第 1 步第 6 项侦察出"厂商软件无模拟模式、无设备时不出流"，按常规做法这意味着真机到货前什么都验不了。自己造 mock 之后，全部六个步骤都能在真机到货前完成并验证。**本项目这张卡完成时，真机联调仍待硬件到货后回填**——也就是说，这套改造是在没有真机的情况下做完并自测通过的。

**第二层：它的验证点设计得比"能跑通"严格得多。**注意"物理正确性"这一项——不是验证"收到了 7 个通道的数"，而是**在已知通道掺入已知频率的正弦波，验证频谱分析在该通道该频率出主峰**（实测 10.03 Hz）。这一项能抓出的错误，是"通道映射错位""采样率虚标""滤波参数错误"这三类**静默错误**——它们都不会让程序崩溃，只会让数据悄悄变成别的意思。

时基正确性那一项同理：它明确写"应 ≈250 而不是成批到达的虚高值"，正是第 4 步④那个 bug 的针对性检查。**先踩到坑，再把它变成一条永久的验证点**——这是自测脚本与一次性调试的区别。

**第三层：它是可重复的、能进 CI 的。**退出码 0／1 意味着这套验证不依赖人读输出判断，可以被自动化反复执行。**改造完成之后，任何一次后续修改都能立刻知道有没有改坏。**

最后一句"自测产生的模拟数据文件当场删除，不入库——这条要写进脚本，人总会忘"看起来是小事，实际是数据治理问题：模拟数据一旦混进真实数据库，将来没人分得清哪些是真机采的。**而"人总会忘"这个判断，正是把它写进脚本的理由。**

## 已知失败模式速查

| 症状 | 根因 | 处置 |
|------|------|------|
| 连上了但一个字节都没有 | 没发 `"start"` 握手 | 见第 1 步第 1 项 |
| 数据断断续续、半行报错 | 没做行缓冲 | 见第 4 步② |
| 采样率虚标、滤波输出怪 | 收包即打本地时间戳 | 见第 4 步④ |
| 频段功率全 0 | 缓冲还在读 4 通道全局常量 | 回第 0 步清单逐处排查 |
| 前端只显示 4 条波形 | 图例／行数写死 | 第 5 步动态化 |
| "数据服务"按钮灰着点不动 | 厂商软件按钮绑定设备连接，无模拟模式 | **正常现象**，等真机或用 mock 自测 |
| 重连后时间轴跳变 | 设备时间戳随重连归零 | 第 4 步④跳变防御 |

〔AI 理解〕这张表的排列顺序有讲究：**前五行是"你以为的故障"，第六行是"其实不是故障"。**把"正常现象"也列进失败模式表，是因为它在排查时消耗的时间与真故障一样多——按钮点不动，人会一直试，一直怀疑自己装错了。
