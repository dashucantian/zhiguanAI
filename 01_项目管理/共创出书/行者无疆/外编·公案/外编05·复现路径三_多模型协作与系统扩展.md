## 上半 · 组织面：让多个 AI 在同一个项目里接力

### 你要解决的问题

一个 AI 窗口的上下文装不下整个项目。你想让多个模型（甚至不同厂商的模型）在同一个仓库里接力干活，不丢上下文、不撞车、不越权。

### 六步

**① 身份登记表——谁在干、哪个模型、哪个窗口**

每个 AI 会话开工时，在登记表里写一行：

```
| AI-015 | W1 工程线 | glm-5.3-flash | W1-GLM53FLASH-20261004-A | 云（已自证） |
```

五个字段：编号、窗口线、模型名、Session ID、执行类别（本地/云/未验）。

**为什么**：换一个模型接手时，它需要知道前面是谁、用什么模型、做到哪了。没有登记表，"前面那个 AI"就是一个黑箱。

**② 交接单——关窗时写、开工时读**

每个窗口关窗前，写一份交接单，包含：
- 本窗做了什么（commit 链）
- 候裁事项（哪些决定还没做）
- 在途文件（哪些文件改了但没提交）
- 红线提醒（哪些事不能做）
- 必读顺序（接手窗先读什么）

开工的窗口**先读交接单**，再动手。

**为什么**：上下文窗口会满、会话会断、模型会换。交接单是唯一不依赖"记忆"的传承机制。

**③ pathspec 显式列名——禁 `git add .`**

多个窗口共用一个 git 仓库时，`git add .` 会把别的窗口的在途文件也暂存进去。规矩：

```bash
git add -- "path/to/my/file1.md" "path/to/my/file2.py"
git commit -- "path/to/my/file1.md" "path/to/my/file2.py"
```

只列自己的文件，不用通配符，不用 `-a`。

**为什么**：共享 index 是公共资源。一个窗口的 `git add .` 可能把另一个窗口改了但还没准备好的文件卷进提交。

**④ trailer 归因——每笔提交写清是谁**

commit message 末尾加 trailer：

```
Author-Role: AI 助理·W1（维那）
Proposal-by: W1 工程线会话
Approved-by: 项目负责人（2026-10-05 金口）
Model: glm-5.3-flash
Session: W1-GLM53FLASH-20261004-B
Window: W1
```

**为什么**：半年后回看 git log，你需要知道这笔提交是哪个模型、哪个窗口、谁批准的。没有 trailer，归因就断了。

**⑤ 巡检日志分窗——各窗只写己档**

每个窗口有自己的巡检日志文件（`巡检日志-W1.txt`、`巡检日志-W3.txt`）。只写自己的，不写别人的。

**为什么**：如果所有窗口写同一个文件，并发冲突不可避免。分窗之后，每个文件只有一个写者。

**⑥ 评审闭环——另一个窗口独立核**

一个窗口做完设计稿，投给另一个窗口评审。评审窗独立跑代码、独立核事实，不采信产出窗的自述。

实例：W1 写了"某 API 全域零注册"，W3 评审时实际跑了一遍，发现 7 个端点注册着——W1 的搜索没递归。三处事实修正，就地注记，历史不改写。

**为什么**：产出方自证不可信（别编 03 判语 011）。第二双眼睛不是形式，是真的能抓住错。

---

### 上半小结

六步合起来，是一条完整的接力链：

```
登记 → 干活 → 关窗写交接单 → 下一个窗口读交接单 → 登记 → 干活 → …
```

中间穿插：pathspec 提交（不撞车）、trailer 归因（可追溯）、分窗日志（不冲突）、评审闭环（不采信自证）。

**实测**：本项目 W1 工程线在 6 天内换了 5 任模型（claude-fable-5.1 → fable-5 → opus-5 → gpt-5.6-sol → glm-5.3-flash），工作没断过一天。

## 下半 · 工程面：给已有系统接上一个会学习的新组件

### 你要解决的问题

你有一个已经跑通的系统（比如一个脑电反馈闭环），想给它加一个"会学习"的组件（比如一个持续学习的脑档案），但不想把原来的搞坏。

### 五步

**① 设计门／施工门分立——先写方案稿，零代码**

动手之前，先写一份方案稿：
- 定位一句话（新组件是什么、与旧系统什么关系）
- 现状事实（旧系统现在有什么接口、什么数据格式）
- 四层设计（数据怎么进来、怎么处理、怎么存、怎么被消费）
- 待裁定清单（哪些决定需要负责人点头）

方案稿**不含代码**。评审过了，才进施工门。

**为什么**：代码一旦写了，就有沉没成本。方案稿阶段推翻一个设计，成本是零；代码阶段推翻一个设计，成本是重写。

**② 逐批金口——每批施工前负责人点头**

施工不是一次性做完，是分批：

```
批 C0（账本事务化）→ 金口 → 批 C1（管线接入）→ 金口 → 批 C2（前端卡片）→ 金口 → 批 C3（契约更新）
```

每批做完，提交，等负责人说"好"，再做下一批。

**为什么**：一次性做完再审，审的人面对的是几千行 diff。分批审，每次只看几百行，质量高得多。而且任何一批出问题，后面的批还没开始，损失有限。

**③ 事务化落库——写一半崩了不丢**

新组件的核心数据结构（比如"脑档案"）必须事务化：
- 写操作包在事务里
- 崩溃后重启，要么完整写入，要么完全没写
- 自测包含"双进程并发写 2×30 轮零丢失"

实例：`registry_tx` 三件套，轻量自测 7/7 通过。宿主内核崩溃（bugcheck 0x3D）后，工作零损失。

**为什么**：新组件刚接上去的时候最脆弱。如果写一半崩了、数据坏了，你分不清是新组件的 bug 还是旧系统的问题。事务化保证"崩了也不坏"。

**④ 契约测试——接口数对得上**

旧系统有 N 个 API 路径。新组件接上去后，路径数变成 N+M。契约测试验证：

```
openapi 实际路径数 == 契约文档记录数
```

每次施工后跑一遍。对不上，就是漏了什么或者多了什么。

实例：契约 v0.2 → v0.3，从 55 装饰器／54 路径增到 58／57，运行态 openapi 实测相符。

**为什么**：接口是新旧系统的接缝。接缝对不上，数据就会从缝里漏出去。

**⑤ 真浏览器验收——不是单测绿了就算**

单测全绿不等于用户能用。最后一道验收必须是**真浏览器**（或真设备）跑一遍：

- 页面渲染对不对
- 交互行为对不对
- 截图留档

实例：从此脑卡片，真浏览器验收 11/11 通过（CDP 无头 Edge），截图落 `output/` 目录。

**为什么**：本项目踩过坑——四套单测全绿，自验收时捉出两处生产级缺陷（正编第七章§五）。单测测的是"代码逻辑对不对"，真浏览器测的是"用户看到的对不对"。两者不等价。

---

### 下半小结

五步合起来，是一条从设计到落地的管道：

```
方案稿（零代码）→ 评审 → 金口 → 批 C0 → 金口 → 批 C1 → … → 契约测试 → 真浏览器验收
```

**实测**：从法师说"改变走向"到第一批代码落库（C0），中间不到 48 小时。三批施工（C1→C2→C3）在一天内完成，真浏览器验收 11/11 通过。

## 两半之间的关系

上半解决"谁在干"，下半解决"怎么干"。

它们不是独立的两件事——下半的每一步都依赖上半的纪律：
- 方案稿投给谁评审？→ 上半的⑥（评审闭环）
- 逐批金口谁给？→ 上半的②（交接单里写清候裁事项）
- 施工提交怎么不撞车？→ 上半的③（pathspec）
- 崩溃后谁接手？→ 上半的①②（登记表＋交接单）

**没有上半的组织纪律，下半的工程管道跑不起来。** 反过来也一样：没有下半的分批验收，上半的接力只是"换了一个人继续乱写"。
