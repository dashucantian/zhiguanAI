# 数字员工与「内／中／外循环」对照研究 v1

**性质：研究与建议稿，不是裁定、不是派工。**
取证时刻：2026-10-29｜对象：QoderWake CN、止观AI当前循环、公开的 agent workflow / community 案例。

> 本稿把来源分三层：①厂商产品页＝能力宣称；②官方文档＝功能与控制点；③厂商案例／演示＝应用实例，但不是独立第三方审计。凡没有独立证据的数字，不当作普遍效果。

## 一、结论先说

**QoderWake 和止观AI不是同一种东西。**

QoderWake 主打的是**组织里的数字员工**：需求在群聊、日历、hook 或 API 出现后，Waker 自动接活、调工具、拆给其他 Waker，经过检查与人工确认后交付。

止观AI 的根本对象是**个人节点**：不是让 AI 接管一个团队，而是帮助一个人建立规约、记忆、任务、证据四层，让人能自主练习、持续复盘，并把这套结构复刻给另一个人。

因此，不应照搬“更自主、更多并行”作为目标；应借鉴它的**现场触发、任务状态板、角色分立、交接轨迹、权限与审批、长任务恢复**，把它们嵌进止观AI的三环：

- **内环**：一个人的目标—练习—记录—复盘；
- **中环**：多个角色围绕任务协作、交接、验收；
- **外环**：个人节点复刻到社区，社区反馈回灌案例与模板。

**当前最大差距不是模型，而是“从真实需求到可验收任务”的中环还靠人工拼；外环反馈入口与回灌节律尚未真正运转。**

## 二、先把 QoderWake 拆开：它实际提供什么

QoderWake 官网把自己定位为“在真实工作现场自主工作的数字员工”，并说可从 IM、schedule、hook、API 四类触发开始工作。[产品页](https://qoder.cn/qoderwake) 是厂商定位；细分能力以 [官方概览](https://docs.qoder.com/qoderwake/overview)、[Waker 管理](https://docs.qoder.com/qoderwake/manage-wakers)、[任务板](https://docs.qoder.com/qoderwake/task-board)、[Autonomous Work](https://docs.qoder.com/qoderwake/automated-tasks) 为准。

| 能力面 | QoderWake 的公开设计 | 对止观AI的启发 |
|---|---|---|
| 触发 | IM／日程／hook／API | 从需求发生处起任务，不只靠 2 小时轮询 |
| 角色 | Waker 有岗位、运行时、权限、资源 | 每窗一职，岗位边界显式化 |
| 状态 | 排队／运行／需人／完成／失败／取消 | 待办显态；完成不等于验收 |
| 协作 | Group、多 Waker 分段交接 | 内／中／外环之间要有交接协议 |
| 能力 | Skills、connectors、knowledge、projects | 只按任务加载必要技能和资料 |
| 安全 | 最小权限＋审批＋日志 | 高风险动作须法师批准 |
| 长任务 | 状态保存、失败恢复、验证和重试 | 七拍之外还需每个任务自己的运行记录 |

QoderWake 文档也提醒：Autonomous Work 应先在普通对话验证，再自动化；任务要有明确输入、范围、结束条件；“完成”不等于“验收”。[Autonomous Work](https://docs.qoder.com/qoderwake/automated-tasks) 与 [Task Board](https://docs.qoder.com/qoderwake/task-board) 都强调查看来源、状态、最新进展和实际产物。

## 三、和止观AI“内／中／外循环”逐层对照

| 环 | 止观AI现在的骨架 | QoderWake可借处 | 现有缺口 |
|---|---|---|---|
| **内环** | 个人节点四层 | 记忆可纠错；岗位 skill | 缺个人运行页 |
| **中环** | 发现→挂账→处置→销号 | 触发＋任务板 | 缺任务 ID／状态 |
| **外环** | 模板＋案例＋闸门 | 角色包可复制 | 反馈入口／分级／回灌未实跑 |

关键差别：**QoderWake 的“员工”以完成组织任务为中心；止观AI 的“个人节点”以人能否自持、能否复刻为中心。** QoderWake 的自主性是可借的执行结构，不是止观AI的价值目标。

## 四、可核的实际案例：借流程，不照搬宣传

### 1. QoderWake：数据分析员的双 Waker

厂商案例称，某数据分析员把重复取数分给“数据检索 Waker”，把开放分析留给“业务分析 Waker”；返回内容附 SQL、指标定义和计算逻辑，业务人员可追问，分析员再复核。[案例 01](https://docs.qoder.com/qoderwake/data-analyst-story-01)

**可借**：按任务性质分角色；输出带计算式与来源；把可重复取数与需人判断的分析分开。
**不可直接当效果证据**：案例是厂商访谈，用户数与任务量是自报，不代表所有组织均能达到。

### 2. QoderWake：一个需求、产品／开发／评审／测试接力

官方工作故事描述产品 Waker 澄清需求后交开发 Waker，再由 Reviewer 独立 review，Tester 按 PRD 与 Spec 验收；关键决策和合并仍由人做。[开发接力案例](https://docs.qoder.com/qoderwake/development-relay-story-03)

**可借**：执行者、审查者、验收者分开；失败回到执行者修；人保留关键门。
**关键警告**：Waker 不该审自己出的件——这和我们监督位回避条是同一条原则。

### 3. QoderWake：商务合作跟进

官方案例把群聊中的“看一下需求”变成需求拆解、方案迭代、会议安排、会议纪要和下一步跟踪，直到合作双方确认。[商务协作案例](https://docs.qoder.com/qoderwake/business-collaboration-story-02)

**可借**：上下文不随对话结束而丢；每次会议产生下一步、责任人和回访点。
**不可照搬**：对外联络属于代表组织发声，止观AI仍须法师批准外发。

### 4. QoderWake × GitHub：事件驱动交付演示

官方 demo 把 Release／Developer／Reviewer／Tester 四个角色接到 GitHub 事件上；每个角色有“能做／不得做”，PR 合并仍有人把关。[GitHub DevOps 演示](https://docs.qoder.com/qoderwake/github-devops)

这是**演示工作流**，不是独立审计的生产案例；但它给了可用的任务状态设计：触发、执行、review、测试、人工合并、发布。

### 5. GitHub Copilot coding agent：issue→draft PR→人工审

GitHub 官方介绍中，agent 从 issue 被指派后在隔离环境工作、提交到 draft PR、显示 session logs；关键 CI/CD 运行前需要人工批准。[官方介绍](https://github.blog/news-insights/product-news/github-copilot-meet-the-new-coding-agent/)。官方也明说 code review **不保证发现所有问题**，AI 产物仍需人审。[Code review 说明](https://docs.github.com/copilot/concepts/agents/code-review)

**可借**：把产物当草稿 PR，不直接落地；变更可回看、可逐条评论；人批准后才进入高风险阶段。

### 6. 治理参考：Microsoft、Home Assistant

Microsoft 的自治 agent 指引主张：任务范围清晰、先测试再逐步放权、高风险动作保留人工监督、权限最小化、保留审计日志。[Microsoft 指引](https://learn.microsoft.com/en-us/microsoft-copilot-studio/guidance/autonomous-agents)。

Home Assistant 的 AI policy 要求贡献者必须理解并能解释提交的改动；其开发建议鼓励小 PR、逐批审查。[AI policy](https://github.com/home-assistant/core/blob/dev/AI_POLICY.md)／[开发建议](https://developers.home-assistant.io/docs/development_tips/)。

这两者给我们的共同启发：**最小权限＋小批交付＋独立复核＋失败有日志**，比一句“AI 要可靠”更可执行。

## 五、止观AI现状：问题不在“没有规矩”，而在规矩还没全部变成运行机制

### 已有的强项

1. **人的判定权写得很清楚**：四项高风险（真机／真实数据／真人／出网发布）须法师字。
2. **监督与监管已分立**：协调位落笔，AI-025 监督位抽检，24e5b510 监管位挂账；“谁不审自己”已明确。
3. **证据纪律比多数宣传型 agent 方案更强**：时刻、尺名、出处；未验不得写通过；实例抽检已抓出真实错误。
4. **复刻三件已经存在**：规约、案例库、闸门；一页常驻索引已从 71,762 字符降至约 1,300 字符。

### 主要缺口（按影响排序）

| 优先 | 缺口 | 为什么是瓶颈 | 目标状态 |
|---|---|---|---|
| P0 | 统一任务对象 | C／MON／函号分散 | 一事一 ID＋来源／主责／状态／验收 |
| P0 | 触发与去重 | 两小时轮询是兜底；易重触发 | 加去重键；续原任务不新建 |
| P0 | 监督闭环 | 回件、销号、回避待可见 | Needs-attention＋24h SLA |
| P1 | 运行记录 | 总日志有，单任务轨迹缺 | 每次运行留 ID／输入／步／产物／审批 |
| P1 | 社区反馈 | 现为设计稿 | 反馈卡→3 日分级→脱敏→回灌→回访 |
| P1 | 体量闸 | F5 已报超线，未瘦身 | 索引≤8k；细则按需加载 |
| P2 | 监管清单 | MON 可追，催办仍手工 | ID／级别／期限／主责／证据／销号 |

## 六、建议方案：分三阶段，不先造“大一统自治员工”

### 阶段 0：先把“任务对象”钉死（1 周内）

建立一张**任务登记行**，最小字段：

```
ID｜来源｜需求原句｜责任位｜状态｜权限级｜时限｜验收句｜证据链接｜复核者
```

ID 只用一种（建议 `TASK-YYYYMMDD-NN`）；C-号是法师裁定，MON 是漂移监管，二者保留为关联字段，**不再充当任务主键**。

### 阶段 1：先在“内部、低风险、可回滚”的一类任务试跑（2 周）

选**信箱来函→归类→待办建议→人工确认**，不自动发信、不改外部飞书、不动原始数据。用 060d716f 试跑件做执行器，6213b8d6 独立监督，24e5b510 监管规则与漂移；法师保留最终批准。

每次运行记录：触发来源、输入摘要、读过的文件、工具调用、退码、输出件、审批人、耗时、失败原因。完成不等于验收，验收必须由非执行者做。

### 阶段 2：把“个人节点”包装成可复制包（4 周试点）

先选 3—5 位**明确同意**的参与者；每位只部署个人索引、任务卡、案例写入模板，不共享个人原始数据。反馈按三类：直接可复用／需个人适配／不采纳；每月公布“收到 N、采纳 M、退回 K”及原因。

### 阶段 3：达到门槛再考虑更多自主

建议试点门槛（**建议值，不是现状**）：

- ≥90% 任务有唯一 ID、责任位、时限、验收句和证据链接；
- 高风险操作未经批准＝0；重复触发重复执行＝0；
- 监督抽检 10 件中，关键事实可回源率 ≥9/10；
- 社区反馈 3 日内完成分级率 ≥90%。

未达标不扩权限，只修流程。

## 七、让监督与监管参与，不让它们变成“多两个人抄表”

| 角色 | 参与点 | 产物 |
|---|---|---|
| 协调位 `fc2ce735` | 统一任务 ID、拆解、落单、推动 | 任务登记行＋运行记录 |
| 监督位 `AI-025` | 抽 10% 任务，三查输入／计算／结论 | 命中／未命中／未验 |
| 监管位 `24e5b510` | 查权限边界、到期漂移、重复触发、外发风险 | MON 行＋月度漂移汇总 |
| 法师 | 高风险授权、方向与最终取舍 | 批准／驳回／改判 |

监督位不派工、不代裁；监管位不审自己经手的件；协调位不自己给自己打“已通过”。每一轮都保留回避记录。

## 八、给 Waker 的“能／不能”边界（建议直接写进岗位卡）

- **能**：读获准目录、做摘要、拆任务、生成草稿、跑离线测试、报告差异。
- **须审批**：改脚本／规约、真实数据处理、对外发送、写入共享台账、增加权限。
- **不能**：自行判疗效、替法师定修行方向、把未验写通过、把社区反馈直接变成新规约。

## 九、总结

QoderWake 的强项是**在需求现场起跑、任务持续推进、岗位交接可追**；止观AI 的独特强项是**个人节点、人的判定权、证据与反自欺的闸**。

最值得借的不是“全天候自主”，而是：**需求出现就生成一条可追的任务；执行、监督、监管分开；每次交付都有验收和回滚边界。**

外环社区闭环的先决条件不是更多功能，而是：一张反馈卡、一条分级规则、一个回灌口、一个公开的月度结果。

## 十、给监督／监管两窗的复核任务（24 小时内）

- **监督位 AI-025**：抽查本稿引用和“案例为厂商自述/演示”的标注；重点核 P0 缺口、分阶段门槛是否有来源，输出“命中／未命中／未验”。
- **监管位 24e5b510**：按 R-01—R-09 查权限、个人数据、对外发、试点指标、MON/任务 ID 是否互相冲突；提出 MON 行，不代法师裁决。
- 两窗不得审自己出过的材料；若发现问题，给 `文件:行`＋复算/复现步骤。
