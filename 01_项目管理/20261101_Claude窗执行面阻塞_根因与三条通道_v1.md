# Claude 窗执行面阻塞：根因与三条通道 v1

- 出：AI-026·DSH 窗 `4ef78b3e`（W3 协调位）｜2026-11-01 00:4x（本机现取）
- 起因：法师问「AI-027 为什么出现这种情况？怎么能够解除这样的问题，让他的能力充分发挥出来？」
- 对象：AI-027＝Claude Desktop 协作窗，代键 `CLAUDE-20261031-A`，无 Windows CLI，执行面仅 `mcp__workspace__bash`

## 一、现象（照实）

两次调 `mcp__workspace__bash` 均返 **`Workspace still starting`**；因此它没能执行我函中要求的 `git status -- <路径>` 核锁，也没落复核文件、没提交，并明示不绕门槛。**它没有做错任何事**，是执行面没起来。

## 二、根因（证据链，全部本机现取）

| # | 证据 | 读法 |
|---|---|---|
| 1 | `cowork_vm_node.log`：`[Bundle:status] rootfs.vhdx missing` | 虚拟机**根盘镜像不在盘**，VM 无从启动 |
| 2 | 同日志：`vmlinuz/initrd version mismatch: have=882518…, want=072b6c…` | 客户端 bundle 已升级，盘上内核还是 10-02 的旧版 |
| 3 | 同日志 21:22:41：`Download stalled: no data received for 30000ms` → `[VM:start] Download failed, leaving VM offline (no auto-reinstall)` | 下载 30 秒无数据判失败，且**明写不再自动重装** |
| 4 | `vm_bundles\claudevm.bundle\rootfs.vhdx.zst.c480f8a62d0d.partial`＝87,993,267 B（83.9 MB），mtime **10-31 21:19:41** 起停长 | 下载卡在 83.9 MB 就地冻住 |
| 5 | 下载地址 `https://downloads.claude.ai/vms/linux/x64/072b6c…/rootfs.vhdx.zst`，三次起（21:21:25／21:22:11／23:19:07） | 从没取完 |
| 6 | 本机探（三级出网·一般元数据·只测可达，不取内容）：HEAD **10.2 s 无响应**（curl rc=28）；Range 0–1 MiB **15 s 取 0 字节** | 这台机器到该 CDN **不通** |
| 7 | 同日志 11-01 00:31:54：`[startVM] VM startup already in progress, waiting...` | AI-027 两次调用正撞在这句上 |
| 8 | 盘余 C 318.2 GB／D 240.4 GB；`vmcompute`／`HvHost`／`hns` 三服务均 Running；WSL 未安装 | 与空间、与服务都无关（它用自带 HCS 微虚拟机，不走 WSL） |

**一句话**：不是权限、不是仓库、不是它不会用——是 workspace 的根盘镜像**下不来**。每次 bash 调用都只能排在那台永远起不来的 VM 后面，所以重试一百次也一样。

## 三、三条通道

### 甲·治本（要法师动手）

让 `downloads.claude.ai` 通（代理／换网络），然后**完全退出 Claude Desktop 再启**——不是新开会话：下载器在进程里，现在状态是「already in progress」，新会话只会排在同一个死下载后面。

判成功三条：① 日志不再出现 `Download stalled`；② `claudevm.bundle` 下出现 `rootfs.vhdx`（GB 级）；③ bash 调用 10 秒内返回。

### 乙·今天就能用（已备好，不依赖任何执行面）

本窗已出**只读包**：`_analysis_tmp\v11_ai027_pack\v11_readpack.md`（49,671 B／1,320 行）——含代核事实（无锁、已推、余数 0）、法师裁定、源码六件全文、v1.1 差分、四个待它判的点。法师转贴 → 它只回「发现清单」→ 本窗代录入并注明：作者＝AI-027、代键 `CLAUDE-20261031-A`、代录入者＝本窗（坑 076 口径：提交层署名不由它承担，正文写清来源）。

### 丙·结构性（建议）

把 AI-027 定为「**终审读码位**」：不写盘、不提交，只出判断。落盘与归因恒由代录窗承担。这样即使 VM 长期不通，它每轮照样可用，且不必再为「核锁」这种可由协调位代做的事卡住。

## 四、为什么乙不降它的能力

它上轮报的四条 P1（代理与重定向、只读未由代码强制、回环校验下沉、`directory` 外泄）**全部来自读码，不来自跑码**；还纠正过我一处误判（`/session/:id` 未实现，README 早已披露）。它的强项是读，不是跑——执行面缺位只削掉「自己写盘／自己提交」，削不掉判读。
