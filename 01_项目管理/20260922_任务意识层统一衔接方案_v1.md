# 任务意识层统一衔接方案 v1（实施前定稿 · 2026-09-22 · W3/AI-006）

> 缘起：法师 09-22 指示——B2 与 A（QwenPaw）、"专属工作伙伴"要**一次性考虑到位、衔接好再实施、不要重复工作**。本方案为四候选的统一架构定稿，经 v0 评估（含附录 A/B/C）收敛而来。**实施前唯一必读即本文件**，v0 作论证底档不再重复引用。

## 一、一页总览：四层分工，每层只干一件事

```
【L4 人格层·可选后上】 维那照察者 ＝ A（QwenPaw 本地）或 专属工作伙伴（云端）二选一
        ↑ 只读信箱＋看板元数据；人设文件全项目唯一一份（§四），两处复用
【L3 视图层·手机即面板】 飞书任务 App ＝ 法师的任务面板：卡片/截止/子任务/提醒/验收勾选
        ↑ 任务卡由 L2 自动生成或由窗口直报；反向有官方"任务清单同步到多维表格"连接器
【L2 引擎层·零常驻】 多维表格自动化流程（B1 正名＝引擎，不是备选）：
        触发（新增待审/状态变更/截止前 N 天）→ 动作（建卡/更新卡/发提醒）——官方项目管理标准场景
【L1 事实源·不动】 ZG 看板（现有多维表格）＝任务唯一真相源；L1~L3 都只是它的投影与转发
```

**衔接核心**：B1 与 B2 不是二选一——**看板自动化（B1）就是生成任务卡（B2）的引擎**，官方文档《自动化流程创建任务场景实践：项目管理》即此标准用法。之前版本把 B1/B2 并列为"两条路径"是切分错了，本方案订正为**一套引擎＋一个面板**。

**本地↔云端唯一通道＝信箱协议**：各窗口（本机）经 lark-cli 读看板、写任务步骤，与 v0 的 inbox/outbox 设计合并为同一套——目录在 `01_项目管理\信箱\`（实施阶段 0 才创建），内容只放**任务元数据**（ZG 编号／标题／卡点一句话／状态），任何录音、学员数据、脑电数据、代码正文不进信箱、不上任务卡。

## 三、额度实测账（2026-09 官方口径，阶段 2 真跑校准）

- 自动化流程（L2 引擎）：**基础版免费 200 次/月**（企业共享＝我租户独享）；测算：状态变更触发 ~80＋建卡 ~20＋截止扫描 1×30 ≈ **130 次/月，留三成余量 ✅**；不足时系统有"即将耗尽"提示，仍超再评商业版。
- AI 通用额度（仅当 L2 动作里用"AI 生成文本"才耗）：**免费约 100 次/月**（⚠️单源待校验）——设计上 L2 全部用**固定模板**播报不耗 AI 额度，AI 摘要留给 L4 可选层。
- lark-cli 任务/消息接口走 OpenAPI 免费额度（100 万次/月），量级无虞。
- 专属工作伙伴／A 若启用：A 零云端额度；工作伙伴耗个人 AI 额度——正是 §五阶段 3 要实测的。

## 四、信箱协议（一次定死，换 agent 不换协议）

```
01_项目管理\信箱\
  README.md        协议本体：字段表＋示例（阶段0建）
  inbox\             法师派单：YYYYMMDD-ZGxxx.md（标题/期望/优先级，元数据级）
  outbox\            窗口回报：办理结果一句话＋看板链接
  维那SOP.md          全项目唯一人设文件（L4 两候选共用）
  卡任务映射表.csv     ZG编号 ↔ 飞书task_guid（本地留存，防双录漂移）
```
规则：文件即消息、命名唯一、只追加不覆盖；窗口侧读写全走 lark-cli／本地文件，L4 层（无论谁家）接入时**读同一目录**——这就是"衔接到位"的落点：L4 换人不改协议、不加平行通道。
