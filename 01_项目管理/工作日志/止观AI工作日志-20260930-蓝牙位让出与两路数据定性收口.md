**先查清"谁占着"，不猜**（`netstat -ano` ＋ `Get-Process` ＋ 只读 BLE 扫描 ＋ `/api/v1/status`）：

| 端口 | 持有者 | 当时状态 |
|---|---|---|
| 9600（NeuraDock TCP 数据服务） | NeuraDock 1.2.0 APP | 在听 |
| 60526（平台 HTTP 指标 API） | 无 | **已废**（旧端口） |
| 8777／8788（实践驾驶舱） | python PID 25264 | 在听 |

**关键更正**：`/api/monitor/status` 回 `{"running":false, "mode":"真机蓝牙"}`——`running=false` ⇒ **驾驶舱没跑会话、没碰任何头环，本机蓝牙是空的**；但 `mode` 仍显示「真机蓝牙」，因为 `console_server.py` **只在 `start()` 写 `self.mode`，空闲不复位**。**"看起来没空"是读数陈旧，不是设备被占。**

**改动**（`console.html`，**仅显示层**，纯新增 36 行、零删除）：

2. 新增 `#ndConflictRow` ＋ `notifyNdConflict()`：当**「真机蓝牙」×「旁证源＝NeuraDock 指标 API」**同时成立，就地亮红字——**只告警、不替使用者改选择**；

**验证三项**：`validate_console.py` PASS（id 157、语法通过）｜冲突判定 **8/8 PASS**｜**8777 实拉首页**含新行与新文案且 `simulate` 仍 `selected`。**不需重启 8777**（`console_server.py:2846` 用 `FileResponse` 每请求读盘），刷新即见。

### 1.3 两路数据定性（法师四问）

法师问：9600 与指标平台数据有何不同？会不会冲突？9600 是七通道全量原始数据吗？本地跑吗？能不能不开那个 APP？

| | **192.168.188.105:9600** | **指标 API（HTTP，随机端口）** |
|---|---|---|
| 是什么 | **全量原始数据**：逐样本时间序列 | **算好的结论**：指标＋质量＋状态 |
| 内容 | 7 通道 × 250 Hz × µV | `focus`／`visual_load` |
| 原始脑电 | **有** | **没有**（`raw_eeg_exposed=false`，厂商刻意不给） |
| 握手 | 连上**必须先发 `start`** | 直接 GET |
| 驾驶舱角色 | 主数据源 → 波形／质检／npz／**入库** | 旁证源 → 只读比对，**不入库** |

依据非推测：`neuradock_receiver.py` 开头明载协议出自厂商开源仓库（通道序 CP5/CP6/PO3/PO4/O1/Oz/O2、250 Hz、µV、`start`、蓝牙 42 字段／USB 10 字段）。**APP 界面第 8 行波形是平的**由此得解：硬件 16 针定义里 **CH8 = "not used"**。

**冲突关系三分**：① 9600 × 指标 API **彼此不冲突**（不同进程不同端口）；② 真正冲突的是**驾驶舱自己的「真机蓝牙」**——法师截图正卡在"正在扫描 Muse 头环"，即我方在抢；③ **同源共死**——实测**关掉 1.2.0 APP 后**，9600 消失，平台立刻 `source.state=error`、`last_sample_age_sec=71.4`、`usable_channel_count=0`、**七通道全判坏、合格度不合格**。

**本地性与暴露面**：数据本地，**但 APP 绑的是局域网 IP `192.168.188.105` 而非回环** ⇒ 同网段机器都可能取走原始脑电——**如实登记为一处暴露面，是否收口请法师裁**。抓取瞬间全机**无任何指向非内网地址的连接**⇒未观察到上传（快照证据，非"永不联网"）。另记：厂商 agent 的 LLM 模式会外发**指标摘要**（其文档明写原始脑电与稠密数组从不包含）。

### 1.4 「能不能不开那个 APP」——核查结论：现阶段绕不开

| 证据 | 内容 |
|---|---|
| 厂商 agent 源码 | 数据源只有 `simulator｜replay｜**TCP**`，默认 `127.0.0.1:9600`——**连厂商自己的开源程序都不碰蓝牙** |
| 厂商 Python 教程 | 标题写 Bluetooth streaming，正文实为 **via TCP (Bluetooth mode)** |
| 录屏软件仓库 | 只放发行说明与二进制，明写"installer／binary 不自动按开源授权"⇒**闭源** |
| 硬件仓库 | 只公开**电极排针**与 **MCU 调试口**，**不含蓝牙 GATT** |

**三条路线候裁**：**甲**（立刻可做、零协议风险）让 exe 随开机自启＋最小化到托盘；**乙**（正路）向厂商索取 GATT 规范或无界面版——维护者 **JunwenLuo（罗工）**，我方档案本就有"罗工回函"草稿，硬件仓库自述"为第三方集成提供接口与端口规范"，**索取属正当请求**；**丙**（不推荐）自行逆向 GATT，**等于自造驱动**，违"不猜厂商协议"且固件升级即失效。**另一捷径**：改用 **USB 线**连采集模块（我方 `TcpReceiver` 支持 `transport=auto`，USB 10 字段自动识别）⇒**蓝牙彻底空出**，但**仍要开那个 exe**。

## 四、战略层

- 本轮的实质是把**"设备到底在谁手里"**这件事从猜测变成台账：蓝牙只有一条链路，谁持有必须能从端口与状态读出来，而不是靠"上次设的是什么"。这与判语 009「镜子非训练器」同向——**设施不替人做判断，但必须让人看得见实况**。
- 旁证源这条线的**独立价值**得到确认：它给的是**结论**（对方算好的指标）而非**数据本体**。教学与验收上要始终分清：**能比对方向 ≠ 数字相等 ≠ 可入库**。
- 「不开厂商 APP」的问题，本质是**要不要把命脉交给一个闭源进程**。在拿到 GATT 之前，本项目对该设备的取数能力**完全依赖对方软件的存续**——这条依赖应当写进设备档案的风险栏，而不是留在一个窗口的记忆里。
