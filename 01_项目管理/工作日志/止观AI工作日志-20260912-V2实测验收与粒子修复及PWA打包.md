### 2.3 粒子穿透缺陷（当日修复）

**根因**：粒子只垂直上升（`pos.setY`），水平坐标 x/z **终生不变**；初始撒点半径 2–16 的环内约 2% 恰落在模型投影内 → 必然垂直穿过瑜伽士身体。

**修法**：触碰即**就地重生到模型范围外**（粒子数恒定，不降密度）。因粒子无水平位移，用水平 footprint 判定即可，**无需射线检测** —— 载入时一次性重排 ＋ 主循环每帧守卫，零额外开销。包围盒外扩 0.18 使「触碰到体表」即散而非穿入体内。

**运行时实测**（`verify_particle_avoid.py`，真加载 28MB 模型）：

| 指标 | 结果 |
|---|---|
| 载入时体内重排 | **19 个** ← 证明修复前确有穿透 |
| 重排后体内残留 | **0** |
| 运行数帧后再查 | **0** ← 双层守卫稳定 |
| 包围盒 | x[-1.647,1.647] y[-0.18,3.18] z[-7.609,-4.391] |

### 2.4 打包技术约束查清（实现前实测，非凭搜索片段推断）

**已具备的有利条件**：
- three.js ＋ GLTFLoader **本地已有**（`vr_assets\`，共 1.35MB），importmap 已指向本地 → **不依赖 CDN**
- 自签证书与 8778 HTTPS **现成**（`local_tls.ensure_cert()` ＋ uvicorn 双端口）
- `/vr` 与 `/vr_assets/` 路由现成
- 无脑电时场景**已能降级渲染**（冒烟测试实证 S.a 落 0.5 中性）
- 后端依赖仅 3 处（`/ws/vr`、`/api/vr/models`、`/api/vr/model`）

**一条不能走的路**：第三方「HTML 一键打包 APK」工具走 **WebView**，而 WebView 对 WebXR 支持很差 → **进不了 VR 全屏**，排除。

**PICO 官方路径**（查证 developer-cn.picoxr.com）：PICO OS 6 新增「Web App」形态，本质是 **Install-free PWA**。任何网址只要满足 **HTTPS ＋ Web App Manifest（name/icons/start_url/display 四必需字段）**，即可作为 Web App 独立运行、按需安装到应用库像原生应用一样从图标启动，**无需提交给 PICO**。要求浏览器 **v3.3.36+**（灰度推送中）。

**一处硬约束**：Service Worker **必须从根路径 `/` 提供**，若放 `/vr_assets/sw.js` 则 scope 仅 `/vr_assets/`，**无法控制 `/vr` 页面**。

**模型体积**：`4.glb` 26.84MB（页面现有逻辑本按体积排序选最小）、`47.glb` 28.16MB、`035d…c64.glb` 88.4MB → 打包总体积约 28MB。

### 2.5 收尾核查发现的证书缺陷（`cce7513`）

法师裁定「当场测」后，AI 核查前置条件时发现：原自签证书**只写 `CN=zhiguan-local`、无 SubjectAlternativeName 扩展**（实证：扩展列表仅 `basicConstraints`）。自 Chrome 58 起证书主机名校验只认 SAN、忽略 CN。

修正：SAN 纳入 `localhost` ＋ `127.0.0.1` ＋ 本机全部局域网 IPv4；`ensure_cert` 每次启动检查现有证书 SAN 是否仍覆盖当前 IP，不覆盖则自动重签（本机 IP 会变：实测 `192.168.43.6` → `192.168.188.105`）。重签后实证：SAN IP `[127.0.0.1, 192.168.188.105]`、DNS `[localhost]`、有效期 2026-09-10~2028-12-14；curl 真实校验退出码 **60 `SEC_E_UNTRUSTED_ROOT`**（自签 CA 不受信任，可点「继续访问」），**非**主机名不匹配。

`local_ips()` 用 UDP `connect()`（**不发包**，仅让内核据路由表选出口地址）＋ `getaddrinfo`（本地解析）取本机 IP，**不出网**，守数据边界纪律。

## 三、决策与共识（决策层）

### 3.1 法师三项裁定（打包方案）

| # | 事项 | 裁定 |
|---|---|---|
| 1 | 装进 Pico 的形式 | ✅ **网页应用 PWA**（官方支持路径，非 WebView 打包 APK） |
| 2 | 是否保留脑电接入 | ✅ **纯引导冥想版**（去脑电，任何人打开即用） |
| 3 | 给谁用 | ✅ **先自己和寺院用**（内部使用，托管从简，不上架不合规审查） |
| 4 | 托管方式 | ✅ **先不托管，只做本机 HTTPS（8778），Pico 当场测，验证通过再决定「局域网自建」还是「公开静态托管」** |

**默认值声明（法师未单独答，AI 按既有裁定取默认并如实标注）**：
- **声音**：引导版默认静音、保留开关，但具备前端自主生成引导音能力（与裁定5「接入但默认静音」一致，不丢「声音气息绵延感」）
- **模型**：用最小的 `4.glb`（26.84MB），与页面既有「按体积排序选最小」行为一致，离线缓存体积也最省

### 3.2 关键架构决策

**单文件双模式，绝不 fork 第二份场景**（守「统一架构不造冗余」）：
- `/vr?mode=guided` → 引导版：零后端零传感器依赖，点开即入
- `/vr` → 脑电版：V2 行为**完全不变**
- 两模式共用渲染／四维分工／粒子避让／声音引擎，**仅数据来源不同** → 以后改场景两版一起受益，不会分叉
- 后端不可达时**自动降级**为引导模式，不给死页面

**引导版参数生成**：两条互质周期正弦叠加（210s / 330s，比值 0.636 非简单整数比 → **不产生拍频**，守对齐方案 §3.2），仍走同一套 EMA（τ=12s）→ 与脑电版共享平滑链路，视觉质感一致。现实锚改用**前端自计时**（`S.elapsed` 由后端推送、引导版恒为 0，不换源则维度4失效、水面永不起伏）。

### 3.3 顺带修复的安全隐患

`/vr_assets/{path}` 静态路由原本可下发 `tls/key.pem`（**TLS 私钥**）。以前影响不大，但 PWA 使 `vr_assets` 成为公开静态目录 → 加拦截：`tls/` 前缀与 `.pem`/`.key` 一律 404。实测 HTTPS 下私钥与证书均 404、SW 缓存中亦无私钥。

## 六、待决事项与风险提示

1. **Pico 浏览器版本风险**：官方要求 **v3.3.36+**（灰度推送中）。若法师设备未更新，安装入口可能不出现 —— 属设备侧版本问题，场景本身照常能跑，届时另想办法（如手动装浏览器 APK 预览版）
2. **本机 IP 会变**：实测已从 `192.168.43.6`（热点）变为 `192.168.188.105`（路由器）。证书已改为 IP 变化自动重签，但**重签后 Pico 需重新信任一次**（点「继续访问」）。且浏览器历史里的旧地址会连不上
3. **H-D 仍是弱验证**：声音默认静音，「能否成底色」未经体感检验
4. **上一轮两处 AI 自我修正（诚实登记）**：
   - 曾称无 SAN「会导致 Pico 当场测失败」——**讲重了**。Chrome 系对主机名不匹配（`ERR_CERT_COMMON_NAME_INVALID`）其实也给「继续访问」，旧证书大概率也能过。补 SAN 的真实价值是去掉多余告警层、消除其它浏览器/WebView 的不确定性，属**稳健化而非救火**
   - 上一轮 `verify_pwa.py` 用了 `--ignore-certificate-errors`，**掩盖了真实证书校验行为**，故当时「SW 注册成功」未在真实校验下验证。本轮补查证书才补上这一环
5. **验证纪律教训（本轮又添一例，累计 6 例）**：`verify_guided.py` 首版误报「脑电版回归、不再连 WebSocket」，根因是 **WebSocket 建立只发 `Network.webSocketCreated`，不发 `requestWillBeSent`**，脚本只监听后者致漏检。已改双证据（ws 事件 ＋ HUD 数据源）。与日志 017 §六.5 的五例同源：**拿想当然的机制/区域/度量当事实**。判据错误不得靠放宽标准掩盖，须查清物理机制后修正
6. **引导版 S.a 为预设流转，非个人化**：引导版不采集任何数据，`saBase=0.52`／`saAmp=0.16` 是固定美学参数，不随练习者状态变化。若将来要「对不同人自适应」，需另立方案（不可在引导版里偷加测量，守红线9）
