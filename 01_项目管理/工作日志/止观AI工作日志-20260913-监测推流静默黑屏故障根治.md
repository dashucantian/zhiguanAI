## 二、事实梳理（事实层）

### 2.1 法师报障原话

> 「看不到脑波图，一直是这个样子。是不是上次把这个 纯监测和 闭环反馈 合并到一个界面当中之后产生了这样的一个问题？检查一下」

截图实况：状态栏「服务就绪」、采集提示「正在连接数据源…」、波形/频段/PSD 区全空。

### 2.2 分层诊断（全部实测，非推断）

**第一步 · 后端状态与前端表现矛盾**

| 观测点 | 结果 |
|---|---|
| `/api/monitor/status` | `{"status":"recording","running":true,"started_at":"2026-09-13 18:52:33","mode":"真机蓝牙"}` |
| 服务进程 | PID 27984 存活 |
| 前端界面 | 永久停在「正在连接数据源…」，波形全空 |

→ 后端认为在采集，前端认为没连上。**分裂状态**。

**第二步 · 第二观察客户端接入推流（决定性证据）**

以只读观察客户端连 `/api/monitor/stream` 观察 10 秒：

```
非tick事件: 🔍 正在扫描 Muse 头环（最长 10 秒）...
非tick事件: ✅ 发现 MuseS-E8D8，正在连接...
非tick事件: 🧠 已连接 00:55:DA:BB:E8:D8 — 数据流传输中
非tick事件: ✅ 已连接，数据流传输中
10秒观察结果: tick=55 ping=0 其他=4
首tick: elapsed=0.7 connected=True packets=137 bands=None
wave通道: {TP9:188点, AF7:188点, AF8:188点, TP10:188点}
末tick: elapsed=14.3 packets=2986
判定: worker 活着且推流递增 → 问题在前端接收/渲染层
```

关键在那 4 条非 tick 事件：它们是 **18:52:33 开始采集那一刻**发出的消息，
到探针接入时（约 19:05）**仍积压在队列中未被消费** → 证明整整 13 分钟
前端一个事件都没取走过。故障层级由此锁定在**推流通道与前端接收层**，
不在采集层、不在 worker。

**第三步 · git 考古否定"合并所致"的猜测**

| 查证 | 结果 |
|---|---|
| `git log -S "connectMonitorStream" -- console.html` | 仅 `2c147ba`（合并半成品基线） |
| `git log -S "api/monitor/stream" -- console_server.py` | **`89996d4`（最初发布 VR 反馈页与控制台骨架）** |
| 09-08 合并大改提交 | `10f7f65` 等，只改前端入口与仪表卡 |

→ 单消费 SSE 设计**自最初发布即存在**，合并大改未动推流架构。
法师的猜测（时间上确实吻合：合并后才高频使用统一界面）**不成立**。

**第四步 · 根因定位（三个缺陷叠加，第四个使故障不可诊断）**

① **线程池饥饿（主因）**：SSE 生成器用
`loop.run_in_executor(None, lambda: MONITOR.events.get(timeout=1.0))` 阻塞取事件
→ 每连接长期占用一个默认线程池线程（上限 `min(32, cpu+4)`）。浏览器
`EventSource` 断线自动重连不断堆积未退出生成器 → 线程池占满 →
新连接的生成器拿不到线程、**永远 yield 不出首条数据** → EventSource 一直 pending
（不触发 `onerror`、也收不到消息）。而 `/api/monitor/status` 是普通 async 接口、
**不依赖该线程池** → 照常返回 `recording`。这精确解释了全部矛盾症状。

② **单消费队列**：多个 SSE 连接互抢事件，任一连接的消费都让其它连接收不到 tick。

③ **队列无界**：无人消费时无限积压（每帧 `wave` 含 4×1280 点）。

④ **前端吞错误**：`monEs.onerror = () => {}`，且全文件**零重连逻辑**
（`connectMonitorStream` 只在页面加载与点开始时各调一次）
→ 一旦断流即永久静默黑屏，无从判断。

### 2.3 AI 自查：我上一轮的验证盲区

09-11 我做 `e2e_audio.py` 时用**模拟源**跑通即判"无回归"，
**未覆盖「前端 SSE 断流」这一真实故障面** —— 这是本故障未被提前发现的直接原因。
验证必须覆盖"资源耗尽／连接异常"这类只在特定运行条件下暴露的形态。

### 3.2 架构决策

- **后端：单消费队列 → 广播注册表（`EventBroadcaster`）**
  `asyncio.Queue` 按订阅者独立分配（非阻塞、不占线程池）；`publish` 用
  `loop.call_soon_threadsafe` 跨线程投递；队列有界（maxlen=200），慢消费者丢最旧一帧
  （推流是实时显示非可靠传输，保实时性优先）；断开时 `finally` 必摘除订阅；
  `start()` 调 `reset()` 清空上次积压
- **`events` 保留为只读兼容属性**指向 legacy 队列：`neuradock_console_selftest`
  直接消费 `MONITOR.events`，避免破坏其接口（守红线5 不建平行路径）
- **同构修复 `ExperimentSession`**：闭环实验路径是同一缺陷，不修必同样复发。
  其 worker 4 处 `self.events.put(...)` 须同步改 `publish(...)` —— 若只把 `events`
  变属性而不改这些 put，事件会只进 legacy、进不了订阅者，**反而弄坏实验流**
- **前端：推流看门狗（纵深防御第二道）**
  由既有 `pollStatus`（3 秒轮询）检测「后端 running 但超 6 秒无事件」→ 主动重连
  （**复用既有轮询，不新建定时器**）；`onerror` 不再吞错误；
  `onopen` 刷新活性时间戳（否则看门狗拿断流前的旧时刻，首帧到达前就误判并反复重连，
  **自我干扰**）；状态栏如实标注「⚠推流 Ns 未更新」；重连≥5次提示
  「数据仍在后台累积，可稍后停止并保存取回」
