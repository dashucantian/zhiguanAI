## 一、四组实测结论

### 实验 1：P 标志是否继承给新建文件

在 OneDrive 同步目录内建探针目录，加 P 后在其中新建文件与子目录：

```
父目录属性：        P
父目录内新建文件：  A  P     ← 继承了
父目录内新建子目录：   P     ← 继承了
```

**结论：P 标志会继承。** 所以"新建文件不受保护"这个担心，在父目录已有 P 的前提下不成立。

### 实验 2：`.git` 内为什么有文件没 P

全量扫描 `.git`：49 个文件，48 个带 P，**唯一不带 P 的是 `.git\index`**。

机制现已明确：

- `.git` 根目录**没有 P**（上轮 attrib 单参数失败）
- `.git\objects\` 等子目录**有 P**（上轮 `attrib +P ".git\*.*" /S /D` 作用于内部项）
- git 更新 index 的方式是"写 `index.lock` → 改名为 `index`"，**改名产生新文件**，继承的是**根目录**属性（无 P）

**所以漏洞的根因是根目录缺 P，受害的是 git 用"改名替换"方式更新的文件**——index、packed-refs、HEAD 之类。objects 下的对象文件因为子目录有 P，反而都受保护。

### 实验 3：隐藏目录能否加 P（三种写法对比）

| 写法 | 结果 |
|------|------|
| `attrib +P <隐藏目录>` | **失败**，报 "Not resetting hidden file" |
| `attrib +P +H <隐藏目录>` | **成功**，属性变为 `H  P` |
| `attrib -H` → `+P` → `+H` | **成功**，属性变为 `H  P` |

**结论：`attrib +P +H` 一条命令即可修复 `.git` 根目录。** 这是纯保护性、可逆操作（`attrib -P` 撤销）。

### 实验 4：git 的归因与隔离能力（临时目录演练，已清理）

**4a. separate-git-dir（把 `.git` 搬到工作区之外）**

```
git init --separate-git-dir=<外部路径> <工作区>
→ 工作区 .git 变成一个指针文件，内容："gitdir: <外部路径>"
→ 外部 gitdir 真实存在，提交、读取日志全部正常
```

**可行。** 这意味着书稿可以留在 OneDrive（照常同步），而 git 历史库放在 OneDrive 之外。

**4b. author 与 committer 分离**

```
git -c user.name='AI助理(qwen3.8-max)' -c user.email='ai@local' \
    commit --author='宗国法师 <fashi@local>' -m '...'
→ 实测结果：author=宗国法师 | committer=AI助理(qwen3.8-max)
```

**可行，且这正是法师要的归因结构**：作者（内容出自谁）与提交者（谁执行了提交）可以是两个不同身份。

**4c. 提交信息 trailer（记录模型与窗口）**

```
提交信息：
  正文测试

  Model: qwen3.8-max
  Agent-Window: session-abc
→ 实测完整保留，git log --pretty=%B 可读回
```

**可行。** trailer 是 git 原生机制（`Signed-off-by:` 就是同类），可稳定承载模型名、会话标识、窗口标识。

## 二、问题一：把 git 放在 OneDrive 里合适吗

### 2.1 四个风险，逐个定性

| # | 风险 | 严重度 | 能否解决 |
|---|------|--------|---------|
| R1 | **脱水损坏**：OneDrive 把 `.git` 内文件转为云占位符，git 读到占位符即报错甚至损坏仓库 | 中 | **能**，`attrib +P +H`（实验 3） |
| R2 | **双写冲突**：OneDrive 同步与 git 写入同一批文件，可能产生 `xxx (1).md` 冲突副本，污染工作区 | 中 | 部分能，靠"改文件时不同时同步"的纪律，无法根治 |
| R3 | **git 历史上云**：`.git` 内含**全部历史版本的全部内容**。一旦云端同步开放，L3 内容（僧团事务、成员真名、未定型条款）连同历史一起进入微软云 | **高** | **不能**，只要 `.git` 在同步范围内就必然上传 |
| R4 | **`.gitignore` 对 OneDrive 无效**：gitignore 只约束 git，**OneDrive 照样同步被 gitignore 排除的文件** | 需知悉 | 不适用（见下） |

**R3 是本问题的决定性风险。** `.gitignore` 给了一个错觉：以为排除掉的内容就安全了。实际它只防"进 git"，不防"上 OneDrive 云"。而 git 历史是**累积**的——即便某次误提交了敏感内容、后来删除并重新提交，**历史里仍在**，上传即全部上传。

**R4 需要法师知悉的现状**：OneDrive 的同步单位是整个 `zhiguanAI` 文件夹，因此 `02_修道班运营\机密-学员数据\`（781 MB）**本来就在 OneDrive 同步范围内**——这不是 git 带来的新风险，是既有状态。法师提到"云端同步有时会开放"，那么**开放时这批机密学员数据会上微软云**。这一条与本方案无关，但必须报。

### 2.2 三个方案对比

| | 甲 · separate-git-dir（**AI 建议**） | 乙 · 留 OneDrive 内＋修 P 标志 | 丙 · 书稿整体移出 OneDrive |
|---|---|---|---|
| 做法 | 工作区留 OneDrive，`.git` 搬到 `C:\Users\tiand\.zg-book-repo\`，工作区 `.git` 变指针文件 | `.git` 不动，`attrib +P +H` 补根目录 | 把 `共创出书` 等目录移到 OneDrive 外 |
| R1 脱水 | **消除**（不在同步范围） | 基本消除（须每次新建子目录后补 P） | 消除 |
| R2 双写冲突 | **大幅降低**（git 内部文件不再被同步） | 仍存在 | 消除 |
| R3 历史上云 | **消除** | **不解决** | 消除 |
| 书稿能否云端查看 | **能**（工作区照常同步） | 能 | **不能** |
| 换机器时 | 指针指向的路径不存在 → git 命令失效，但**文件照常可看可读**（可接受降级） | git 可用（历史随云同步） | 需另行拷贝 |
| 实施成本 | 中（须迁移 `.git`，约 10 分钟，含验证） | 低（一条命令） | 中 |
| 与"统一架构不造冗余" | 符合（仍是一个仓库，只是库位置外移） | 符合 | 符合 |

**建议甲，理由三条**：

1. **它分离了两个本该分离的关注点**：内容的跨设备可见性（OneDrive 负责）与版本历史（git 负责）。法师在外面想看稿子，OneDrive 照旧；git 历史含 L3 全文，不该上云。
2. **R3 无法用其他手段解决**。只要 `.git` 在同步范围内，历史必然上云。乙方案修得再好也修不掉这一条。
3. **降级方式可接受**。换机器时 git 不可用，但**文件完全正常**——而法师在别的机器上大概率只是看稿、改稿，不需要跑 git。回到本机，git 立即恢复。

**甲方案的代价须如实说明**：`.git` 移出 OneDrive 后，**git 历史不再受 OneDrive 备份保护**。本机硬盘故障会同时丢失工作区（若无云同步）与历史。缓解办法：定期把 `.git` 打包备份到法师指定的另一处（本机其他分区／移动硬盘／私有云），但这需要法师定策略，本方案不代定。

**乙方案不是不能用**，它适用于"法师认为 git 历史上云可接受"的情形。若采乙，则至少须：① `attrib +P +H` 修根目录 ② 每次 git 操作后检查新建子目录的 P 继承 ③ 接受 R3。

### 2.3 一个必须澄清的误解

法师问"如果在这里新建文件夹或者文件的话，会怎么样"——若指 `.git` 内部：**git 自己新建的文件会继承所在目录的 P 标志**（实验 1 已证），所以只要根目录补上 P，后续 git 操作产生的文件都会自动受保护，不需要每次手工补。

若指**书稿目录内新建文件**：那些文件本来就该被 OneDrive 同步（法师要在外面看），不需要 P 标志，也不该加。

**唯一需要长期留意的是**：若将来在 `.git` 内手工新建子目录（极少见），须确认 P 继承。正常 git 使用不会产生这种情况。

## 三、问题二：修改之后不做记录吗

### 3.1 现状实测：有记录，但**记错了人**

本轮三次提交的归因，实测如下：

```
f64f0f5 | author=dashucantian <dashucantian@users.noreply.github.com>
        | committer=dashucantian <dashucantian@users.noreply.github.com>
7e0d9d2 | author=dashucantian <同上>  | committer=dashucantian <同上>
dfe08dd | author=dashucantian <同上>  | committer=dashucantian <同上>
```

**三次提交全部由 AI 执行，但 author 与 committer 都署的是法师的 GitHub 账号。**

根因：仓库本地配置 `user.name=dashucantian`、`user.email=dashucantian@users.noreply.github.com`（09-06 打通 GitHub 远程仓时设的，当时是为了 push），AI 提交时未指定身份，git 就用了这个配置。

**所以法师的理解需要修正一处**：不是"不做记录"，是**记录存在但归因错误**——而且错得很危险：将来翻历史，会以为这些改动都是法师自己做的。

### 3.2 法师的理解哪部分正确

> "只是保留了改写的版本迭代可以查询，是这样吗？"

**这部分正确**。git 确实完整保留了：

- 每次提交的**时间**（author date 与 commit date 分开记）
- 每次提交的**完整变更内容**（哪一行从什么变成什么，字符级）
- 提交信息（可写"为什么改"）

本轮已验证：`git log --oneline` 可查三次提交，`git diff` 可看任意两版差异，`git cat-file` 可从库中读出任意版本的文件内容（别编 07 读出 25568 字节）。

**缺的不是"版本迭代可查"，缺的是"归因正确"。**

### 3.3 一个必须诚实说明的技术边界

法师要求"知道是谁、在什么时间改的"。**"什么时间"和"改了什么"git 能自动记录；"谁改的"git 无法自动得知。**

原因：

- NTFS 记录文件的 **owner**（创建者），但**不记录每次修改者**。owner 是法师的 Windows 账号，无论谁改都一样。
- git 记录的是**提交者**，而**提交 ≠ 修改**。AI 今天提交的内容，可能是法师三天前改的。
- 想在"修改的那一刻"捕获修改者，只有两条路：**监控文件系统／键盘**（已被 09-06 裁定否决，四条依据仍成立），或**修改时主动声明**。

**所以归因只能靠"约定＋提交时确认"，不可能全自动。** 这不是方案缺陷，是技术边界。任何声称能自动准确归因的方案，要么在监控（违法且已否决），要么在猜（不可靠）。

## 四、问题三：归因机制设计

### 4.1 git 原生能力已够用（实验 4 已验证）

三层归因，全部用 git 原生机制，不需开发：

| 层 | 字段 | 记什么 | 实测可行 |
|---|------|-------|---------|
| 1 | **author** | 内容的实际作者：法师口述／法师手改＝法师；AI 撰写＝AI | ✅ `--author=` |
| 2 | **committer** | 执行提交者与时间：通常是 AI（因为是 AI 在操作 git） | ✅ `-c user.name=` |
| 3 | **trailer** | 模型名、会话／窗口标识、改动依据 | ✅ 提交信息尾部 |

建议的提交信息格式：

```
docs(别编06): 订正"制成"为"自成"

法师 2026-09-11 指出引语转写讹误，据逐字稿原件核验后
全量更正四处扩散点，并登记台账 KZ-001。

Author-Role: 法师口述订正
Model: qwen3.8-max
Agent-Window: <会话标识>
Errata: KZ-001
```

对应 git 记录：`author=宗国法师`、`committer=AI助理(qwen3.8-max)`、时间为提交时刻。

### 4.2 多 AI 多窗口场景（法师特别提到）

法师说"后续所有 AI 参与到项目中来的时候，它随时会在各个窗口对任务执行改写"。这里有**两个不同性质**的问题，须分开处理：

**问题 A：归因（谁改的）**

每个 AI 窗口提交时，在 trailer 写明自己的身份。但有一个诚实的限制：**AI 不一定能可靠获知自己的会话标识**——这需要实测确认。若拿不到，退而求其次用"模型名＋提交时刻＋改动范围"三者组合，实践中足以区分不同窗口。

建议建一份**代理身份登记表**（`01_项目管理\AI代理身份登记.md`）：每个 AI 窗口首次参与项目时，登记自己的模型名、承担范围、首次提交时间。这样 trailer 里的标识有对照可查。

**问题 B：并发（同时改同一文件）**

这比归因更危险。多个 AI 窗口同时改一个文件，后写的会覆盖先写的，**且 git 察觉不到**（git 只在提交时比对，不监控工作区）。

可行的纪律（不开发、纯约定）：

1. **改前先提交**：任何 AI 动手改文件前，先 `git status` 确认工作区干净；若有未提交变更，先处理（提交或报告），不叠加。
2. **改后即提交**：一轮改动完成立即提交，缩短工作区暴露时间。
3. **认领制**：同一时段一个文件只由一个窗口负责（可借飞书看板的承担者字段）。
4. **冲突不强行覆盖**：发现工作区有非自己产生的变更，**停下报告**，不覆盖（与项目既有"删除／覆盖遇同名项先保留两边并询问"同一纪律）。

**这套纪律的关键是第 1 条和第 4 条**：它们把"静默覆盖"变成"显式停下"。

### 4.2bis 本轮实测捕获的并发实例（2026-09-11 19:47）

**这不是假想场景，是刚刚发生的实况。** 在法师提出三问、我做实测核验时，`git status` 显示工作区有 **47 条未提交变更**，构成如下：

**被删除的文件**：`01_项目管理\止观AI模型使用与AI协作经验台账.md`

- 本 AI 于 19:06 基线提交时将其入库，blob **22,903 字节，内容完好可恢复**（`git cat-file -s` 与 `git show` 已验证）
- 现已**从磁盘消失**
- 40 个未跟踪文件中**无任何同类台账文件** → 判定为**纯删除，非改名重构**

**被修改的 5 个文件及其时间戳**（均非本 AI 触碰）：

```
19:11:34  评测集黄金任务集_素材\README_L4线素材说明.md
19:15:17  20260910_评测集黄金任务集_v1.md
```

**这个实例同时验证了三件事**：

1. **L1 的价值得到实证**：若没有 git，这 5 处修改与 1 处删除**完全不可见**——法师不会知道自己的《模型使用与 AI 协作经验台账》已经不在磁盘上了。git 让它当场暴露。

### 4.3 法师自己改文件时怎么归因

这是最难的一环，因为法师改文件时不经过 AI，没有任何自动记录。三个方案：

| | 做法 | 可靠性 | 成本 |
|---|------|-------|------|
| 甲 | **约定式**：法师改完后在对话里说一句"我改了别编 06 的某处"，AI 提交时署 author=法师 | 中（依赖法师记得说） | 极低 |
| 乙 | **提交时确认**：AI 检测到未提交变更后，把变更内容列给法师，问"这是您改的还是我改的"，按答复归因 | **高**（每次都有确认动作） | 低（每次多一轮问答） |
| 丙 | **编辑器插件**：法师用特定编辑器改文件时自动记录身份 | 高 | 高（须开发，且法师可能用记事本／Word） |

- 乙把归因变成**每次提交都发生的固定动作**，不依赖法师记得主动说。AI 反正要提交，多问一句成本极低。

**乙的一个副作用是好的**：它迫使每次提交前都过一次"这些变更是什么"，等于自动做了一次变更审查，能及早发现误改。

### 4.4 时间记录的精度问题

git 自动记录两个时间：**author date**（内容创作时间）与 **commit date**（提交时间）。

法师要"什么时间改的"——严格说 git 记的是**提交时间**，而实际修改可能更早（比如法师周一改的，AI 周三才提交）。

缓解：提交时在 trailer 里注明实际修改时间（若可知）。但**这同样依赖声明**，无法自动获取文件的"最后修改时刻"作为可靠依据（OneDrive 同步、attrib 操作都会改动时间戳）。

**诚实结论：时间记录能精确到"提交时刻"，"实际修改时刻"只能靠声明，可能有偏差。** 若法师要求严格的修改时刻记录，那就必须上文件监控——已被否决，且违法风险高，不建议重启。

## 六ter、E14 联网查证（2026-09-12 法师令"先实测清楚 E14"）

E14 的核心是"丙 OneDrive 选择性同步排除 `.git`"能否成立。本机进程未运行（启动 OneDrive 会触发 L3 上云，AI 绝不擅自启动），无法本机实测；此点属**公开技术语义**，故联网查证微软官方与社区，不凭记忆断言。三条独立来源高度一致，**结论：丙不可行。**

**查证 1：`attrib +P`（始终保留在本机）防不防上传？**

微软官方 Q&A 原话：标记"Always keep on this device"后，"**it will still sync simultaneously** … When you connect to the internet, OneDrive will automatically sync the changes you made to the cloud server." 即 **+P 只保证本地不被脱水（不被 Storage Sense 清回云占位），完全不阻止上传**。

→ **直接更正本稿上一轮结论**：我上轮给 `.git` 加 P 标志，对 R1（脱水损坏）有效，但对 **R3（历史上云）毫无作用**。当时把 P 当成了"保护"，夸大了它的能力范围——这是本会话**第四次**凭推断说大效果（前三次：KZ-004、OneDrive 两处错误、notes 假阴性），记入台账。

**查证 2："选择文件夹"控制上传还是下载？**

微软社区支持原话：设置里"选择文件夹"的列表"**is not for choose what to sync FROM your computer to the cloud. Rather, it is the opposition**（相反方向）. It is to choose what's already in the cloud to sync TO your local computer." 即**它只控制"云端哪些文件夹下载到本机"，不控制"本机哪些文件夹上传到云端"**。

**查证 3：能否排除同步根内的子文件夹上传？**

微软论坛审阅人＋SuperUser＋多个来源一致：OneDrive 是 **scope-based（范围式）同步，不是 rule-based（规则式）备份**，"**There is no way to exclude a child folder within a root folder that is configured to synchronize to OneDrive**"（无法排除已配置同步的根文件夹内的子文件夹），"no ignore file or exclusion list"（没有 ignore 文件或排除清单）。唯一办法是"**move that sub-folder out**（把子文件夹移出同步根）"。

**E14 查证结论**：

| 设想 | 查证结果 |
|------|---------|
| 丙 选择性同步排除 `.git` | **不可行**——选择文件夹只控下载方向，且无法排除同步根内子目录上传 |
| `.git` 留 OneDrive 根内、靠设置阻止上云 | **无解**——OneDrive 无 ignore 机制，根内任何内容都会上传 |
| 唯一能阻止 `.git` 上云的办法 | **把 `.git` 物理移出 OneDrive 同步根**＝E1 甲 separate-git-dir |

**故 E14 收敛为 E1 甲（外移），丙方案撤销。** 这也反过来印证 GPT 与本稿的共同结论（`.git` 不该留 OneDrive 内）是对的，而 GPT"靠目录分级即可、不必搬 .git"的主张被这组证据进一步否定——**目录分级同样无法阻止已 commit 进 `.git` 的内容上云**。

**连带影响 E9**：`02_修道班运营\机密-学员数据\`（781 MB）要不上云，同样不能靠"选择性同步排除"（已证伪），只能整体移出 OneDrive 根或确认其可上云。E9 行已据此更正。

**一处本机实测补充（对照组方法）**：曾尝试用 OneDrive 日志反查 `.git` 是否已被同步过——但实测 4320 个日志**全为二进制格式**（.odl／.etlgz），明文路径检索不到（"zhiguanAI" 0 命中是格式所致，非未同步）。故日志路径无法证明同步状态，**改以"路径物理位于同步根内"这一硬事实判定**：`C:\Users\tiand\OneDrive\zhiguanAI`（含 `.git`、11017 文件、3189 MB）确在同步根 `C:\Users\tiand\OneDrive` 内，默认在同步范围。同步根内另有 `Desktop(1)`、`Zen-EEG(1)`、`图片(1)` 等 OneDrive 冲突副本，旁证同步曾运行并产生过冲突。

## 七、一句话结论

**三个问题的答案**：

1. **git 放 OneDrive 里不合适**——不是怕脱水（`attrib +P +H` 能修），是怕**历史上云**：`.git` 含全部内容的所有历史版本，云端同步一开放就全上微软云，且 `.gitignore` 管不着 OneDrive。建议用 `separate-git-dir` 把 `.git` 外移，书稿留在 OneDrive 照常同步。
2. **有记录，但记错了人**——本轮三次提交全是 AI 做的，author 与 committer 却都署着法师的 GitHub 账号。版本迭代确实完整可查（时间、字符级差异、历史版本内容都能取回），缺的是归因正确。
3. **"谁改的"只能靠声明，不能自动获知**——git 原生支持 author／committer 分离＋trailer 记模型名（均已实测可行），足够承载"谁、什么模型、什么时间"；但**文件系统本身不记录修改者**，想自动捕获就得上监控（已否决且违法风险高）。建议"提交时确认"为主：AI 每次提交前把变更列给法师、问明归因，顺带完成一次变更审查。

**最该立刻处理的是 E4**：现在每提交一次，就多一条署着法师名字的 AI 改动。
